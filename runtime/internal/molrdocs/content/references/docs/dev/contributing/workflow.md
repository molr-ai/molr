# 开发协作流程

本文维护任务隔离、分支、验证、提交、合并与清理流程。开发环境见[环境约定](https://molr.ai/zh/docs/dev/contributing/environment/)，验收入口和服务生效见[验收规范](https://molr.ai/zh/docs/dev/contributing/acceptance/)。

## 适用范围

- 先按修改对象判断是否需要 worktree：已由 Git 跟踪或计划纳入版本管理的代码、测试、配置和文档，适用本节的独立分支与 worktree 流程。尚未跟踪但准备提交的新文件也属于此范围。
- 仅维护 `internal-docs/` 等已被 Git 忽略、且不准备提交的内部资料（如推广文案、研究笔记、内部规划）时，直接在资料原位置修改；不为此创建分支或 worktree，也不走提交、合并、服务验收或项目构建测试流程。交付时提供文件链接并核对内容及引用资源即可。若同一任务还涉及版本管理范围内的修改，则按本节创建 worktree；随开发产生的内部记录保存在该任务 worktree，已有内部资料仍在原位置维护，清理时按[公开内容与内部资料](https://molr.ai/zh/docs/dev/releasing/public-content/#公开内容与内部资料)要求保留资料。
- 主工作目录（仓库的主 worktree，可通过 `git worktree list` 确认）固定保留 `main`，用于查看代码、同步 GitHub 已合并的主线和运行主分支服务。**禁止直接在主工作目录修改代码，也禁止在该目录切换到功能分支进行开发。** 上述版本管理范围内的功能开发、修复、重构及其测试、配置和文档修改均在独立 worktree 中完成。

## 主线与 PR 门禁

- GitHub 仓库的 `main` 是主线的权威来源，版本管理范围内的改动统一通过 GitHub PR 合并。本地 worktree 负责开发和独立验收；主工作区只快进同步远端主线，不再本地合并任务分支或直接推送 `main`。
- 本文命令以 `github` 表示指向上游 GitHub 仓库的远端。先用 `git remote -v` 核对地址；实际名称不同则替换命令中的名称，不假定 `origin` 就是上游。Fork 贡献者从上游主线创建分支，向自己的 fork 推送并向上游提交 PR。
- 保留 Gitea 时，其 `main` 只从 GitHub 单向同步，不独立接收主线合并；Gitea CI 可用于补充验证。切换流程前核对两端历史，尚未进入 GitHub 的提交通过任务分支和 PR 集成，不用强制推送覆盖差异。
- 维护者应在 GitHub 为 `main` 配置 PR 合并要求、线性历史、必需检查 `CI passed v3`，以及合并前分支必须与目标主线保持最新；禁用强制推送和删除主分支，常规开发不绕过保护。允许 Squash merge 和 Rebase merge，不使用 merge commit。启用门禁前核对实际工作流的检查名称和成功运行记录；文档约定不代表远端设置已生效。检查名称变化时同步维护分支规则。
- `CI passed v3` 汇总源码、构建、浏览器和安装等任务，任何必需任务失败、取消或意外跳过都不能合并。PR CI 通过后仍需用户验收和明确合并授权；当前流程不额外要求多层审批或 merge queue。

## 开始任务与开发

- 开始任务前先检查 `git status --short --branch` 和 `git worktree list`，确认当前目录、分支与已有任务。不得覆盖、重置或清理他人的未提交变更。
- 每个独立任务使用一个分支和一个 worktree；先执行 `git fetch github`，从最新的 `github/main` 创建，如已有该任务的 worktree，则继续使用。分支名使用 `feat/<task>`、`fix/<task>` 或 `chore/<task>` 等有明确含义的名称。无法获取远端时明确报告未核实最新主线，不把缓存引用当作最新状态。
- worktree 推荐放在主工作目录下的 `.cache/worktrees/<task>`，该目录由现有 `.cache/` 忽略规则排除，不纳入 Git 提交。例如，在主工作目录执行 `git worktree add --no-track -b feat/<task> .cache/worktrees/<task> github/main`。路径统一以主工作目录为基准，不在任务 worktree 内嵌套创建。不能创建 worktree 时先解决路径或权限问题，不得退回主工作目录直接开发。
- 创建后，版本管理范围内的编辑、依赖安装、代码生成、构建、测试及提交都以对应 worktree 为工作目录。并行任务不得共用同一个 worktree，也不得修改其他任务的 worktree。
- Runtime 新增、删除或改名公开函数、具体方法或接口方法时，同步维护 `runtime/tests/coverage-*.md` 中的行为测试映射；嵌入接口展开的方法也需要登记。局部包测试通过后仍须运行 `npm run check:contracts`，提交前和 rebase 后运行 `npm run check`。映射必须引用实际验证该入口行为的测试，缺少断言时补测试，不得自动填入无关用例或跳过清单检查。`make -C runtime test` 等测试入口会先执行全仓库契约清单检查，不受 `PACKAGES`、`RUN` 筛选影响。
- 各 worktree 的依赖安装目录、构建产物、编译缓存和 Runtime 测试数据独立管理；持久验收实例及其私有记录按[实例目录约定](https://molr.ai/zh/docs/dev/contributing/environment/#实例私有目录与源码隔离)放在源码树外，按任务关联和清理；可复用下载遵守[共享下载缓存约定](https://molr.ai/zh/docs/dev/contributing/environment/#开发机器目录与共享下载缓存)。不得复用或修改主工作目录的运行数据库、凭证及私有数据目录。开发和验收期间不得停止或替换其他任务或主分支的服务；合并完成后按[合并后的服务生效](https://molr.ai/zh/docs/dev/contributing/acceptance/#合并后的服务生效)要求更新主分支服务。

## 后台等待与轮询门禁

内部权限、计划、任务、消息和持久化状态的变化，默认由提交后通知唤醒；已知过期时间使用最近到期定时器。订阅必须先于读取，事务回滚不唤醒，取消／关闭必须释放订阅和定时器。没有新事件、没有到期边界、没有待重试失败时，不得周期性查询数据库或重复读取状态。查询加索引或延长轮询间隔不能替代此约定。

外部系统没有通知能力、协议要求心跳、系统指标需要间隔采样、可见界面需要动画或时间显示时，可以使用定时工作。每处必须明确：

- 为何无法使用事件或已知截止时间；单次超时、退避重试、协议心跳与持续轮询应分别说明。
- 每个实例的最小间隔／最大频率、启用条件、空闲调用预算、重试退避和截止条件；请求不得重叠，后台工作随所属上下文结束，前端按可见性与订阅生命周期停止。
- 可执行的行为证据：初始化后推进时间仍没有多余存储／HTTP 调用，变化立即唤醒，到期生效，取消后无残留工作。优先使用虚拟时钟与实际调用计数；只断言“配置间隔大于某值”不能证明空闲行为。

`npm run check:polling` 解析全部平台的 Runtime Go 源码、各应用／包的 TypeScript 源码及发布观察命令 `scripts/watch-release.mjs`，检查定时器、等待、Reset、前端轮询协调器和显式查询间隔。生产 `realtime.NewFeed` 必须显式提供 `WatchAuthorization`，`scheduler.NewService` 必须提供 `TickSignals` 与 `NextTick`；缺少这些能力时不能通过添加例外清单放行。新增入口、重复入口数量变化、延迟／局部频率表达式变化和过期登记都会失败；新建但尚未提交的源文件同样参与检查。`scripts/polling-policy.json` 记录现有入口的用途、运行预算与相关测试。`--list` 只输出观测清单，不提供自动更新／自动接受命令。失败时先评估事件方案；确需保留时逐项复核并在同一次变更中更新预算和测试，不得批量重建清单以消除失败。已有例外不能作为新业务照搬轮询的依据。

`npm run test:polling` 执行扫描器的反例测试、前端虚拟时钟请求预算，以及权限观察器、调度器、事件流和渠道投递的空闲／变化／到期契约。指定契约被删除、跳过或没有实际执行时也失败。静态检查接入 `npm run check`；行为契约在 GitHub 与 Gitea CI 的 source 阶段执行。新增后台服务应加入对应的空闲契约，不只登记定时器。

静态门禁是局部语法检查，不能证明任意封装、跨文件配置或第三方库没有轮询，也不会把全部定时器都判断为 SQL 查询。修改共享频率配置或等待封装时，应一起审查其调用方并补调用预算测试。代码审查须核对业务路径的实际调用数，不能仅依据清单通过判断设计合理。

## 验收、合并与清理

- 提交、推送、创建 PR 和合并按用户已授权的范围执行；已有授权不重复询问，完成开发本身不代表获得推送或合并授权。推送前按公开内容规范审查实际内容及暂存区。在授权范围内推送任务分支并创建面向上游 `main` 的 PR，未完成验收时可使用 Draft PR。
- PR 应对应一项范围清楚的逻辑改动，说明解决的问题、最终行为、验证结果和未完成项；标题和描述随最终实现更新。默认使用 **Squash merge**，将开发和审查过程中的修补提交合为一个主线提交，最终提交信息说明改动及原因并关联 PR。可独立验收的改动优先拆成多个 PR；确需保留有独立意义的提交序列时，在 PR 中说明原因，整理并验证各提交后使用 **Rebase merge**。
- **任务完成后必须先提供验收入口并等待用户验收，不得直接合并。** 只有用户验收后明确授权合并，且当前 PR 的必需检查通过，才能在 GitHub 合并；开发完成、测试通过、PR 创建或提供验收链接均不代表获得合并授权。等待验收期间保留任务 worktree 和验收服务。一次性登录链接、私有部署地址及详细验收资料通过私有渠道交付，不写入公开 PR。
- 合并前在任务 worktree 内执行 `git fetch github` 和 `git rebase github/main`，不得使用 `git merge main` 或 `git merge github/main` 同步任务分支。冲突在任务 worktree 内解决，完成后运行 `npm run check` 和相关验证，更新 PR 并等待当前版本的 CI 通过。多个 PR 按顺序集成；前一个合并后，后续任务重新同步并验证。已共享分支在 rebase 前协调使用者，重写远端任务分支须有明确授权并使用 `--force-with-lease`，不得覆盖他人的新提交。验收后有影响验收结论的改动时重新提供验收，不沿用旧结果。
- 在 GitHub 合并时核对 PR 的目标分支、最终 head SHA、合并方式、检查和授权对应同一版本；head 变化时重新核对，不启用未经授权的自动合并。合并后记录最终主线提交，再执行 `git fetch github`。确认主工作区干净且本地 `main` 是 `github/main` 的祖先后，以 `git merge --ff-only github/main` 同步；发现本地独有提交或分叉时保留现场并查明原因，不 reset 或强推覆盖。确认 PR 的最终主线提交已包含在同步后的 `main`，再按验收规范完成[主服务生效](https://molr.ai/zh/docs/dev/contributing/acceptance/#合并后的服务生效)。
- 交付时说明任务分支、worktree 路径、PR 链接（尚未创建则说明）、验证结果及合并状态；合并后同时说明最终主线提交和主服务生效情况。按[验收交付标准](https://molr.ai/zh/docs/dev/contributing/acceptance/#验收交付标准)提供验收入口；仅 worktree 验收服务中需要登录的页面要求提供可直接登录的一次性链接。主工作区服务提供普通访问地址即可，无需生成或提供登录链接。
- **合并成功且主分支服务生效验证通过后，必须清理本任务的 worktree，无需等待用户再次要求。** Squash/Rebase merge 会生成新 SHA，不能仅用 `git branch --merged` 或任务分支是否为 `main` 的祖先判断完成。核对 PR 已合并、对应的最终 head 与本地任务 HEAD 一致、最终主线提交已包含在本地 `main`，且没有未提交变更或合并后新增提交；不一致时保留 worktree 查明原因。精确停止该 worktree 的验收服务，按[保留上限](https://molr.ai/zh/docs/dev/contributing/environment/#验收资料与备份保留上限)删除历史验收资料、仅保留一份开发环境备份；产品需求、研究和推广成果按公开内容规范保留，再使用 `git worktree remove` 移除目录。不得因分支显示“未合并”而批量强删，也不得影响其他任务的 worktree 或服务。合并交付时说明清理结果。
