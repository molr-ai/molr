# Resource and File Tool Contracts

Updated: 2026-10-06. This document is intended for tool and Runtime developers; for user authorization operations, see [Resources and Permissions](../../../docs/en/guides/permissions-and-budget.md), and for the runtime environment, see [Linux Command Environment](../../../docs/en/sandbox/linux.md).

## Explicit Full Access Calls

`shell_execute` and `file_*` accept an optional `full_access`; omitting it or setting it to false maintains standard isolation and scope checks. Setting it to true requires that the selected node allows this capability and that the assistant holds a valid Full Access compute authorization; file calls do not substitute directory authorization for this permission, nor do they automatically switch paths due to existing Full Access authorization. Full Access file paths can be absolute paths, with `/work` retained as an alias for the current assistant's workspace; standard calls still reject paths outside the workspace and directory authorization. Multimodal snapshots retain the FullAccess flag and re-authorize upon loading.

`Requestable.FullAccessAvailable` indicates requestable, while `Resources.FullAccess` and `Sandboxes.FullAccessComputeIDs` indicate explicitly called and currently authorized; `Grants[].Scope.FullAccess` distinguishes authorization types. The model's structured projection retains these fields and `full_access` during requests to prevent loss of permission semantics in the context.

## How Models Understand Resources and Permissions

`permission_list` (formerly `resource_list`) groups queries for the current assistant's obtained authorizations, the catalog of requestable permissions, and built-in capabilities, which remain usable even when Shell is disabled. Old tool names are no longer published or accepted. It returns compute, storage, network, and specific models based on the current assistant's effective authorizations, without returning host paths or credentials. The `Grants` for each resource scope retains the ID, Actions, Scope, and ExpiresAt of effective authorizations, and separately provides `Operations`: operations, usage pathways, current availability, and reasons for unavailability. Capability snapshots are not authorization credentials; actual execution still re-checks permissions, validity periods, and deployment restrictions.

- `Source: "user_grant"` in `Resources` indicates user-authorized resources. Storage `Path` uses paths within the resource, and `/` is explicitly marked as `resource_root_not_host_root`, not the system root directory. Write permission for one directory cannot extend to another; authorizations for different models are not merged into authorizations for all models of a Provider.
- `Requestable` provides secure metadata for resources in the shared resource directory that the current account can request, are connected, and are not disconnected, including ResourceID, Name, Kind, SandboxID, and supported Actions; models are precise to ModelID/ModelName, and `/` in storage PathPrefixes indicates the maximum scope within the resource. It only describes what can be requested, not what is already authorized or currently available. Maximum 200 items; if exceeded, marked as RequestableTruncated; CurrentTime is used to determine the expiration time of requests.
- `Source: "runtime"` or `"sandbox"` in `BuiltInStorage` indicates capabilities inherent to the compute environment. `/work` belongs to the current assistant and persists across executions; `/global` is a read-only file directory shared by the current account (AGENTS.md, skills, memory), where file tools and local Shell use the same files; `/tmp` belongs only to the current command execution and is recreated for the next execution. The workspace is read-write by default via `file_*`, not relying on additional storage or compute authorization, but requires the target sandbox storage to be available; regular members also need corresponding sandbox and tool group references; compute isolation readiness does not determine file capabilities; `Operations` separately explains the compute authorization required for Shell pathways. Temporary directories are used only through the current `shell_execute`. These built-in directories are not listed as external directories granted by users.
- User authorization is not inferred from directory permission bits or file existence; internal paths such as `/molr` do not belong to business resource directories.
- `file_read`, `file_write`, and Shell share storage bindings, path authorizations, and deployment directory restrictions. Writing with file tools can use write-only authorization, but Shell's writable mount also exposes reading, so both read and write authorizations are required; queries separately explain the availability of these two operations.

Shell only mounts the resource scopes selected in the request. `permission_list` returns a stable `ShellPath` in the form of `/resources/r_<资源 ID 摘要>/<资源内路径>`; the same resource and path are unaffected by name or request parameter order. Directories with the same name in different resources do not conflict. Scripts directly use the returned paths and do not need to calculate digests themselves. Overlapping or duplicate mount scopes are rejected; when only subdirectories are authorized, host parent directories and sibling directories are not exposed.

## Authorization Requests

`permission_request` creates a request but does not directly grant permissions. Required fields include `resource_id`, `resource_kind`, `resource_description`, `actions`, `reason`, and a future RFC3339 `expires_at` (for combined requests, set only at the top level, with items in `additional_requests` inheriting the same time); storage must fill in `path_prefixes` within the resource. Must select a real `resource_id` from `permission_list.Requestable`; model requests also require the belonging `model_id`. Requests for unknown resources or with only descriptions are rejected before creation, without generating cards or waiting states; administrators must first connect and assign resources. Compute, network, and managed workspace requests also require quotas; see [Resource Authorization Quotas](../security/resource-quotas.md#data-and-approvals) for combined requests and validation rules. Tool descriptions require least privilege: request only the resources needed for the current task, the fewest operations, the narrowest scope, and the shortest reasonable authorization time; do not default to whole-resource or permanent authorization. The entire request is at most 4096 bytes, and a single assistant has at most 20 pending approval requests; identity and task are determined by the execution context, and owner or assistant IDs passed by the model are not accepted.

Requests, assistant chat cards, and tool operation receipts are committed as `pending` within the same transaction; if submission fails, both are rolled back together. Duplicate creation is prevented via operation receipts and request records; the same assistant, task, and normalized requirement (excluding reason text) reuse pending requests and their MessageID, without issuing duplicate cards. The card type is `permission_request`, with TargetID pointing to the real request; displayed content and current processing status are read by the authorization API. Clicking the card directly opens a pre-filled form. After request completion, execution saves `PermissionPending`, unexecuted tools in the same batch return `not_started`, and the current execution ends with `waiting / permission_pending`, without calling the model again. Restart recovery retains this boundary.

The owner API submits `approve` or `reject` with version and idempotency keys. Users can modify resources, models, operations, directory scopes, and durations; assistant suggestions follow least privilege, and only the owner's final confirmed value determines authorization; assistant suggestions are not treated as the owner's permission ceiling. Actual authorization continues to check resources, models, and deployment boundaries via the original Grants service and creates them; request status, authorization, and recovery events are committed within the same transaction. Rejection does not create authorization. Duplicate approvals do not generate a second authorization or a second recovery event.

`permissions` automatic context reads effective authorizations before each model call; additions, modifications, revocations, or expirations cause version changes and replace old snapshots; it does not contain host paths or credentials, nor does it initiate remote sandbox probes. Maximum 200 items and 128 KiB; if exceeded, explicitly marked as Truncated, retaining a full authorization summary to detect changes.

`permission_requests` automatic context source provides all pending approvals and recent decisions (maximum 40 items); this is only approval evidence, not authorization credentials or instructions. Decisions are written to `resume_requested` events and retain the original task ID; both approval and rejection resume the loop, and the next model call carries the latest decision and effective authorization; the model must check the actual scope before continuing. Manual stop boundaries, paused, or terminal tasks prevent old requests from automatically waking up. Users can still send new messages while waiting; new messages are processed as independent events.

## File Tools

File tools operate by default on the Runtime's local unique persistent workspace for the current assistant: omit `resource_id`, use relative paths (e.g., `notes.txt`) or `/work/notes.txt`, and use `.` or `/work` to list the workspace root directory. This capability does not require additional storage or compute authorization, but regular members need corresponding sandbox and file tool group references. When compute isolation is unavailable, ready storage can still be used; `sandbox.enabled: false` disables local storage, compute, and network, causing access to the local workspace to fail, but does not affect separately connected and available remote sandboxes. When accessing external storage, `resource_id` must be explicitly passed, at which point `path` is interpreted as a path within that resource and authorization is checked. `/tmp` does not belong to the persistent workspace and can only be used in the current Shell execution. The workspace is bound by the server according to owner and assistant identity, and file tools and Shell share the same directory; tool parameters cannot select other assistants. File tools and Shell share storage authorization and deployment directory restrictions; current file tools execute on Linux, and other platforms refuse execution until equivalent path isolation implementations are available.

The workspace initializes the following missing directories during automatic context preparation or first file access, using restricted descriptors for operations and rejecting symbolic links; existing content is not overwritten:

| Path | Purpose |
| --- | --- |
| `/work/inbox/` | Raw attachments and imported materials |
| `/work/projects/` | Work files, scripts, and drafts organized by semantic matters; no new project business entities added |
| `/work/outputs/` | Delivery files; saving is not publishing, still sent via conversation_publish |
| `/work/.agents/skills/`, `memory/`, `reviews/` | Skills, detailed memory, and dreaming reviews; summaries remain in `/work/MEMORY.md` |
| `/work/.local/state/molr/` | Execution records such as large tool results and full Shell output saved according to XDG state semantics, persisted across commands and restarts; currently no automatic cleanup |
| `/work/.cache/` | Regenerable cache, persisted across commands; currently no automatic cleanup |

Business directories are default conventions; users can specify other locations; system directories retain their established purposes. Default directories can be used without Shell authorization. When writing or moving to new subdirectories, `create_parents=true` can be explicitly set; each missing parent directory must be within an authorized write scope, otherwise it should first be created via other authorized methods. Directory purposes and lifecycles are explained via workspace automatic sources; specific file lists, bodies, and runtime artifacts continue to be read on demand. See [Context Updates](../runtime/agent-context.md#sources-and-loading) for instruction loading scope.

| Tool | Parameters and Behavior | External Storage Permissions (Own workspace allowed by default) |
| --- | --- | --- |
| `file_list` | List a single directory, `offset` starts from 0, defaults to `limit=100`, maximum 200. Returns `Entries`, `Version`, `Truncated`, `NextOffset`. The next page must pass the previous page's `Version` as `expected_version`; uses filesystem order, does not recurse, does not follow symbolic links | read |
| `file_read` | Read UTF-8 text, `offset` is the line number starting from 1, defaults to `limit=200`, maximum 2000. Returns `Text`, `StartLine/EndLine`, `Version`, `Truncated`, `NextOffset` in original newline format; `TotalLines` is provided only when the end is reached | read |
| `file_write` | Create or completely replace a UTF-8 file. `overwrite` must be explicitly passed; `false` prohibits overwriting existing files, `true` allows overwriting. Can carry `expected_version` to prevent changes that occur after reading; requires parent directory to exist by default, `create_parents=true` can create missing parent directories with write permissions | write |
| `file_edit` | Use `old_text`, `new_text` for exact replacement, must pass the `expected_version` returned by read. Zero matches, expired version, or multiple matches all reject modification; only explicit `replace_all=true` replaces all matches, does not use regex or fuzzy matching | read + write on the same path |
| `file_move` | Atomically move or rename a single regular file; `to_path` uses the same workspace/storage resource as the source path, target must not exist, must pass the source file's current `expected_version`. Does not move directories or move across resources; `create_parents=true` can create target parent directories with write permissions | write on source path and target path |
| `file_delete` | Delete a single regular file according to `expected_version`; expired version, symbolic links, and directories are all rejected, does not provide recursive deletion | write on target path |

Read output is limited to 64 KiB, single scan is limited to 64 MiB; overly long lines, binary, and invalid UTF-8 return explicit errors. Files and text for write and local edit are limited to 1 MiB, larger batch or binary processing uses Shell. The offset limit for directory pagination is 100,000, oversized directories can be processed in batches using Shell.

File modifications first write to a temporary file in the same directory and sync, then re-check authorization and target version, finally atomically replace. Explicit rejection of overwrite, version conflict, and match failure do not modify the target file; if sync fails after successful write, the result is retained for verification, no blind retry. Read rejects symbolic links, hard links, and special files; listing directories can display the name and type of link entries, but does not read the target. File modifications on the same path within Runtime are executed serially; waiting for the lock can be cancelled, after acquiring the lock, cancellation status is checked again, at this point cancelled or timed-out requests return the lock token and do not continue executing protected file operations and media cache updates. Shell or other host processes do not participate in this lock, version checking is not a global file transaction against any external process.

See [Multimodal Files](../runtime/multimodal-files.md) for supplementary multimodal reading. The access model for files and Shell is different; do not infer current authorization from directory permission bits or capability snapshots.

## Long Tool Results

All tool text results sent to the model are uniformly limited to 16 KiB. Overly long results are fully saved to an independent assistant workspace `/work/.local/state/molr/tool-result-<sha256>.json`, returning a deterministic structural summary, limited head/tail preview, execution/pagination metadata, byte count, SHA-256, and full text path. Saving uses restricted path checks and atomic writes, prohibiting links and overwriting other files; operation receipts retain the original text, recovery after save failure reuses the receipt, does not re-execute side effects.

`file_read` adds `byte_offset` (0-based) and `max_bytes` (default and maximum 4096), returns `NextByteOffset`, can read JSON long lines segment by segment. Byte reading cannot be mixed with line ranges, metadata_only, or media options; the start point must be a UTF-8 character boundary. Normal text line reading still uses the original 64 KiB page limit; pages exceeding the unified inline limit are also returned as files. Single JSON tool results retain 64 MiB abnormal output protection, multimedia content continues to use independent capability/media budgets.

Shell streams stdout/stderr separately to `/work/.local/state/molr/tool-shell-<digest>-stdout.txt` and `-stderr.txt` before preview truncation, results return path, actual byte count, and `OutputComplete`. Preview maintains original deployment limits (default 64 KiB); full text capture is limited to `min(64 MiB, sandbox.max_file_bytes)` per execution total, exceeding quota or disk write failure cancels that process and explicitly marks save as incomplete, cannot treat partial files as full text. Files are retained with the assistant workspace, currently not automatically cleaned up by time; long-term high output usage needs to be managed according to disk budget. `Exit.OutputTruncated` only indicates that the preview was truncated, does not mean the saved full text is incomplete.

## Network Scope Query

Network permission scope is returned by `permission_list` in the `Network` field of two groups: authorized `Resources` and requestable `Requestable`: `Target` includes the actually deployed `Protocols`, `Addresses`, `Ports`, `ExcludeAddresses`, `ExcludePorts`, `Restrictions` explicitly states that the sandbox gateway works at Layer 4 (transport layer), only supports TCP/UDP, protocols outside this scope (such as ICMP) will not be forwarded; also explains system address and DNS virtual mapping limits, `LoopbackAccess` explains sandbox loopback and host aliases, authorization quotas and shared usage see `Grants[].Constraints`, `Usage`, requestable limits see `Requestable[].AuthorizationCeilings`. Names can be modified by users, scope cannot be inferred from names; fields are taken from the current rules of the corresponding local or remote sandbox. `Known=false` uses `Reason` to explain offline, disabled, or target removed, does not treat old snapshots as current authorization scope. Requestable items are not authorized items, actual execution still requires valid authorization; Runtime automatically selects the valid network authorization of the current assistant within the same sandbox.

## Explicit Remote Targets and File Transfer

Assistants do not configure a default sandbox. Omitting `sandbox_id` resolves fixedly to `local`; resource IDs do not participate in implicit node selection, the target and the node to which compute, directory, and network resources belong must be consistent. Remote regular file operations must provide directory resources; remote Shell defaults to `/tmp`, no persistent assistant workspace. Files, Shell, model media, tool receipts, and port forwarding retain explicit node sources. Remote context discovery and `/api/assistants/{id}/sandbox` interface have been removed.

`file_transfer` accepts `source`, `destination`, `overwrite`, optional `source_version`, `expected_version`. Endpoints use `sandbox_id`, `resource_id`, `path`, only allowing one end local, one end explicitly remote. Source must be readable, target must be writable; maximum 20 MiB, overwrite must carry target version. Download detects version changes during reading; write uses atomic replacement. Arbitrary Shell or host processes still do not participate in cross-node file transactions. Operation receipts and remote upload operation identities are used to determine results, do not automatically retry unknown writes.

Chat attachments and avatars use local files; remote files must be explicitly downloaded first. General long results are always written to local `/work`. Remote Shell logs are collected to local according to operation cursor, `SandboxID` describes the execution node, `OutputSandboxID` describes the node where the log is located; incomplete logs do not change the execution result of commands that have already occurred.

## General file_search

file_search follows FileTarget: defaults to local `/work`, `/global` is read-only, external directories require read authorization, remote explicitly requires sandbox_id, Full Access still requires explicit request and compute authorization per call. Search uses controlled file traversal and Go RE2, does not concatenate Shell commands, does not require normal Shell compute authorization.

Required path. pattern defaults to plain string, regex enables line-by-line regex; case_sensitive defaults to true. glob/exclude_glob are relative path patterns, supporting **, *, ?, character groups; does not interpret .gitignore. The TargetKind in results indicates whether the actual search target is file or directory. mode=content returns path, line number, snippet, and context_lines (0–5) context; mode=files returns only matching paths, filters by path when pattern is not passed. include_hidden defaults to false, but explicitly selected hidden directories will be traversed, for example `/work/.agents/memory`.

Each search first splits the path segments of the glob, reuses patterns during traversal; `**` matches step-by-step by path segment fallback, does not build a recursive state table for each candidate. Patterns are retained only within this search, include/exclude order, directory pruning, and per-path authorization checks remain unchanged.

Content scanning traverses line by line after the entire file passes version, size, and UTF-8 validation, directly references file bytes, retains only the current line and at most five lines of preceding text; reads subsequent text on demand when hit. Stops line traversal when result limit is reached, does not pre-build line index for the entire file.

Default 50 results, maximum 200 results; maximum scan 10,000 items, 32 directory levels, 2 MiB per file, cumulative 64 MiB, 5 second budget and 32 KiB result budget. Lines over 4096 bytes, non-UTF-8, binary, and links are counted in Skipped by reason; long lines and oversized files set Complete=false. Complete, Truncated, StopReason, and scan statistics clearly define result boundaries, do not provide pagination cursors that might miss items. Changes during directory or file scanning also report incomplete. Results are only for locating, use file_read to get current content and version before modification.

File search does not parse memory state, nor does it specially treat any directory as a "memory bank". Memory rules are explained by the system prompt, memory_* tools have all been removed. Remote search is provided with Sandbox Protocol 6, requires supporting node updates.

Dream directly reuses the aforementioned general file tools, limiting visible tools and memory path scopes solely through the execution context; regular assistants can also use `file_move` and `file_delete`, with local and remote storage using the same parameters and permission rules. Move, delete, and other side-effecting tools share operation receipts; replaying a successful operation will not move or delete files that appear later. Dream's undo and provenance records are maintained by observation callbacks, without separate tool schemas or executors. See [Dreaming and File Memory](../runtime/dream-memory.md) for details.

## Shell Execution and Port Forwarding

`shell_execute` uses `compute_id`; remote calls additionally require explicit `sandbox_id`. Regular commands wait synchronously for a maximum of 60 seconds; if not finished, they continue in the background under the original task. `background: true` returns immediately in the background, and `tty: true` creates a terminal; these two are mutually exclusive. `timeout_seconds` is an optional runtime limit; 0 or omitted means no limit is set. Authorization expiration, revocation, and resource limits still apply.

`forward_ports` accepts up to four unique HTTP service ports (1–65535); `forward_protocol` only accepts `http` (default), including WS upgrades. `Task.Forwards` exposes Protocol/Port/Address/URL/State. Targets remain fixed to execution IPv4 loopback. The public gateway requires the current Molr session and task ownership; raw TCP is disabled.

Ports listen on the Runtime. Remote tasks are forwarded via a TLS Upgrade channel authenticated with fixed certificates and service tokens, requiring the remote end to declare `PortForwarding=true`. Each entry supports a maximum of 32 connections, the Runtime supports a maximum of 128 connections in total, and the execution supports a maximum of 32 target connections. Connection probes are counted separately and do not consume the cumulative outbound network quota. HTTP/WS entries authenticate user sessions; HTTPS deployment requires a forwarding certificate. Ports are not cookie isolation boundaries.

Background tasks generate assistant events upon completion. Foreground synchronous completion and TTY exit do not generate duplicate completion events. If background tasks or TTYs exist, an aggregated reminder is sent every five minutes, with timing starting from when the first task enters the background or the terminal is opened. TTYs establish a foreground process group within the sandbox; text input appends a newline, and Ctrl-C targets the foreground task. Each terminal usage creates a new sandbox, reading `/work/.profile` on startup; non-interactive commands do not load this file.

GPU usage follows compute permissions, with no additional Shell parameters. `constraints.compute.gpu.device_ids` in requests must come from the list of requestable devices; temporary scopes use `temporary.limits.compute.gpu.device_ids` and retain the full compute quota. See [Resource Quotas](../security/resource-quotas.md) for detailed scope validation.

## Browser tools

`browser_session` accepts start/status/close. Start selects an authorized local `compute_id` and existing network grants, reusing the assistant's active task. `browser_action` accepts snapshot/screenshot/tabs/get_url/navigate/new_tab/click/fill/press/scroll/back/forward/reload/select_tab/close_tab. Actions use `task_id`; navigation accepts HTTP/HTTPS and about:blank. Launch paths, arbitrary JavaScript and CDP connections are not exposed.

A user takeover rejects model mutations and close with `browser_user_controlled`; readonly actions remain available. After handback, writes return `browser_snapshot_required` until a fresh model snapshot succeeds. A lost write response ends the execution rather than retrying a potentially completed action. Screenshots are read through scoped file/media handling. Tasks share the existing quota; each assistant has one browser with multiple tabs and a persistent private profile.

`browser_session` start/status returns a sanitized `Proxy` summary (Mode/Server/Bypass/Authentication/Version), `ProxyAppliesTo` (current_session/next_start), and `RestartRequired`. Running tasks use their launch snapshot; configuration changes do not replay startup or switch connections. `LastNetworkFailure` contains TaskID/At/Reason/Message/Proxy and optional Sandbox (Reason/At), which is only a sandbox event observed during the action, not proof of causality. Browser diagnostic messages retain network error identifiers only; unknown failures direct the assistant to status. Successful navigation clears the current task’s failure; successful read-only actions do not. Proxy endpoints use existing sandbox network grants. Models cannot configure proxies, environment variables or proxy passwords.
