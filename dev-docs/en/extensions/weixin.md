# WeChat Channel

The fixed Go adapter is located at `runtime/internal/im/weixin`. Protocol verification is based on `@tencent-weixin/openclaw-weixin@2.4.9` (2026-10-06); refer to [Tencent Protocol Description](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md). This is a fixed channel adapter; it does not load OpenClaw or persistent backend plugins. For user operations, see [WeChat Chat Entry](../../../docs/en/chat-channels/weixin.md); for request fields, see [HTTP API](../reference/http-api.md).

## Entry and Identity

Bindings belong to Molr users, assistants, and existing sessions, while fixing the WeChat bot and the scanning user. Scan results are confirmed only by authenticated requests with assistant write permissions. QR code requests are stored in-process and expire after five minutes; late confirmations after cancellation cannot take effect; restarts require re-initiating incomplete scans. Completed bindings are persisted and do not depend on browser session survival.

A WeChat user or bot cannot be bound repeatedly across assistants or accounts. Each inbound message rejects group messages, bot echoes, and non-bound senders. Account enablement and assistant status are re-checked on every send and receive; unbinding deletes the binding, cancels the queue, and invalidates the old binding generation. Firing pauses the channel, rehiring resumes it; cloning defaults to WebUI.

`conversation.ReceiveChannel` is the message inbound entry exclusively for trusted assembly and does not belong to HTTP `Client`. It verifies the current binding via `AuthorizeChannel` within a transaction, without forging user Sessions or creating full-permission Tokens. Standard `SendUser` passes through `CheckWebInput` within the same transaction; when a binding exists, chat writes from WebUI, SDK, and plugins are rejected. Reading, management, and approval maintain existing permissions.

## Persistence and Delivery

Status queries filter by current account and binding, retrieving the most recent 30 deliveries while preserving nanosecond-precision creation times; for identical timestamps, records are selected in reverse order by record key, then returned in ascending order by session sequence number and segment number. Queries use corresponding composite indexes; historical growth does not require sorting all deliveries first.

The private keyspace consists of `weixin.bindings`, `weixin.incoming`, and `weixin.deliveries`. Binding credentials are encrypted using AES-GCM with binding identity AAD; they do not appear in status DTOs, SSE, model context, or logs. Network access is restricted to WeChat HTTPS APIs with domain validation; actual DNS addresses must be public, and HTTP redirects forwarding tokens are prohibited.

Message deduplication records, chat writes, reply credentials, and cursors for an inbound batch are committed in a single transaction. Message IDs preserve uint64 values losslessly; duplicate messages from the same bot and user do not re-trigger the assistant. Polling is only responsible for storage and does not wait for assistant execution.

When the assistant explicitly Publishes, the `Published` callback creates independent delivery records within the same message transaction, without competing for the IM Outbox consumed by the scheduler. By default, newly published messages are delivered only to the current binding; history prior to binding is not resent. Content splitting follows UTF-8 boundaries, with each segment limited to 3500 bytes; each attachment creates a separate delivery record, and successful text does not mask attachment failures. Images are sent as image messages after upload; other attachments are sent as file messages. Cards are converted into titles, summaries, and Molr links requiring login.

Deliveries persist `sending` before requesting the platform. A valid JSON object with HTTP 200 is recorded as `accepted` when `ret` / `errcode` both have no non-zero errors; consistent with the Tencent 2.4.9 client, successful responses may omit `ret`, which must not be marked as unknown. Empty responses, `null`, and invalid JSON remain unknown. Missing context or `ret=-2` results in `waiting`; new inbound context can re-trigger; HTTP 429 is attempted up to five times, with at least one minute between attempts. Timeouts, standard 5xx errors, and lack of a complete successful response result in `unknown`, with no automatic resend; upon process restart, lingering `sending` becomes `unknown`. `ret=-14` pauses send/receive and requires re-scanning. `client_id` is fixed at delivery creation but does not assume strict idempotency guarantees from the server.

When unbinding or replacing a binding, the cancellation query filters by account, binding generation, and `pending / waiting / sending` status, loading only deliveries that can still be cancelled; historical records with completed, failed, or unknown results remain unchanged. Cancelling deliveries, resolving corresponding reminders, and cleaning up reference mappings are completed within the same transaction.

Sending, scan-binding changes, and unbinding are serialized by account and assistant; while waiting for locks, request cancellation and timeouts are responded to, without modifying binding or delivery status, nor releasing locks held by the current operation. Scan polling clears the in-progress flag after cancelling the wait, allowing subsequent retries. Requests initiated before the unbind returns may have already been accepted by the platform. Account revocation cannot withdraw external requests that have entered the network. The Runtime lifecycle cancels and waits for channel workers before closing the database.

## Evidence Boundaries

Protocol documentation comes from client implementations and does not represent the complete server-side contract. `context_token` has no fixed validity period commitment; successful responses are not read receipts. Real account scanning, verification codes, client display, and behavior after long periods of inactivity still require account acceptance testing; simulated protocol tests cannot replace these verifications. Native history synchronization, group chats, and multi-entry sending are out of scope for this version. Media protocols and error paths have been verified via controlled transmission; real WeChat client image/file display still requires account acceptance testing.

## Error Display and Refresh

Polling scheduling retains both `connected` and `reconnecting` bindings. Retryable errors use the shared `retry.Policy`; after consecutive failures, it waits sequentially for 5, 10, 20, 40, 80, 160, 320, and 640 seconds, then maintains 640 seconds, with no limit on attempts and no random jitter; waiting starts counting after the current failure handling ends, and resets to 5 seconds after a successful poll and inbound batch commit. Network, credential reading, and inbound processing failures share this backoff counter; unbinding or permission revocation can cancel the wait. After Runtime restart, reconnecting bindings are also restored, but the backoff counter starts from scratch; polling stops when re-scanning is required. Backoff calculation is centralized in `runtime/internal/retry`; model retries reuse the same calculation, retaining their own interval configuration, jitter, attempt count, and total wait limits.

When the connection enters `reconnecting` or `login_required`, a unified connection notification is generated, explaining automatic reconnection and re-scanning respectively. Repeated failures in the same connection state do not duplicate reminders; closing reminders does not stop retries; notifications are automatically resolved after successful polling or unbinding. If the error cause changes but remains in automatic reconnection, the same notification is retained; when re-scanning is required, it is updated to a new reminder.

The chat page displays a single prompt only when delivery is abnormal, including failures, unknowns, waiting for new context, and rate-limit retries; success and normal queuing are not displayed. Delivery writes synchronize the `notification` module within the same transaction, distinguishing anomalies by delivery ID and status/error code. The frontend reads unified notification records; closing saves the ignore state via the notification interface, no longer determined by component memory. Old prompts are not prematurely resolved during sending; they are resolved after success or cancellation; waiting, failure, unknown, and rate-limit results generate reminders. No delivery details are set. Historical unknown records are not guessed to be successful, nor automatically resent.

Shared error prompts in the WebUI are deduplicated by error code, prioritizing display in the current popup; after closing, background queries do not repeatedly reappear, and new explicit operations can re-prompt. Prompts use compact semantic color styles and do not expand request numbers by default. The SDK parses HTTP `Retry-After`; the same login identity suspends standard GET requests within the window; the retry button displays the wait time. Query retries only refresh the current query; WeChat delivery events only refresh WeChat status; QR code polling does not invalidate page data.

## Images, Attachments, and Model Context

Media protocols refer to [Tencent Upload/Send Implementation](https://github.com/Tencent/openclaw-weixin/blob/main/src/messaging/send-media.ts) and [Download Implementation](https://github.com/Tencent/openclaw-weixin/blob/main/src/media/media-download.ts). Inbound processing first validates the sender, binding, and deduplication record, downloads/decrypts files outside the SQL transaction, saves them to the existing file system using `files.ChannelStore.UploadChannel`, then re-checks binding and file ownership within the message transaction and associates `AttachmentIDs`. File writing reuses size, quota, idempotency, and object commit mechanisms; writing or associating files cannot continue after binding invalidation. When some attachments fail to receive, text and successful attachments are retained, and unread failed content is explicitly marked.

The channel attachment limit is the smaller of Runtime `MaxUploadBytes` and 100 MiB; if not configured, 20 MiB is used. Images and standard files are supported bidirectionally; inbound videos are saved as attachments, and outbound videos are sent as standard files. The media CDN only allows HTTPS `*.cdn.weixin.qq.com`, reusing public DNS/IP validation and prohibiting redirects, without carrying bot Authorization. AES-128-ECB/PKCS#7 is used according to Tencent format, supporting image hex keys and media raw/hex-base64 keys. Downloads and response reads have byte and time limits.

CDN uploads attempt up to three times for network failures, HTTP 408/429/5xx, and missing download parameter headers, reusing the same upload address, file key, and ciphertext, with intervals of 250/500 ms; other 4xx errors, illegal addresses, or cancellations stop immediately. Upload/local read failures occur before sending the message and are explicitly recorded as `attachment_failed`; timeouts or abnormal responses in the final `sendmessage` remain `unknown`. Outbound processing only reads file IDs that have passed normal Publish authorization and are fixed to the outbox; external file selectors are not accepted.

Each model request automatically provides context via real-time `chat_channel`, indicating the current WeChat entry, image/file/voice reception capabilities, reference context boundaries, avoidance of interactive cards, and text degradation methods for necessary cards. After unbinding, the context source is removed and not written to permanent assistant instructions. The QR code connection page displays a data privacy notice about Tencent potentially retaining messages and attachments before authorization.

## References and Voice

Inbound processing parses embedded text/attachments in `ref_msg`, `svr_id`, and `partial_text`. Inbound IDs and server-side `message_id` in successful send responses are parsed losslessly; reference mappings are persisted isolated by account and binding generation; items in the same inbound batch can also reference the previous one. Each binding has a maximum of 4096 mappings, valid for 30 days, with each text limited to 16 KiB; attachments reuse file storage, and CDN keys are not saved in the cache. Unbinding or replacing bindings cleans up mappings. Partial references are located by start/end occurrence counts and validated when `quotemd5` is provided; if mismatched, they are marked as unverified and the available original text is retained, without guessing the selection. Cache missing/expired or file deleted scenarios are explicitly prompted. Referenced attachments are associated via the restricted file entry of the current binding; external file IDs cannot access other sessions.

WeChat voice messages without transcription are first downloaded and decrypted, then decoded into 24 kHz mono WAV by the embedded SILK WebAssembly in `internal/voicecodec`. The object has no host function imports; memory is limited to 32 MiB, execution to 5 seconds, compressed input to 4 MiB, and decoded output to two minutes; Runtime maintains a pure Go static build. On failure, the original SILK attachment is retained, and the model is prompted not to guess unread content. Existing WeChat transcriptions prioritize text and do not re-download. Subsequent processing continues to use existing attachment reading and audio model capabilities, pricing checks, and does not automatically call external transcription services. Source, build method, and license are described in [Voice Decoder](../../../runtime/internal/voicecodec/README.md).

## Existing Binding Identification

When the current target assistant is in a connected state, the login interface directly returns `already_connected` and does not create a QR code. In other cases, obtaining a QR code only carries the existing tokens for that account and that target assistant, without exposing bindings of other accounts or assistants. Upon receiving `binded_redirect`, the binding generation from the initiation of the scan and the identity fields provided by the server must be matched, and existing credentials must be validated via `getconfig` without consuming the message; after confirmation, the binding ID, cursor, reply context, and pending send queue are maintained. A missing matching binding remains a conflict, and invalid credentials do not report success. Late-arriving results after cancellation, unbinding, or permission revocation cannot restore the connection.
