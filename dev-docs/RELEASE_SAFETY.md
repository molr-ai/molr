# 开源发布与私有文件隔离

本规范适用于源码归档、Linux 发行包和三个前端应用。许可证范围及完整第三方声明的维护见 [许可证与分发](LICENSING.md)。公开内容和内部材料的维护规则见[开发规范](DEVELOPMENT.md#公开内容与内部资料)。

## 本地文件与 Git

运行数据库、密码、主密钥、登录链接、实际部署配置、日志、缓存和备份应放在 Git 忽略的私有目录，例如任务 worktree 的 `.cache/` 或仓库以外的独立运行目录。

`.gitignore` 覆盖常见数据库及 WAL/SHM、私钥/证书容器、初始密码、保存的登录链接、环境文件、备份和本地配置。`runtime/configs/` 只保留 `*.example.json`；`.env.example` 和 `.env.*.example` 可提交，但内容仍必须使用示例值。不要为了通过检查而把真实凭据改名成示例文件。

忽略规则不会从 Git 历史或暂存区移除已经提交/暂存的文件。运行：

```bash
npm run check:release
npm run test:release
```

`check:release` 分别检查暂存区原始 Git 对象，以及已跟踪和未被忽略的工作目录文件。它能发现强制 `git add -f` 的常见私密文件，也不会被“暂存区仍有密钥、工作文件已经改干净”的状态绕过。忽略的本地运行目录不打开、不复制、不自动删除；需要调查历史泄漏时单独检查历史，而不是修改忽略规则后宣布已经清理。

检查错误只输出路径和问题类别，不输出匹配的凭据正文。

## 内部文档

仓库根目录 `internal-docs/` 保存不公开的需求、研究和本地验收记录，整体由 Git 忽略。发布检查同时拒绝暂存区、指定源码提交及前端输出中的该目录，不能通过强制加入绕过。公开构建必须在没有此目录的全新检出或源码快照中完成。

官网文档只从 `apps/website/src/docs-routes.ts` 中登记的公开 Markdown 读取，未登记文件不会自动进入客户端包。新增路由意味着公开全文，加入前必须审查内容；禁止指向内部目录或通过符号链接读取它。

已提交材料移入忽略目录只改变当前文件树，不删除旧历史。公开旧仓库前仍须审核其可达历史；清理 worktree 前按开发规范保留本地内部材料。

## 公开静态资源

Vite 的 `public` 目录会整目录复制，Git 忽略规则不控制这一步。可公开的原始静态资源明确列在 `scripts/release-policy.json` 的 `publicFiles` 中；新增文件必须先确认其内容适合公开，再更新清单。当前清单包含共享品牌资源和两个首屏初始化脚本。

三个应用通过 `scripts/release-assets.ts` 在加载配置时检查公开目录：未列入清单的文件、符号链接、数据库内容及明显密钥格式会使构建失败。前端输出写入后再次扫描，预览服务启动前也检查现有产物。构建失败后的目录不能用于发布；不要把 `public` 用作下载、日志或临时截图目录。

官网通过 `MOLR_RELEASE_DIR` 分发安装包时，还会校验被选中的归档、校验文件和下载清单：文件名符合规则不代表内容就允许公开。输入目录中未被选择的其他文件不读取、不复制；最终网页下载目录若混入额外文件则拒绝验收。

## 源码归档

先审查并提交要公开的版本，然后运行：

```bash
npm run build:source -- --ref HEAD
# 或选择已审查的明确提交：
# npm run build:source -- --ref <commit>
```

输出位于 `dist/sources/`，包括 `molr_source_<commit>.tar.gz` 和 SHA-256 文件。命令检查所选提交的全部文件和内容，再通过 `git archive` 导出；随后验证每个归档文件与对应 Git blob 一致。符号链接、submodule、常见私密路径和明显凭据会阻止导出。改变内容的 `export-subst` 或隐去已跟踪文件的 `export-ignore` 不会被静默接受。

**源码包只包含所选提交。** 暂存区、工作目录修改、未提交新文件以及忽略的运行数据均不加入；它也不包含 `.git` 数据库。不要把整个工作目录压缩后当作源码包。发行构建 `build:release` 需要 Git 检出，以记录确切的构建提交；从不含 `.git` 的源码包可按部署指南分别构建 Go Runtime 与前端。

此命令不改变远端仓库可见性、不清理历史、不推送代码；将已有 Git 仓库设为公开仍会公开其可达历史，需要另行审核。

## Linux 发行包

`npm run build:release` 在构建前运行源码检查与许可证检查，然后生成 WebUI，并以 `CGO_ENABLED=0` 和 `-trimpath` 构建 Runtime。`-trimpath` 防止编译器把本机工作目录和模块缓存绝对路径写入产物；它不会清理源代码中自行写入的文本。

打包时只传入 `scripts/release-policy.json` 中的六个文件：

- `LICENSE`
- `THIRD_PARTY_NOTICES.md`
- `bin/molr-server`
- `release.json`
- `scripts/install-linux.py`
- `scripts/install-linux.sh`

不递归打包工作目录或 staging 目录。生成的临时归档必须通过成员类型、明确清单、重复路径、内容和元数据检查，才原子替换最终归档并生成校验与下载清单。BusyBox、运行配置、数据库、密钥和验收数据均不属于发行包。

可独立检查现有产物：

```bash
python3 scripts/release_safety.py release dist/releases/molr_0.1.0-local_linux_amd64.tar.gz
python3 scripts/release_safety.py release-directory dist/releases
python3 scripts/release_safety.py frontend apps/webui/dist
```

检查归档时不解压执行任何文件。归档中的符号链接、硬链接、越界路径、额外文件、缺少必需文件、异常发布元数据或不匹配校验会被拒绝。

## 个人信息与历史

公开文档使用仓库相对路径、通用账户说明和明确标注的地址占位符。实际工作目录、验收地址、账号与日志只保存在忽略的本地验收目录；历史验收记录保留测试结果，不保留机器连接信息。网络分类中的私有地址段、人工测试数据、产品域名以及第三方原始版权和联系方式不属于需要批量替换的个人资料。

新增提交或 `.mailmap` 不会删除旧提交对象中的身份或文件内容。源码归档不含历史；直接公开原仓库则会公开相应的可达历史。需要移除旧信息时，先确定发布方式和范围，再在独立副本处理；不得直接改写共享仓库、强制推送或自动删除旧分支。

## 验证与范围

修改发布流程时运行 `npm run test:release`、`npm run check:release` 和相应应用构建；验证被拒绝的文件确实没有进入产物，源码包与所选提交一致。具体结果、提交和产物摘要保存在本地验收记录中。

检查使用 Python 3 标准库，无新增 Python 第三方依赖。测试使用人工哨兵、临时 Git 仓库和临时归档，不加载真实用户凭据。已验证的案例包括强制加入被忽略文件、暂存区/工作目录差异、静态目录混入文件、伪装扩展名的 SQLite、归档链接和路径越界、下载清单与校验异常。

密钥检测只覆盖高置信格式，例如 PEM 私钥、部分供应商令牌及完整的 Molr 一次性登录链接；不能识别所有口令、编码/加密内容或个人资料。允许的图片和文档仍需人工审查，不能把检查通过解释为“绝无敏感内容”。历史提交、账号个人信息和内部文档的公开取舍不由此脚本自动处理。
