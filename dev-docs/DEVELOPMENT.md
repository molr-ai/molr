# 开发协作与验收

本文是本项目贡献者与编码代理共同遵守的开发规范，涵盖任务隔离、验收、构建、合并生效及服务管理。[AGENTS.md](../AGENTS.md) 作为必读索引引用本文；这里的要求具有相同约束力。应用使用与正式部署说明另见 [产品部署指南](../docs/deployment/README.md)。

## 公开内容与内部资料

本仓库按可公开分发维护。提交前审查实际内容及暂存区，代码、注释、测试夹具、图片、附件、文档和生成文件都适用：

- 不提交真实凭据、密码、私钥、令牌、一次性登录链接、数据库、日志、备份、客户／个人资料或实际部署配置。示例必须使用人工数据、相对路径和明确的地址占位符；不能只改扩展名或文件名来绕过检查。
- 不提交来源不明、无权分发或尚未审查许可的代码、字体和素材。第三方原始版权、许可证及必要 NOTICE 不作个人信息清理，按 [许可证与分发](LICENSING.md) 保留。
- `docs/` 面向用户，`dev-docs/` 面向公开贡献者，均描述当前实现、限制及可重复验证方式。内部产品目标、商业／竞品判断、未定路线图、讨论原文和包含本地环境信息的验收记录放入仓库根目录 `internal-docs/`。需要记录时创建该目录；它整体被 Git 忽略，不是公开文档的依赖。
- 从内部材料提炼公开说明时，重新核实实现并移除个人资料、部署细节和内部决策过程。公开文档不得链接或依赖内部文件；官网只加载已审查的路由文档，不能通过目录 glob、raw import、软链接或复制到 `public/` 绕过范围。
- 提交前检查 `git status --short`、`git diff --cached --stat`、`git diff --cached`，运行 `npm run check:release` 和 `npm run check:licenses`；文档路由或发布流程变化还需运行对应构建与测试。禁止用 `git add -f` 加入内部目录，不为通过检查删除拦截规则。
- 忽略规则不删除已跟踪文件和历史对象。移动已提交的内部材料后，要检查暂存区中的原文件已删除；历史公开范围单独审查。发现已泄漏凭据时先撤销或轮换，再处理历史，不把移入忽略目录当作泄漏已经解决。
- 清理 worktree 前必须保留 `internal-docs/` 等有价值的未跟踪资料：合并时迁入主工作区同名忽略目录或维护者指定的私有存储，校验摘要，遇到同名不同内容保留双方。Git 不会合并这些文件，不能随 worktree 清理而丢失。

发布检查用于防止常见误提交，不代替内容和来源审查。临时验收地址通过交付消息提供，账号、链接和详细记录只放本地忽略目录。Git 提交身份由维护者决定；不得擅自重写历史或修改全局身份配置。

## Worktree 开发规范

- 主工作目录（仓库的主 worktree，可通过 `git worktree list` 确认）固定保留 `main`，用于查看代码、集成已完成的分支和运行主分支服务。**禁止直接在主工作目录修改代码，也禁止在该目录切换到功能分支进行开发。** 功能开发、修复、重构及其测试、配置和文档修改均在独立 worktree 中完成。
- 开始任务前先检查 `git status --short --branch` 和 `git worktree list`，确认当前目录、分支与已有任务。不得覆盖、重置或清理他人的未提交变更。
- 每个独立任务使用一个分支和一个 worktree，从最新的本地 `main` 创建；如已有该任务的 worktree，则继续使用。分支名使用 `feat/<task>`、`fix/<task>` 或 `chore/<task>` 等有明确含义的名称。
- worktree 推荐放在主工作目录下的 `.cache/worktrees/<task>`，该目录由现有 `.cache/` 忽略规则排除，不纳入 Git 提交。例如，在主工作目录执行 `git worktree add -b feat/<task> .cache/worktrees/<task> main`。路径统一以主工作目录为基准，不在任务 worktree 内嵌套创建。不能创建 worktree 时先解决路径或权限问题，不得退回主工作目录直接开发。
- 创建后，所有编辑、依赖安装、代码生成、构建、测试及提交都以对应 worktree 为工作目录。并行任务不得共用同一个 worktree，也不得修改其他任务的 worktree。
- 各 worktree 的依赖、构建产物、缓存和 Runtime 测试数据独立管理；不得复用或修改主工作目录的运行数据库、凭证及私有数据目录。开发和验收期间不得停止或替换其他任务或主分支的服务；合并完成后按下文规范更新主分支服务。
- **任务完成后必须先提供验收入口并等待用户验收，不得直接合并。** 只有用户验收后明确授权合并，才能将任务分支合并回 `main`；开发完成、测试通过或提供验收链接均不代表获得合并授权。等待验收期间保留任务 worktree 和验收服务。
- 合并前同步最新 `main`，在任务 worktree 内完成冲突处理和相关验证。多个分支按顺序集成；前一个分支合并后，后续分支重新检查与最新 `main` 的兼容性。合并冲突也必须在任务或专用集成 worktree 中解决，不得在主工作目录手工修改代码。
- 提交、合并和推送按用户已授权的范围执行；完成开发不代表自动获得推送授权。合并回 `main` 时确保主工作目录干净，优先使用已验证分支的快进合并（`git merge --ff-only <branch>`），合并后确认状态与必要的集成检查。
- 交付时说明任务分支、worktree 路径、验证结果及是否已合并，并按下文要求提供验收入口；需要登录时提供可直接登录的一次性链接。
- **合并成功且主分支服务生效验证通过后，必须清理本任务的 worktree，无需等待用户再次要求。** 清理前确认变更已提交并合并，精确停止该 worktree 的验收服务，妥善保留需要留存的验收数据，再使用 `git worktree remove` 移除目录；不得强制删除含未提交变更的目录，也不得影响其他任务的 worktree 或服务。合并交付时说明清理结果。

## Worktree 独立验收服务

- 涉及运行行为或界面改动的 worktree 必须启动隔离的验收服务，不等待用户另行要求；仅启动任务涉及的应用，每个前端应用只运行一个开发服务。纯文档修改无需额外启动服务。WebUI 接入真实后端时必须连接该 worktree 自己的 Runtime，不能代理到主分支或其他任务的 Runtime。
- 启动前检查已有进程及实际监听端口，为每个实例分配空闲且不冲突的端口。WebUI、官网或 UI Design 沿用 `0.0.0.0` 的局域网监听约定；Runtime 沿用已约定的安全监听和 TLS 配置，不为绕过启动限制而放宽安全设置。
- 验收实例使用独立的配置、数据库、密钥、登录账号、助理工作区、缓存与日志。可将本地运行文件放在该 worktree 的 `.cache/acceptance/` 下；不得从主环境复制真实凭证或复用其数据目录。凭证及验收数据不纳入 Git 提交。
- 保存该实例的启动方式、端口和数据目录，便于继续验收与重启。改动后检查验收服务是否已加载当前代码；需要时只重建、重启本 worktree 的对应服务，并保留已有验收数据。
- 交付前验证页面可访问、前端代理指向正确的独立 Runtime，以及相关功能或能力状态正常。向用户提供局域网验收地址和验证结果；**需要登录的验收页面必须提供点击后可直接登录的一次性登录链接，不得仅提供普通登录页或要求用户手动输入用户名、密码。** 无需登录的页面提供可直接访问的链接。临时测试服务不能替代供用户访问的验收服务。
- 一次性登录链接必须指向对应 worktree 的 WebUI 和独立 Runtime，使用该验收实例的账号生成。验收链接有效期默认设置为 **3 小时**（`expires_in: 10800`），用户另有要求时按其要求设置；生成时显式指定有效期，不沿用工具可能较短的默认值。验证登录流程时使用单独的测试链接，交付前重新生成尚未使用的链接，并注明具体到期时间及其时区，不能提前消费交付给用户的链接；链接过期或已使用时重新生成，无需用户手动登录。链接和令牌不纳入 Git 提交。
- 验收服务在等待验收和合并期间随 worktree 保留；合并完成并验证主分支服务生效后，随本任务 worktree 一并清理。清理时先精确停止该 worktree 的服务进程，并妥善处理需要保留的数据，不使用会影响其他实例的批量终止命令。

### 真实模型测试

- **需要使用真实模型进行测试或验收时，优先使用主环境中已经配置好的本地模型。** 先只读检查现有模型连接、模型名及能力配置，确认服务可用且满足本次测试所需的工具调用、多模态和上下文容量等要求；不默认另起推理服务或改用云端模型。
- 在任务 worktree 的独立 Runtime 中配置同一本地推理端点和模型，使用本任务的测试账号、助理及人工构造资料。共享的是模型推理服务，Runtime 配置、数据库、登录会话和工作区仍须隔离；凭证处理沿用上文约定，不修改主环境模型配置，不停止或替换其服务。
- 已配置的本地模型不可用或能力不满足测试要求时，再选择其他合适模型，并在验收记录中说明原因。记录测试日期、实际模型、配置和结果，部署地址、凭据及完整请求／响应保存在本地忽略目录，不写入公开文档或测试夹具。
- 确定性的协议与回归测试仍可使用模型模拟服务；需要验证真实模型行为或归纳质量时，应实际调用上述优先模型，并明确区分真实模型测试与模拟测试的结果。

## Runtime 构建与沙盒验收

- **主服务和各 worktree 验收实例的 Runtime 均必须使用静态构建，显式设置 `CGO_ENABLED=0`。** 使用 `runtime/.go-version` 指定的 Go 版本，在对应任务 worktree 内构建；更新主服务时必须使用与目标 `main` 提交一致的干净构建 worktree。例如在其 `runtime/` 目录执行 `CGO_ENABLED=0 go build -o ../.cache/acceptance/molr-server ./cmd/molr-server`（先创建输出目录）。Runtime 默认复用自身二进制作为沙盒 helper，动态链接产物即使能启动 HTTP 服务，也不能用于当前的精简沙盒环境。
- 部署前检查最终产物，不能仅凭构建命令或参数判断：用 `file <binary>` 确认静态链接，用 `go version -m <binary>` 核对 `CGO_ENABLED=0` 和构建提交，主服务产物还必须满足 `vcs.modified=false`；验收产物记录任务当前的修改状态，不得将含未提交修改的验收产物部署到主服务。必要时用 `readelf -h -l <binary>` 确认架构匹配、ELF 类型为 `EXEC` 且没有 `INTERP` 段。检查不通过时不得替换正在运行的服务。
- **构建后和部署后均检查二进制权限，Runtime/helper 使用 `0755`，不得为 `0775`、`0777` 等组可写或其他用户可写的模式。** Bubblewrap（默认 `/usr/bin/bwrap`）和 helper 必须是可执行的普通文件，路径及其父目录不得经过符号链接；不要通过放宽权限绕过检查。另行确认静态 BusyBox 可用，其来源和解析后的文件权限应符合 Runtime 的检查要求。
- 启用沙盒的 Linux 实例必须具有有效的 cgroup v2 委派。沿用已验证的 systemd 用户服务启动方式，设置 `Type=exec`、`Delegate=yes`、`DelegateSubgroup=supervisor`、`KillMode=control-group`；服务名使用以 `molr` 开头的独立名称，每个 worktree 使用不同的 unit。不要随意改回普通登录会话中的后台启动方式，也不能将 systemd unit 启动成功视为沙盒已就绪。
- 更新主 Runtime 前再次核对构建提交与当前 `main`，保存旧二进制和配置；替换使用临时文件校验后原子重命名，不能直接覆盖正在执行的二进制文件。保留原数据库、密钥和账号；需要复制数据目录时先正常停止对应实例，完成后按原安全配置重启。记录实际 PID、构建提交、二进制摘要、启动方式和回退位置。
- **每次启动、重建或重启后，除页面和 HTTP 连通性外，还必须通过已认证请求检查 `GET /api/sandbox`；配有 WebUI 的实例还须通过其代理完成验证。** 沙盒未被用户明确关闭时，要求 `Enabled=true`、`Capabilities.Reason=available`，且 `Shell`、`ProcessIsolation`、`FileIsolation`、`NetworkIsolation`、`ResourceLimits` 均为 `true`，确认 Runtime 的真实隔离启动探针通过。此项适用于独立验收和合并后的主服务；不能只凭启动日志、监听端口或 `/api/status` 正常就宣布验收成功。
- 沙盒异常时依据实际原因码定位：`sandbox_package_incomplete` 优先检查 helper 的静态链接和静态 BusyBox；`sandbox_helper_unavailable` 检查 Bubblewrap/helper 的存在性、可执行权限、组或其他用户写权限及符号链接；cgroup 或其他启动错误检查对应 unit、委派状态和日志。不得通过关闭沙盒、放宽隔离或回退宿主执行掩盖问题；修复后重新验证能力状态，未恢复时明确报告不可用项。

### 启动就绪与认证验证顺序

适用于独立验收和合并后的主服务更新。验证脚本必须将启动等待、会话恢复、能力检查与回退判定分开，避免验证流程本身引发反复重启或登录限流。

- **先等待 HTTP 就绪，再执行认证验证。** `systemctl restart` 返回或 unit 处于 `active` 只表示进程已启动。用无需登录的只读请求（例如 `GET /`）等待 HTTP 响应，明确总截止时间与轮询间隔；截止前的短暂连接拒绝按启动中处理，不立即触发回退。就绪探测不能调用登录、一次性链接预览／兑换等认证入口；HTTP 就绪后仍须完成上文要求的已认证沙盒能力检查。
- **复用验证会话，不在每轮检查前重新登录。** 同一验证入口复用 Cookie jar／浏览器上下文及其 CSRF proof，覆盖更新前基线、更新后验证和必要的复查；重启后先用 `GET /api/auth/me` 确认会话仍有效，仅在确认失效后重新认证。直连与 WebUI 代理分别维护符合各自 Cookie 名称和来源规则的会话，不能把两个入口误算成一次登录，也不能混用其他实例的凭证。脚本创建的验证会话在整轮工作结束后统一注销；确需跨脚本保存时，只存于本任务私有忽略目录并使用 `0600` 权限，不输出凭证或纳入提交。
- 验证前核对实际限流实现和部署配置，预留测试登录及交付链接验证所需次数。当前 [认证实现](../runtime/internal/auth/service.go) 的账号窗口为 1 分钟、来源地址窗口为 10 分钟，两者使用同一配置阈值，默认均为 5 次；**成功登录也计数，不能按 `login_attempts_per_minute` 的名称推断所有窗口都是一分钟。** 限流记录持久化，重启服务不会重置窗口；直连与代理也可能被 Runtime 识别为同一来源地址。
- **HTTP 429 表示验证被限流，不能单独作为新版本故障或回退依据。** 停止重复认证，有 `Retry-After` 时遵守该值，并核对是否另有认证层窗口；没有该响应头时，依据实际生效的限流层与窗口确定恢复时间，不猜测等待一分钟。已有有效会话可继续完成其权限范围内的检查；不能通过清空计数、提高阈值、切换来源地址或反复重启绕过限流。
- 回退前核对进程状态、启动日志、就绪截止时间和具体失败阶段。启动尚未完成、验证凭证失效或验证请求被限流，均不能直接认定部署产物有故障；确认新进程启动失败、超过合理就绪期限或实际能力检查失败后，再按故障原因决定修复或回退。无法完成认证检查时明确报告“验证未完成”，不能仅凭页面可访问宣布部署成功。
- 交付用的一次性登录链接复用本轮已认证会话签发，必要的敏感操作验证沿用现有流程；继续遵守三小时有效期和测试／交付链接分离要求，不为签发、预览或验证链接重复执行账号登录。

## 合并后的服务生效

- **合并回主工作区后，必须检查正在运行的主分支服务是否已加载合并后的版本；必要的重建、重启与验证属于合并工作的组成部分，无需等待用户再次提醒。**
- 编译型服务（例如 Go Runtime）存在相关改动时，使用与当前 `main` 相同提交的干净 worktree 构建，再更新主服务二进制并正常重启；Runtime 必须遵守上文“Runtime 构建与沙盒验收”的静态构建、权限、启动和能力验证要求。更新前再次核对 `main` 的提交，防止并行合并期间用旧构建覆盖新版本；保留原配置、数据库、凭证及可用于回退的二进制。
- 主工作区前端沿用下文约定的三个开发服务。若已通过热更新加载新代码，可保持运行；依赖、启动配置变化或热更新未生效时，重启对应服务。合并不额外启动构建预览、文档站或其他重复前端实例。
- 只操作已确认属于主工作区的相关进程，保留其他 worktree 的验收服务。重启后核对监听地址、端口、前后端连接及改动涉及的功能，不能仅凭进程启动日志判断成功。
- 合并交付时说明代码是否已生效、实际重启了哪些服务以及主环境访问地址；若启动或验证失败，明确报告未生效的部分。

## 开发与预览服务

- 本地日常开发只使用开发服务。主工作区常驻 WebUI、官网、UI Design 各一个实例，不同时运行同一应用的构建预览或重复开发实例；官网首页和文档共用同一个官网服务。
- 以下默认端口适用于主工作目录；独立 worktree 按任务需要使用各自分配的空闲端口，每个涉及的前端应用同样只运行一个开发服务。下文的“仓库根目录”指当前任务 worktree 的根目录，主分支服务则使用主工作目录。
- 启动前核对进程所属目录、命令和监听端口。已有符合要求的服务就复用；切换启动方式时停止同一工作区的旧实例，不通过另开端口保留重复服务。
- 开发服务默认监听 `0.0.0.0`，允许同一局域网内的设备访问。除非用户明确要求，否则不要绑定 `127.0.0.1` 或 `localhost`。

| 应用 | 仓库根目录启动命令 | 主工作区端口 |
| --- | --- | --- |
| WebUI | `npm run dev`（或 `npm run dev:webui`） | `5191` |
| 官网及文档 | `VITE_SITE_MODE=live npm run dev:website` | `5189` |
| UI Design | `npm run dev:design` | `5188` |

- 官网本地开发和验收在启动命令中显式带上 `VITE_SITE_MODE=live`。未设置该变量或留空时，程序仍使用 `coming-soon`；检查其他模式时调整同一实例的环境变量并重启，不另起常驻服务。
- 现有 `build`、`preview` 等命令保留，构建预览仅用于明确需要验证产物的临时检查，检查完成后停止，不作为日常开发或合并后的常驻服务。官网预览沿用构建产物中的模式。
- 启动或调整后确认实际监听地址、端口、开发模式和实例数量，并提供可用的局域网访问地址 `http://<本机局域网 IP>:<端口>`。
