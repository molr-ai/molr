# Resource Authorization Quotas

The compute, network, and filesystem hard quotas below apply to Linux. macOS compute grants retain duration only; network grants are a quota-free toggle and workspace capacity quotas are unsupported. Groups can still limit task concurrency. Network revocation stops the managed process group using that grant, rather than applying Linux connection-level updates. See [native macOS command permissions](../../admin/sandbox/macos.md) for node capabilities and API values.

2026-10-03: Added account isolation, administrator user groups, and independent member quotas; see [Multi-user and Member Quotas](users-and-groups.md) for the shared resource catalog and dual-layer checks.

Updated: 2026-10-02. The current implementation and acceptance boundaries are defined by this document and the tests. For user operations, see [Resources and Permissions](../../user/guides/permissions-and-budget.md#compute-network-and-workspace-quotas).

## Full Access Exceptions

The compute authorization `Scope.FullAccess=true` only allows `execute`, and prohibits `Constraints`, `Temporary`, path/model scopes, and read-only options. It exists independently of the standard compute authorization for the same resource; standard calls only match standard authorizations, and explicit Full Access only matches Full Access authorizations. Modifying authorizations cannot use this to stack standard quotas.

Full Access calls do not apply compute, network, workspace, or group concurrency quotas, and do not count towards the standard limit of ten concurrent tasks. Existing limits in external systems remain in effect. The `AllowFullAccess` referenced by groups defaults to false; standard members can only be authorized after explicit delegation by an administrator; removing the delegation invalidates existing Full Access permissions. Standard calls still execute according to the quotas described below.

## Module Responsibilities

`internal/quota` unifies model budget accounting, network ledgers, call quota statistics, and cycle calculations. `policy` retains identity/authorization checks and completes cost reservations via quota; model reservations, tools entering Running state, and plugin HTTP call registrations continue to share the original transaction with the corresponding quota checks. `auth` manages group quota configurations, and `app` is responsible for identity and resource resolution, service assembly, and returning display data. cgroup, network gateways, and filesystem project quotas still take effect on the execution side; the database does not replace kernel hard limits.

Quota usage for model, tool, and plugin HTTP calls follows the local call lifecycle: models only occupy reservations and concurrency during `reserved`, tools only occupy concurrency during `running`, and `prepared/running` for HTTP connections occupies concurrency. Upon call exit, it is either settled normally or recorded as `unknown`; `unknown` retains evidence of unknown results/costs and the original cycle call count, but no longer occupies cost reservations, concurrency, or cross-cycle call quotas, nor does it authorize automatic retries. `released` still only indicates confirmed non-charging, distinguished from unknown costs. If a trusted receipt is obtained later for unknown costs, idempotent supplementary settlement can be performed, with costs attributed to the original call cycle.

Models uniformly read persisted receipts via the exit finalization path; cancellation contexts do not skip finalization. After the Runtime acquires an exclusive lock and before scheduling worker threads start, it first supplements settlement for existing receipts of old reservations, then ends remaining local occupancy; persisted results and background Shell tasks are retained and handled by their respective existing recovery logic. No leases, renewals, or periodic cleanups are added. Concurrency represents local in-flight calls and cannot guarantee that disconnected external services have stopped executing. Releasing unknown costs may result in a small amount of actual consumption not being counted; this is an explicit trade-off for personal budget protection. Network traffic ledgers and storage quotas maintain their respective existing rules and do not automatically refund based on the unknown status of calls.

Quota queries use database-side account/resource/status/time filtering and composite indexes. Tool and plugin HTTP calls are counted via covering indexes, without reading call records into the business layer; cycle counts, active counts, and unknown result counts share the same transaction snapshot, and cycle boundaries use nanosecond-precision UTC private time keys. Active calls outside the cycle are additionally counted in the call volume, with `Carried` separately marking this portion; active calls within the cycle are counted only once, and `unknown` is only counted in its occurrence cycle. Display and admission reuse `ModelTotals` / `CallTotals`; member quotas are accumulated by user, and neither Group ID nor Grant ID serves as the ledger identity. The semantics of model amount statistics and per-call upward rounding of exchange rates are preserved.

Network accounts directly read database records via stable account keys; the same execution-side transaction coordinates all levels. Usage reads reuse the transaction in the call context, without creating independent transactions or waiting for database locks; query the calculation cycle change view, and persist changes for the next reservation. Connection slots are not persisted; restarts still terminate old executions.

## Data and Approvals

`policy.Grant.Constraints` separates compute, network, and storage quotas from `Scope`; standard compute, network, and managed-workspace authorizations must explicitly provide quotas; model, tool, and external catalog scope authorizations do not require quotas. `Temporary` replaces the base quota before the specified time and restores it upon expiration. `PermissionRequestInput` supports `grant_id`, `grant_version`, and up to seven `additional_requests` items; the main application plus additional items create or modify authorizations in a single database transaction, and approval retries are idempotent. Before creating an approval request, validate the real `resource_id`, resource type, supported operations, model ownership, and existing authorization version item by item; requests with only descriptions are not accepted. Errors are returned via `ok=false`, `error.field`, and `error.message` in the tool result, with additional item fields prefixed with `additional_requests[i].`. Validation failures do not write requests, chat cards, or idempotent receipts, and do not trigger `permission_pending`. Upon approval, re-validation continues based on the final values filled in by the user. The original application, final `Granted`, and `GrantedAll` are retained separately. Running task invalidation handling is executed after the combined approval transaction commits; rollback on failure cannot prematurely terminate tasks.

The permission request list reads a maximum of 200 items, and the model context reads a maximum of 40 items; both prioritize pending items within the same read transaction, then supplement processed records in descending order of creation time; items with the same creation time are sorted by request ID in ascending order. Creating a request only reads pending items for that assistant, first reusing identical requests, then checking the limit of 20 pending items.

`permission_list` and the model context retain authorization versions, quotas, usage, and applicable capabilities. The three frontend authorization entry points share the quota form, supporting temporary quotas; combined cards pre-fill item by item, allow collapsed editing, and approve all at once, with the top-level authorization time applied uniformly to all sub-items. `GET /api/resource-usage?assistant_id=…&resource_id=…` reads local or remote usage after verifying the owner and assistant binding. This query excludes revoked, expired, and Full Access authorizations in the database, reading only the first valid standard authorization in key order; authorization selection and temporary quota calculation use the same point in time, returning no standard quota if there is no match.

## Compute

New authorizations create a shared parent cgroup for the same owner/assistant in the current sandbox, with each execution being its child cgroup. CPU, memory, and processes/threads are cumulatively limited at the parent level; `temp_bytes` limits the `/tmp` tmpfs memory temporary disk for a single execution, with actual writes counted towards compute memory and cleaned up with that execution; it does not occupy the persistent storage quota of `/work`, and the interface explicitly labels it as "Memory Temporary Disk /tmp". The actual timeout also applies to a single execution. The CPU unit is one-hundredth of a core. Compute modifications stop related tasks, and new tasks use the final approved values; currently, there is no guarantee of extending the deadline or raising the RLIMIT of started processes without interruption.

Deployment of `authorization_ceilings` is separate from the sandbox base protection configuration, with Runtime and remote backends verifying separately. Restarts reclaim legacy executions in the shared parent group, without reusing old processes that are still running.

GPU device access is placed in `ComputeConstraints.gpu.device_ids`; default/empty lists do not authorize GPU. This field is a hardware scope, not a VRAM or compute power quota. Both deployment and user group scopes verify base and temporary configurations; modifications, revocations, and temporary configuration expirations follow the compute task termination rules. Assistant applications retain the complete compute configuration, and standard Shell automatically obtains the effective device set based on `compute_id`. The number of tasks follows the standard execution concurrency limit, without adding a new GPU concurrency ledger.

## Network

`network_mode` defaults to automatic, and `none` explicitly disables outbound network. The Runtime generates network mappings based on the current assistant, sandbox, effective authorizations, and real deployment targets; model tools no longer expose `network_ids`. Old calls can carry an explicit subset of IDs, but this is not an authorization and still requires real-time checks.

Each actual connection selects a unique network source in the stable order of deployment rules; it does not switch to another source due to quota exhaustion. The ledger key is owner/assistant/actual network source, not using Grant ID, to prevent clearing resources when creating new authorizations or duplicate connections. Traffic uses the bidirectional forwarding payload metric; DNS requests and responses are counted towards the effective network source selected during resolution, and query quota is obtained before calling the resolver; port forwarding does not belong to this outbound quota.

The gateway requests traffic reservations and connection slots from the parent process via the existing trusted control channel. Persistent reservations precede writes, and unused portions are released after settlement; the read direction deducts quota after receiving data and before delivery, avoiding TLS deadlocks caused by idle read pre-occupancy. Failed unsettled reservations still occupy quota in subsequent cycles. The ledger is managed by `internal/quota` and saved in the SQLite of the actual execution side: local machines use `runtime.db`, and independent Sandboxes use `sandbox.db`. Reservations and settlements for assistant and member accounts are committed in the same transaction; connection slots are still managed with the Runner lifecycle. Call volume is bounded, currently up to 64 KiB per call; larger throughput batch prefetch optimizations have not yet been implemented.

Daily/weekly/monthly cycles are calculated based on natural cycles in fixed IANA time zones, with weeks starting on Monday, and DST using actual calendar boundaries. Base cycles and time zones are not editable, and temporary quotas must use the same cycle. Changing amounts does not clear historical consumption. Concurrency slots are shared by the same sandbox Runner; they are released upon connection end or execution destruction, and restarts terminate old executions.

The quota module reuses up to 64 parsed named time zones within the process, sharing a single load result for budget validation and cycle calculation. Cycle boundaries are still calculated based on the current time of each call; account time zone changes immediately use the new time zone, and `Local` follows the current host time zone.

Network revocation and expiration are checked at the connection layer, not merged into the deadline of the entire Shell. Idle TCP connections are also periodically re-checked; remote Runtimes update current authorizations via the lease renewal link. Network quota adjustments do not cancel compute tasks.

## Workspace

Built-in workspaces are registered as `managed-workspace` storage resources, still using the `/work` of the same assistant. Capacity support relies on pre-configured Linux project quotas; applications and interfaces clearly distinguish this capability from the legacy single-file/disk low-watermark protection. `resourcequota.ApplyWorkspace` validates directory project identity and existing file ownership, using kernel byte and inode hard quotas; Shell prohibits ioctls and quotactl that change project ownership. File tools, imports, and Shell share this filesystem boundary.

When selecting workspace quotas for an assistant, first use the account in the shared resource catalog to locate the workspace resource, then filter authorizations by the calling account, assistant, and that resource. This step only loads authorizations for the current workspace, retaining historical records for effective authorization priority and base capacity fallback after expiration/revocation. User group shared capacity is separately validated by group quota checks.

The Runtime does not automatically create project IDs for existing directories, nor does it automatically escalate privileges or remount. This capability may be unavailable on the default user service and must be explicitly reported; do not treat periodic directory scans as hard limits. The original 10 GiB configuration only applies to the upload attachment library; external shared directories are still managed by their resources and deployment. Temporary expansions restore base limits upon expiration, retaining existing files.

## Remote and Migration

The capability protocol version is 9, and transport endpoints continue to use the `/v2/sandbox/` path; version negotiation explicitly rejects old backends to avoid losing new quota fields. Requests carry trusted compute, network, and workspace constraints, and the backend re-executes deployment boundary validation. `quotas` controls request binding to existing execution identities, only updating network authorizations within the original mapping, without adding new network targets.

Compute, network, and managed-workspace authorizations must explicitly include `Constraints`. Creation and editing interfaces reject missing quotas, and execution selection and remote backends reject missing compute/network quotas, without providing deployment limit fallbacks. Existing old authorizations are directly deleted via one-time data maintenance; the Runtime does not retain startup cleanup, migration, or conversion code. Model/tool, external catalog scope permissions, and approval history are retained. Automatic network selection deduplicates by actual source, adopting the most recently updated quota authorization. Network historical usage and unsettled reservations are stored in the database of each execution instance, and database snapshots include this ledger; remote execution sides still require independent backups.

## Authorization Validity

Combined applications fill in `expires_at` at the top level, and sub-items inherit it; approvals use the top-level `ExpiresAt` as the validity period for the entire group, with `null` indicating permanent. Temporary quota restoration times are saved independently and cannot be later than the authorization expiration. Before creating an application, validate resource existence, ownership, type, operations, and quotas item by item; failures do not generate approval records or cards.

## Verification Methods

Runtime tests cover concurrent reservations, cross-cycle settlements, transaction rollbacks, revocations, and combined approvals. Real Linux sandbox special checks verify multiple executions sharing compute limits and network usage; workspace hard capacity requires a filesystem supporting project quotas and actual configuration, and ordinary unit tests cannot prove it is in effect.

The end-to-end entry point is `MOLR_E2E_SANDBOX_SERVICE=1 npm run test:webui -- resource-quotas.spec.ts`, requiring Linux, systemd user services, static BusyBox, and a specified Go version. This flag starts an independent delegation service for each temporary Runtime; if skipped due to unmet environment requirements, sandbox acceptance cannot be reported as passed.
