# Runtime Public Deployment and Security Boundaries

2026-10-03: Added account isolation, administrator user groups, and independent member quotas; see [Multi-user and Member Quotas](users-and-groups.md) for shared resource directories and dual-layer checks.

Updated: 2026-10-03. Status: The monolithic Runtime is connected to real implementations; see [Runtime README](../../../../runtime/README.md) for verification scope and adapter limitations.

The Go monolithic server supports deployment on public servers. Authentication, authorization, sessions, and auditing are built into the same program; self-hosting does not imply that requests are trusted, and LAN access requires authentication by default. Independent accounts and administrator user groups are supported: business data is isolated by account, resource directories are maintained by administrators, and ordinary members' execution is simultaneously restricted by user group scope, member quotas, and assistant authorizations; no inter-user shared spaces or independent authentication services are provided.

Full Access is an explicit computational permission exception: it executes directly in the service environment only if the deployment of `sandbox.allow_full_access`, the ordinary user group's `AllowFullAccess`, assistant `Scope.FullAccess` authorization, and every `full_access: true` check pass. This path has no file, network, process isolation, or resource limits provided by Molr, and can access credentials and data accessible to the service account itself; application-layer multi-user confidentiality boundaries cannot constrain this system access. It is intended for trusted use scenarios already deployed in externally isolated environments. Calls that do not explicitly request Full Access continue to follow the isolation mechanisms described in this document; isolation failures do not fall back to direct execution.

## LAN HTTP and Initial Installation

`tls_mode: lan` is an explicit trusted LAN plaintext mode, allowing numeric private/loopback URLs and listening addresses, while rejecting public peers, unregistered Host/Origin, and proxy forwarding headers. It does not provide transport confidentiality; use TLS for public networks. Session cookies are named by port, retaining HttpOnly, SameSite, and CSRF protections; Secure/__Host cookies for HTTPS are not downgraded.

Local bootstrap generates a random owner password, saves it to `initial-password` (0600) in the private data directory, and simultaneously writes the initial bootstrap state. HTTP does not open account initialization. access/doctor are executed via the normal authentication API, adhering to the current password and MFA; re-running installation does not reset accounts. Provider auto-discovery is triggered only by administrators, limited to fixed loopback candidates, and rejects redirects; it does not constitute a general port scan or network policy exemption.

## 1. Entry Points and Deployment

Public network entry points must use HTTPS, which can be configured directly by the server with certificates, or TLS can be terminated at a trusted reverse proxy. In proxy mode, use network access controls to restrict direct backend connections, and trust only explicitly configured proxy sources and forwarding headers; do not determine source trustworthiness based on client-self-reported `X-Forwarded-For` or protocol headers.

The listening address can be `0.0.0.0`; the listening scope and authentication are independent. Explicitly configure the external address, allowed Host/Origin, trusted proxies, certificates, and data directory in the configuration; verify the actual TLS chain for public deployments, and do not judge "encrypted" status solely based on request headers. Business APIs do not accept plaintext public network authentication requests.

The public entry point includes only pages/static files required for login, the login flow, and minimal liveness probes containing no internal information. Other interfaces require authentication by default, including SSE, search, attachments, artifact downloads, and management operations. Debugging, performance profiling, and detailed runtime metrics are not default public network interfaces.

## 2. Account Initialization and Authentication

The owner is created via local `molr init -config … -username … -password-stdin`; see [Deployment Guide](../../admin/README.md) for complete deployment steps. When uninitialized, business services are not opened, no installation page is provided for public network pre-registration, and no default account passwords or public registration entries are set. Passwords are provided via interaction or protected input, and are not written to command-line arguments or regular logs.

The first version supports username/password login, password modification, login device management, and logout. TOTP two-factor authentication and one-time recovery codes are supported; enabling them is recommended for public deployments. Security setting changes, password modifications, access token creation, and data cleanup always require recent identity re-verification. Saving Provider/management credentials and data exports are controlled by the "Sensitive Operation Verification" switch, which is off by default; when off, valid owner sessions, permissions, and CSRF are still verified. When on, re-verification is required, and if TOTP is bound, the verification code is also checked. This switch and verifier binding/unbinding are centralized in User Settings → Security. Account recovery is performed locally by operators holding host management rights; after recovery, old sessions and access tokens are revoked, and audit records are left. Login errors do not reveal whether an account exists; login and two-factor authentication are rate-limited by account and source to prevent permanent lockouts from being abused to block owner access. [OWASP Authentication Recommendations](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

Passwords use Argon2id with independent salts, storing only hashes; see `runtime/internal/auth` for parameters and verification logic; do not store passwords in plaintext or using ordinary fast digests. TOTP keys require protected storage, and recovery codes store only verification digests. [OWASP Password Storage Recommendations](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

## 3. Browser Sessions and Client Tokens

Browsers use random, unpredictable session tokens; the server stores revocable session records and token digests. Device identifiers only participate in session matching and do not grant permissions; clients save a random deviceId based on the browser site origin or App installation instance and service address; the server stores only its digest and uniquely constrains device sessions by account and digest. Each full authentication generates a new SessionID, Token, and CSRF, replacing the device's old records, notification permission subscriptions, and recording audits in the same transaction; failed logins do not replace them. MFA challenges are bound to device digests, display information, and the session ID at the start; old challenges cannot overwrite newer successful logins. Cookies are set with `Secure`, `HttpOnly`, and appropriate `SameSite`; non-default ports are isolated via cookie names, and login tokens are not exposed to frontend scripts. After login, session identifiers are rotated, and idle and absolute expiration times are set; upon logout, password change, or remote device logout, corresponding sessions are revoked. [OWASP Session Management Recommendations](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

CSRF tokens and origins are verified for state-changing requests using Cookie authentication, including the login flow; GET requests do not produce business writes. Same-origin deployment is the default solution; cross-origin access is allowed only for explicitly configured origins, and CORS does not replace identity verification or CSRF protection. [OWASP CSRF Protection Recommendations](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

CLI or native clients can use independent, revocable access tokens with validity periods and operation scopes, sent via the `Authorization` header; the server stores only token digests. Tokens must not be placed in URLs, SSE query parameters, model contexts, or regular logs, and cannot obtain scopes exceeding owner permissions. High-sensitivity account management operations also require independent identity confirmation and cannot be completed solely with ordinary business tokens.

Browser SSE continues to use login cookies, while native clients use authentication headers. Identity and data permissions are checked during connection establishment, disconnection recovery, and continuous pushing; delivery stops and connections close after session/token expiration or revocation; established connections do not imply permanent authorization. Logging out a device only terminates that device's access; accepted background tasks continue to run according to current assistant permissions and task status, and users can separately cancel tasks.

## 4. User Permissions and Assistant Permissions

| Check Layer | Issues Addressed | Implementation Location |
| --- | --- | --- |
| Identity Authentication | Who initiated the request, are credentials valid | `auth` and API middleware |
| User Authorization | Does the user have permission to read/write the assistant, message, task, resource, or file | Business modules and `policy` |
| User Group Constraints | Is the model, tool, or sandbox assigned, does it exceed member cumulative quotas | `auth`, `policy`, and Runtime execution entry |
| Assistant Authorization | Can the assistant perform the action on the specified resource, does it exceed the budget | Tool, model, and operation execution entry |

Authorization defaults to deny and is checked during every object access and execution. Resource queries constrain the owner and visibility scope, not trusting user IDs in requests; file IDs, task IDs, search filters, and SSE cursors cannot substitute for authorization. Hiding buttons on the client, random IDs, and successful login are insufficient to prove that an operation is allowed. [OWASP Authorization Recommendations](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

Private data for each account stores ownership and performs checks; administrator status does not bypass private object permissions of other accounts. Permission judgments are placed at business entry points to ensure consistent rules for HTTP, built-in tools, and background plans; checks cannot be performed only at the routing layer. If authentication storage or authorization checks fail, operations are rejected and do not degrade to anonymous access.

Agents use the owner, assistant, and task identities bound to the server, and do not hold user passwords or login tokens. Scheduled tasks execute with the saved assistant identity when due, re-checking current Grants, resource scopes, budgets, and task status; prompts, retrieved materials, or model outputs cannot grant permissions. Permission revocation blocks subsequent operations; in-flight operations are handled according to their cancellation and result verification capabilities.

When an assistant reads attachments uploaded by the account, it must obtain access rights through the attachment's owning task, assistant ownership, or its own session. Session association checks only read the ConversationID and AttachmentIDs of messages, and check ownership once per session within the same read-only transaction; results are used only for this access, and current permissions are re-checked for subsequent requests.

When the owner hires an assistant and selects a model, it is considered as allowing the assistant to read and call that model. Runtime creates the corresponding Grant during the hiring transaction, binding the authorization to the selected model's `Scope.ModelID` and its Provider; other models under the same Provider are not automatically authorized, call addresses follow the Provider's current configuration, no separate Grant address whitelist is stored, and no write, management, or other resource permissions are granted. Grants can be revoked in the permission interface; idempotent retries and renaming do not restore revoked permissions. This authorization does not exempt deployment network policies, model prices, or budget checks.

## 5. Files, External Requests, and Program Execution

- **Files and Content**: Uploads are limited by size, type, and quota, using controlled storage identifiers; access verifies ownership and path boundaries, handling path traversal, symbolic links, and archive extraction overflows. Databases, configurations, and backups are not placed in static resource directories. Downloads are authorized individually; untrusted HTML, SVG, Markdown, and cards cannot obtain arbitrary script execution capabilities on the main site; previews use secure rendering or isolation methods.
- **External Requests**: Model proxies, web reading, and external connections verify protocols, targets, and actual connection addresses, allowing `127.0.0.1` by default, blocking cloud metadata, other loopbacks, link-local, and unauthorized internal network targets, and re-validating upon redirects and DNS resolution changes. When connecting to local or LAN models is required, deployers must explicitly allow specific IPs in the static configuration `network.allowed_private_ips`, effective after restart; WebUI and resource interfaces cannot modify this policy. Connections still verify the origin bound to the resource, do not open general internal network access, and do not forward authentication information to new targets. This boundary is used to prevent SSRF. [OWASP SSRF Protection Recommendations](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)
- **Program Execution**: Host startup commands are constructed by trusted code, limiting executable operations, parameters, working directories, file, and network permissions; scripts generated by models are only handed to fixed interpreters within authorized sandboxes. The server runs as an unprivileged identity; controlled subprocesses cannot inherit all environment keys or access server private data; if required isolation cannot be implemented, related operations are rejected.
- **Capacity and Timeouts**: Limits are placed on request bodies, uploads, search results, SSE connections, task concurrency, tool output, and execution time. Login protection takes effect before authentication, and business quotas are implemented per subject to avoid a single request or assistant exhausting global resources.

## 6. Data, Auditing, and Upgrades

Login accounts, sessions, and access tokens are saved in the protected data directory; real model and connection credentials are managed and encrypted by `credential`, with the master key and database backups protected separately. Logs do not record passwords, cookies, tokens, authentication headers, or complete sensitive request bodies.

Complete model responses and raw assistant messages are private execution data, persisted during normal execution without relying on debug collection; request authentication headers are not recorded, nor are they published via chat, status queries, or ordinary SSE. Adapters only return fields allowed by this protocol and matching sources; storing unknown fields cannot bypass cross-Provider isolation.

`audit` records login successes/failures, session and token revocations, permission modifications, resource connection changes, sensitive data operations, and management operations, including subject, action, target, time, result, and request identifier. Audit entry points are accessible only to owners, with retention and capacity limits set. Auditing is not a promise against host administrator tampering; host management rights belong to the deployment trust boundary.

Backups contain sensitive data, are managed as protected files, and cannot be downloaded via public static links. After restoring backups, old login sessions and client tokens are revoked to avoid restoring revoked credentials; the recovery process re-confirms account control. Upgrades preserve permission semantics and verify migrations; security fixes are delivered through complete server releases.

## 7. Public Delivery Acceptance

Public network access capability is a basic requirement for the first version, at least verifying:

1. Uninitialized states cannot preempt accounts, anonymous access cannot read business data, search results, attachments, or SSE; public entry points go through HTTPS.
2. Passwords, two-factor authentication, expiration, remote logout, recovery, and token revocation take effect; old SSE connections stop receiving new data.
3. Modifying object IDs, cursors, resource paths, or declaring identities cannot bypass permissions; background plans and tools cannot bypass permission revocation.
4. Cross-site writes, malicious content previews, file overflows, SSRF, and command injection are blocked by corresponding boundaries.
5. Forged proxy headers cannot bypass authentication or source restrictions; authentication failures, uploads, and long connections cannot occupy resources without limits.
6. Logs, errors, downloads, and backup paths do not leak credentials, debug entry points are not exposed, and recovery does not reactivate old sessions and tokens.

The above constraints are verified by backend implementations and integration tests; tests cannot replace independent security audits. Agent Shell is only opened when a Linux sandbox is configured with corresponding computational permissions; execution is rejected if isolation conditions are insufficient. Linux directory tools use openat2 to prohibit link traversal; other systems reject this tool. Deployment still requires valid TLS and correct trusted proxy configuration.

Shell has adopted Linux Bubblewrap, seccomp, cgroup v2, and controlled network egress; other systems are not currently open; see [Sandbox Usage Instructions](../../admin/sandbox/linux.md) for deployment limitations. Model scripts are only handed to fixed interpreters after isolation is implemented; host startup parameters and resource bindings are always constructed by trusted code. Resource directories are directly mounted, writes take effect immediately, and cancellations do not roll back; Shell network does not inherit local access permissions from model connections, and device passthrough is not supported.

## Authentication Record Retention

Login device queries exclude revoked, absolutely expired, and idle-expired sessions before pagination. Invalidation does not rely on recycling tasks; Runtime performs authentication recycling after startup and every hour, with a maximum of 500 records per batch, a one-second interval between backlog batches, and failed records are retried in the next cycle after logging errors. Session revocations are deleted after 7 days, or unrevoked sessions are deleted 7 days after their absolute/idle expiration; login links are deleted after ExpiresAt exceeds 7 days; expired challenges can be deleted directly. Deletion predicates are re-evaluated within write transactions, retaining valid sessions and MFA that can still be completed. Audit records are not deleted along with credential records.

The WebUI uses IndexedDB atomic transactions to initialize the `deviceId` and maintain the login lease, supporting LAN HTTP; the lease covers pre-login CSRF, password/link exchange, and MFA, preventing simultaneous logins from other tabs. Logging out preserves the `deviceId`, while closing the page releases the lease; leases from abnormal exits are reclaimed upon expiration. Cross-tab identity updates reuse `BroadcastChannel`; late 401 responses from old identities do not clear already rotated sessions.
