# Automatic Context Update

Before every model request, the Agent Loop re-fetches currently available tools, account preferences, workspace descriptions, and project instructions and Skills from the Runtime local assistant workspace. It compares applied versions by content hash; when changes occur, it generates a private `context_changed` notification containing the complete valid content, source, scope, and revocation records. Versions and add / replace / remove changes are retained in internal state and debug records. The first request treats existing sources as new additions. If there are no changes, no notification is appended, and no new `context.changed` debug record is generated.

Tools simultaneously update the `Tools` of the model request. Tool definitions are sent only via `Tools` and are not repeated in automatic snapshots or base prompts. Internal tool summaries are still generated from the same Definitions result, used to detect changes in definitions, permission metadata, and availability. Tool calls still validate real-time permissions during execution; context updates cannot grant permissions. Updates occurring during model generation take effect on the next model request after all tool results for that turn have been collected, without interrupting generation or breaking tool call / tool reply pairs.

The base prompt specifies `conversation_publish` as the sole channel for communicating with the user, explicitly stating that direct `content` / final replies are invisible to chat users; if a reply is required, it must first be published and the tool result checked. Known base prompts in old checkpoints are precisely matched at model request boundaries and replaced with the current template, without rewriting custom system instructions or automatically publishing internal text to chat.

When a user message turn receives a model end response with no tool calls, if the entire turn has not actually attempted `conversation_publish`, the Runtime inserts a private reminder with the user role, asking if the message sending was forgotten, and stating that it is still possible to end directly if no reply is needed; the reminder does not mandate sending. The original execution loop then continues, with at most one reminder per turn, including user messages taken over urgently in that turn. Pure background events do not trigger this; it also applies after background turns take over user messages. `PublishAttempted` and `PublishReminded` are saved with the current execution cursor, reminders and markers are atomically persisted, model retries, restarts, and context compression do not reset the count, and new user turns restart the count. Attempts that failed or have unknown results do not trigger this reminder to avoid misleading resends; skipped calls are not counted as attempts. Stopping, execution errors, and waiting for permissions do not trigger re-runs, and continued requests remain subject to original step limits, budgets, and cancellation limits. Neither reminders nor direct replies are automatically published to chat.

User input in user message events appends natural language constraints after the first line of JSON: call `conversation_read` before responding, starting from the most recent history and paging to earlier history according to `NextCursor`; each page returns messages in ascending order by message sequence number, with the latest message last. Read all current unread messages, and comprehensively process supplements, corrections, and cancellations in order; do not read only the trigger for `MessageID` or the latest single message, nor guess the body from event references. If the read boundary cannot be confirmed, continue reading to the end of history. This is a prompt constraint; message delivery, queues, and confirmation mechanisms retain their original behavior.

Automatic context, control, recovery, verification, handover, and urgent notifications directly use the user role; identified Runtime notifications in old checkpoints are converted to user role during continued execution / request projection, retaining source, body, and recovery metadata. The first base instruction remains system, and custom system instructions are not rewritten by this migration. Historical workbench records and checkpoint load snapshots retain the original role.

## Sources and Loading

- Chat entry: When connecting to WeChat, add the `chat_channel` source, describing image/file capabilities and prompting to avoid interactive cards; necessary cards will be converted to text and links. Current bindings are re-read for every request; the source is removed after unbinding; it is not written to the assistant's permanent instructions.
- Tools: `Tools.Definitions` re-authorizes and filters every turn. Names, descriptions, and parameters only enter the request's `Tools`; automatic notifications do not list tool inventories or tool revocation lists. The hash of the complete internal definition still detects changes in required operations and other metadata.
- Current authorization: `permissions` refreshes the current assistant's effective authorizations before every model request; additions, modifications, revocations, and expirations change the snapshot version, replacing old authorization information. Scope and validity come from real Grants; if unchanged, they are not re-injected, and actual tool execution still re-authorizes.
- Authorization requests: The `permission_requests` source reads only pending approvals and recent decisions for the current assistant (up to 40 items); after approval or rejection, the snapshot is entirely replaced. Approval records are not effective authorizations or executable instructions; users can modify the proposed authorization scope and duration, and must still query `permission_list` before continuing work. After rejection, repeated applications are not allowed without new instructions or changes in requirements.
- User preferences: After authorizing the current execution, read timezone, language, and currency by the associated OwnerID, injecting them as `user_preferences` / `runtime/user_preferences`. Version is calculated only based on the valid values of these three items and their respective sources, excluding the total settings version, other settings, or the current clock. If the timezone is unsaved or invalid, it is marked as unknown; if language and currency are missing, en / USD are used and marked as default, while saved valid values are marked as user_settings. These are user-overridable default preferences, not additional instructions or permissions. Language determines the default reply language; currency does not rewrite original amounts or budgets, and conversion requires a justified exchange rate. Existing event time fields retain their original semantics, and no real-time current_time is added.
- Workspace: `workspace` / `runtime/workspace` sources describe the availability status of the local `/work`, assistant-level persistence, default directory purposes, account-shared read-only `/global`, and single Shell temporary directory `/tmp`. Default directories are initialized on first use if missing, without creating or overwriting AGENTS.md, memory bodies, or user files. If the local sandbox is disabled or group references are missing, it is marked as unavailable, and file instructions for that workspace are not injected. Normal file counts, bodies, timestamps, and disk usage do not participate in this source's version; directory descriptions do not grant permissions and do not include host paths.
- Project instructions: Fixedly read `/work/AGENTS.md` and `/global/AGENTS.md`; subdirectories read AGENTS.md for that directory and its parents according to the successful local workspace `file_list`, `file_read`, `file_search` access paths; search results use `TargetKind` to distinguish files and directories, file targets load instructions from the parent directory, directory targets load from themselves, and the same rule applies even with zero hits, without recursively enumerating project files. Upon first entering a directory, `file_list` should be called separately first, and files modified or Shell executed only after the next model request loads the instructions; repeat when entering deeper directories. Each document applies only to its directory and subdirectories, with more specific instructions taking precedence. Loaded scopes are saved in automatic sources, continuing to refresh after compression and restart; they are revoked upon deletion. External resources, remote, Full Access, and failed reads do not trigger local discovery.
- Instruction exclusion scope: AGENTS.md in the root directory `inbox/`, `outputs/`, `.local/state/molr/`, and in any level `.agents`, `.git`, `node_modules`, `.cache`, `.venv`, `vendor`, `dist`, `build` are not automatically loaded. Skills still use independent entries. Imported materials and execution outputs are only data to be read on demand.
- Skills: Discover assistant-workspace Skills at `/work/.agents/skills/<目录名>/SKILL.md`. Initial directory information includes directory name, read path, and YAML frontmatter preserved as-is (YAML is not interpreted within the Runtime). A successful workspace `file_read` activates that Skill, and the full body is automatically injected in the next turn; partial reads also activate the full body. Subsequent modifications refresh the body, and the loaded state is maintained after restart. Reading via Shell is not a reliable loading signal; directory prompts require using `file_read`.

Runtime project repositories, host home, other assistant directories, or automatic traversal of authorized external storage are not read. Remote computers do not provide workspaces and are not automatic context sources; remote AGENTS.md or SKILL.md with the same name are only task materials for explicit reading. Project instructions and Skill content are scoped workspace guidelines, which cannot override Runtime rules or explicit user instructions, nor do they automatically become higher-privilege instructions.

Currently, file sources follow the restricted reading of Linux directory tools: rejecting symbolic links, hard links, special files, and out-of-bounds paths. Content hashes are used to identify changes, and file timestamps are only used to detect concurrent modifications during collection. Collection explicitly fails upon encountering read errors, concurrent modifications, or exceeding limits, without treating unread content as deleted, nor initiating model requests or reserving the model budget for this instance.

Skill directories are only shallowly enumerated, up to 4096 items; instructions check up to 256 access directories and their ancestors, 32 levels deep, without scanning normal project trees; single files are up to 64 KiB, and total read volume is up to 512 KiB. The discovery phase only injects metadata, but bounded reading of the file is also required to detect Skill body changes. The directory display limit for frontmatter is 8 KiB; if there is no frontmatter, discovery is still based on directory name and path. All sources are limited to 256 (including tools), and revocation records retain abnormal capacity protection, without silently truncating valid instructions. Model context is managed according to the token capacity and automatic compression rules below.

CLI companion Skills are similarly placed in the `.agents/skills` directory of the normal workspace; plugins do not provide independent Skill types or virtual file paths.

## Notification and Persistence

Notifications are model context events internal to the Loop. New notifications directly use the user role and retain the RuntimeContext marker for identification and snapshot replacement. Identified Runtime system notifications in old checkpoints are migrated to user role during continued execution / request projection, retaining source content and permission boundaries. There is only one current base system instruction, and notifications are not merged into it. The triggering event itself uses the user role. It is not a user message, is not published to chat, and is not queued as an independent scheduler Job. Therefore, the same Handle during operation can immediately use the new version in subsequent model calls.

Model-visible notifications include:

- `sources`: Current valid sources excluding tools. Retains category, source, and scope; structured bodies directly use objects / arrays, and file bodies remain raw strings. Only Skills need to display loading status.
- `removed`: Still valid non-tool revocation records; re-adding the same source clears the revocation records for that source.
- Template descriptions for complete replacement, source trust boundaries, permissions, and preference implications. There are no change lists, snapshot hashes, or duplicate source versions; memory temporarily retains the original entry format.

`Automatic` internally still saves complete source identifiers, versions, changes, and revocation states. Tools only save metadata summaries, not another schema body.

Upon update, previous automatic notifications are entirely replaced, retaining only one valid snapshot to avoid continuous accumulation of old bodies. Historical model messages, tool call results, and vendor reasoning states remain unchanged, and notifications explicitly state that old content has been replaced or revoked.

The Checkpoint JSON retains `Inputs` and `Automatic` (valid snapshot, applied versions, revocation records, Skill loading status); during execution, the exact position of the notification in the request is also retained so that model requests can be restored as-is. These fields reference the shared message prefix via [Context Storage](context-storage.md), and database checkpoint rows do not duplicate the body. After recovery, it first compares with current sources, then reassembles notifications; if sources are unchanged, the same version is used, and recovery is not mistakenly recorded as a new change. Resetting context also clears these states. Automatic compression retains `Automatic` and does not discard source state by only summarizing `Inputs`.

Currently, idle assistants are not actively woken up due to file changes. When idle, the latest version is loaded before the next normal event execution; consecutive multiple file modifications are naturally merged into the latest content seen at that boundary.

## Verification and Observation

The workbench records private `context.changed` steps; `model.start` displays the actual injected content and Tools of the same version, and `Automatic` can be viewed in the checkpoint. This information is not exposed through the normal chat stream.

Behavior tests cover: tool revocation and instruction updates during operation, notification deduplication, tool definition consistency, restart recovery and revocation, Skill directory / on-demand loading / update / deletion, path isolation, read failures and budget boundaries, as well as existing reasoning state and checkpoint compatibility tests.

## Model Context Template Specification

`runtime/internal/agent/prompt/templates/` centrally maintains templates for base instructions, automatic snapshots, events, stops, handovers, recoveries, urgencies, and compression summaries. Structured sources and each built-in tool result use the field tree explicitly selected in `prompt/schemas.go`, output via JSON text templates; directly serializing business structures or arbitrary maps into model prompts is prohibited. New internal fields do not automatically enter the context; new tools or fields must explicitly define their model display contract.

`presentation.go` generates an independent display copy before every actual model request, shared by normal requests and compression requests; token estimation and `model.start` also use the same display result. Checkpoints, operation receipts, and historical raw tool results retain internal structures for Skill activation, message delivery evidence, and recovery. Tool call IDs, parameters, roles, media, and vendor states are still handled according to the model protocol; user original text or vendor reasoning content is not rewritten via text templates.

Permissions, preferences, and Skill metadata are no longer double JSON encoded; text only retains quotes, backslashes, and control character escapes required by JSON, without HTML escaping. Empty optional fields are omitted, but meaningful false, 0, empty lists, and empty file bodies are retained. Empty authorizations explicitly indicate no explicit authorization; empty authorization request sources are omitted, and it is explicitly stated that they clear the old request window. `ExpiresAt=null` indicates no planned expiration, and missing indicates that the information was not provided; truncation, unloaded media, unknown side effects, and failures must be retained. Large tool results retain archive paths, the sandbox they are in, size, and exit / pagination evidence, without injecting head and tail fragments of internal JSON.

Templates do not repeatedly provide usage instructions from tool definitions to the model; source descriptions only explain the current state and its trust boundaries. The tool schema in request `Tools` is the sole authority. Format errors in structured automatic sources fail before model calls and budget reservations, and cannot be disguised as empty sources. Tool results that cannot be displayed are explicitly marked as unavailable, stating that the operation may have completed and side effects cannot be repeated based on this.

During recovery, even if the content hash is unchanged, the display format of automatic notifications is re-checked, and old formats are replaced; old events and tool results are projected at request boundaries, without changing original persisted evidence. Memory sources and memory tools retain existing behavior and content. Dreaming uses independent fixed Markdown system organization rules and user evidence batches, not reusing normal session context.

## Session Urgency During Execution

The WebUI provides "Urgent" when the assistant is working and there are unread user messages. Messages can still be sent during work; the stop button remains. The request uses `POST /api/assistants/{id}/expedite`, containing `Mutation`, `ConversationID`, `ThroughSequence`. Unread user messages up to that sequence number are read in send order; subsequent messages require another urgent request. Repeated requests are idempotent; requests across owners, across assistants, for archived sessions, and for future sequence numbers are rejected. If the assistant has already ended or stopped, `not_running` is returned, and execution is not resumed.

Urgent requests are persisted to disk first, then the current model sub-request is cancelled. Tool calls are not forcibly cancelled; after running tools return, unstarted calls in the same batch receive an explicit "not executed" result, followed by reading the urgent messages. Body and attachment metadata are obtained via the authorized `conversation_read`, entering the model as user-level input, and cannot be elevated to system permissions. The original task and completed tool results are preserved. Model calls, tool replies, takeover messages, and recovery positions are persisted; takeover normal message queue items do not execute independently before the current turn completes, and are consumed in one go after turn confirmation. Urgent requests do not bypass stop, permissions, quotas, context, or step limits.

`AcceptedAt` continuation indicates scheduling receipt; `ReadAt` indicates that the model request carrying the message body has received a successful HTTP response from the vendor, generated by trusted delivery metadata. The WebUI uses `ReadAt` to display as read, and `message.read` events notify clients to refresh. Read does not mean completed. Calls cancelled by urgent requests still save billing evidence; known costs are settled normally, and unknown costs are retained pending confirmation.

The `Expedite` in the status interface includes `ThroughSequence` and `State`: `pending`, `waiting_tool`, `waiting`, `read`. During tool execution, it displays "Urgent, will read after current operation ends"; when execution is restricted, the pending status is retained.

The input box always retains the send button; during execution, a "Processing" ghost button is displayed to its left, with a default transparent background and loading icon. On hover, it displays a gray background, stop icon, and "Stop" text. Clicking interrupts the current turn and returns to `idle`. This operation persists the `user_stopped` control event, saving it along with completed operations and uncertain results of interrupted operations into the private context. The control event itself does not trigger a new model request; subsequent user messages, plans, operation completions, and other normal events continue to execute according to normal scheduling. The stop transaction cancels previously generated pending events and saves the interruption boundary. Messages still in the IM outbox, delayed deliveries, or old events restored after restart will not wake up execution; new messages and normal events generated after stopping can still wake up execution. Old unread messages are retained in the session but are no longer automatically added to subsequent urgent batches. The cancellation signal is bound only to the old execution ID.

`Lifecycle("stop")` is an independent persistent deactivation mechanism (e.g., firing the assistant), still using the `stopped` status, and cannot be mixed with the input box interrupt button.

## Token Capacity and Automatic Compression

The context window is resolved by "User manual override `ContextLimit` → Provider declared `ProviderContextLimit` → System fallback 256K (262,144 tokens)". The manual field uses 0 to indicate unset, left blank in the WebUI; the fallback only takes effect at runtime and is not written back to the model configuration. The model catalog returns both `EffectiveContextLimit` and `ContextLimitSource`, and the resource list displays values and sources. Provider refreshes update declared values, retaining manual overrides. The 32,768 in old auto-discovery records cannot distinguish between guesses and provider declarations, so it is first treated as unknown; refreshing the model catalog can restore the declaration; old manual configurations remain unchanged.

For each model request, context usage prioritizes the `InputTokens` from the most recent successful response as the baseline; cached tokens are already included in the input count and are not added again. The most recent assistant response, new/changed inputs, and tool definitions supplement incremental estimates, not directly added to `OutputTokens` which may contain unreturned reasoning. Estimates and adapters share reasoning selection logic: OpenAI-compatible does not count private reasoning state, DeepSeek only counts `reasoning_content` where the current backend identity matches and is actually returned, and other extension fields that are not sent are not counted. An initial estimate is established only when there is no baseline, the backend is switched, or the context is rebuilt after compression; subsequent requests update the baseline with new receipts. Estimates are explicitly labeled with their source, are not equal to the exact count of the model tokenizer, and cannot be used to reject model requests, shrink output quotas, or reject valid summaries. When the provider completely lacks necessary usage, the model adapter still explicitly reports an error, and unknown costs are not recorded as free.

The assistant’s `ContextCompressionTokens` stores a token threshold; zero selects the automatic value `min(128*1024, floor(effective model window*0.8))`. Custom values are clamped between `min(64*1024, maximum)` and `maximum`, where `maximum = floor(effective model window*0.8)`; small windows use a fixed maximum. At safe checkpoints the engine reads the latest assistant preference and clamps it against the model actually used by the current turn. Creation, update and cloning preserve this setting; omitting it on update preserves the preference, while zero restores automatic mode. The deployment-level ratio setting has been removed. The previous limits of 180/200 inputs and 1 MiB JSON have been removed; only the 256 MiB anomaly/storage protection upper limit is retained, not used for model capacity judgment. Upper limit checks reuse the JSON encoding buffer per single input, accumulating only length, without allocating a temporary JSON copy of the full history; the count includes escapes, private metadata, and array separators, consistent with the full JSON encoding length. Checks still validate all inputs, encoding errors maintain original priority; single inputs themselves still require an encoding buffer.

Compression is uniformly executed by `context_compression_requested` / `after_step` events. Automatic detection checks the window after the complete model response, after the tool batch ends, and before the next model request; when the assistant’s token threshold is reached, it only enqueues; pending compression events are consumed even if the current turn has already ended. Manual `/compress` uses the same delivery method, bypassing the automatic threshold; repeated requests are merged. Actual compression is only executed after the complete tool call batch ends. The summary request fully preserves the messages, automatic sources, vendor status, order, and tool definitions of the current context, appending only one user role compression instruction at the end, trying to reuse the vendor KV cache; it does not trim recent or earlier messages, does not serialize chunks, and does not perform rolling summaries. The summary output limit takes the smaller of the model output limit and 1/4 of the window, without capacity pre-checks based on estimated input. Actual over-window is determined by model API error codes; failures retain all original context.

Summaries only accept results that end normally with `stop`, have non-empty body, and no tool calls; `length` is rejected for submission even if partial body exists. Termination reasons are saved in the model receipt, and incurred costs are settled normally. Upon success, the new checkpoint, status, and success record are saved in the same transaction: retaining the base instruction, saving the complete summary as a user history reference message marked with source, restoring recent Runtime events and current automatic context. The reasoning state of the summary request is retained only in receipts/debug evidence. New summaries are not rejected for submission due to overestimated size; automatic compression does not occur again before the next normal model response updates the usage baseline; manual compression can still be executed. Failures do not automatically retry repeatedly; retries with the same history, model, tools, and output budget reuse known request receipts, and configuration changes generate independent request IDs.

Inputs before compression are held by references from the current checkpoint, persisted summary requests, and collected workbench history respectively; permanent `agent.context_archives` copies are no longer created. After the event completes, request input references that are no longer needed are released, and history is retained according to the workbench item count policy; old branches are reclaimed in the background after all references are released. Upon compression failure, the current input remains unchanged, and chat records, tool operation receipts, and cost credentials are not affected by history cleanup.

The status interface `Context` returns the current window, usage source, token count, effective token threshold `CompressionThresholdTokens`, and compression count; the development workbench can view context usage and compression records, and the chat page no longer displays the context occupancy line. The workbench records `context.usage` and `context.compaction` (original text fingerprint, occupancy before/after compression, single request policy, and retained message count). The fingerprint is used to associate debug evidence and does not indicate retention of a permanent original text copy.

## Assistant Unique Current Execution State

Normal chat, plan triggers, and manual continuation share one authoritative current state in `agent.checkpoints`. Checkpoints are saved by incrementing `Sequence` at recovery boundaries such as receiving events, before actual model requests, upon receiving complete model responses, for each tool result, urgent takeover, and compression success, no longer waiting for the entire turn to succeed before updating. Event-level `agent.turn_progress` only saves version 2 assistant ID, checkpoint version reference, and takeover flag, no longer saving a second full context.

The Checkpoint's private JSON adds `Current` (current event, execution ID, tool definitions, model response position markers, tool/model step cursors, urgent message processing position) and `PendingEvidence` (operation references requiring re-verification). After restart from the same event, execution continues from the execution position of that checkpoint; model messages already written to the checkpoint are directly reused, and tools still use the original operation ID / receipt; historical `agent.handled` is only used for duplicate delivery confirmation and cannot overwrite the current state.

New event takeover retains the token usage baseline from the most recent model return, estimating only new content, not switching to a lower full estimate due to event switching. Before the new event takes over the unfinished turn, it first reads local tool receipts: restoring tool results that have been submitted but not yet written to the context, supplementing explicit `not_started` replies for unexecuted calls in old responses, and retaining side-effect uncertainty for running, cancelled with unknown results, and unknown operations. Model results have no independent recovery cache; responses not yet entered into the checkpoint are not restored. The recovery process does not execute old tool queues; new events execute according to current instructions and new task identity, with old targets retained only as historical facts. Old events are marked as taken over; delayed retries cannot re-execute them or overwrite the new context. Model/tool bills and original operation receipts are not deleted, and costs are not assumed to be zero or side-effects rolled back due to takeover.

Stopping saves the current context, completed results, unknown operation references, and stop event together; subsequent new events will re-verify late receipts. Tool replies use trusted `ToolOperationID` to match operations, avoiding replacing wrong results when different turns reuse the same model tool-call ID. All checkpoint updates are compared by version, checking execution identity, stop boundaries, and explicit reset time, rejecting delayed write-backs from old executions. Explicit resets clear the current recovery state and pending verification references, retaining the original session, operation receipts, and bills; debug history is retained according to the workbench policy.

Old deployments must first stop, back up, and convert checkpoints and pending recovery progress via a one-time offline tool; the runtime no longer imports old full event snapshots, returning an error if unsupported storage formats are found. Dreaming still uses independent batch context and progress, not overwriting normal assistant checkpoints.

New regression coverage includes: plan continuation confirming facts after failure, recovery from receipts after tool result save failure without executing unstarted calls, re-requesting and retaining original cost records when model responses are not yet written to the checkpoint, late results after stopping, isolation of duplicate tool-call IDs, interception of old execution write-backs, and rejection of unconverted old progress. Existing urgent, pause/stop, reset, budget, dreaming, and compression tests continue to apply.

## Checkpoints and Workbench Records

After the server enables `debug.enabled`, checkpoint saving during execution, turn end, user stop, and context reset uniformly collects `checkpoint.saved`. Records and checkpoints are added to the same persistence transaction: version conflicts, transaction rollbacks, or commit failures do not leave success records, nor do they advance the debug revision; after commit, the workbench is refreshed via the debug event stream. Normal execution progress saving reuses the normalized content identifier of the context storage to determine changes; if the full recovery state and execution/event identity have not changed, no checkpoint is written, version is not incremented, save time is not modified, save events are not collected, and debug revision is not advanced. Version conflicts and stop checks are executed first. Forced saving occurs after model call completion; save records are also retained for turn end, user stop, and context reset; each actual save collects only once. Control operations without running trajectories create independent checkpoint update records.

`checkpoint.saved` only saves version, time, size, `Cause`, and `ContextOmitted`, not duplicating the full context; `context.build` is collected immediately after reading the checkpoint, before new trigger events are added. Internal CAS verification reads do not duplicate load records. Historical inputs are read from collected `context.build` or model call context; the latest checkpoint is read from the current state. Old records are retained; if snapshots are missing, it explicitly prompts not collected, without borrowing nearby model inputs to impersonate historical checkpoints.

Records are constrained by server-side debug switches, per-account execution item retention policies, single payload size, and masking rules; whether the workbench entry is displayed does not affect collection; diagnostic failures do not prevent business saving, over-limit data is explicitly marked, and original checkpoints or original session history are not changed.

Compression failure reasons distinguish `model_context_exceeded` (model API explicitly returns context over-limit), `context_summary_truncated` (output quota truncation), and `context_summary_invalid` (no valid complete summary); other model errors follow unified request error classification. The workbench records failure end and original text fingerprint. Only explicit vendor error codes are identified; over-window is not guessed based on estimates or parsing of error bodies that may contain private content.

## Unified Event Delivery

`AssistantEvent.DeliveryMode` explicitly defines event intervention boundaries: `interrupt` cancels the current model sub-request, supplementing unexecuted results for unstarted calls after started tools return; `after_step` waits for the current model response and its entire batch of tool results to complete; `when_idle` claims from the queue when there is no current execution, not requiring the queue to be empty. Execution timing and event handling behavior are separated; stop control events immediately end execution but do not initiate model requests.

Normal user messages, scheduled plans, task start/modify/continue, and permission decisions generate `resume_requested` using `when_idle`; urgent promotes selected messages to `interrupt`, still using authorized reading, read evidence, and original task identity. Shell completion/run reminders, operation completion, and context compression use `after_step`. Dreaming uses `when_idle`, maintaining low priority and session exclusivity; its independent context does not receive compression and notifications from normal context.

Explicit methods are saved when writing events; old records are parsed compatibly via `Delivery()`, writing normalized job records upon claiming or consumption. Scheduler and Loop share pending job filtering, stop boundaries, and same-assistant serial constraints. Notification access and checkpoint saving are in the same transaction; compression success checkpoints, counts, event results, and job confirmations are also committed in the same transaction. Urgent messages retain existing takeover and read confirmation mechanisms. After service restart, recovery is from checkpoints and model receipts; completed tools cannot be re-executed.

The original state is maintained while waiting for compression events; during processing, `Status.Compression.State=running` is used, and the interface displays "Compressing context"; the actual state is restored after completion. Results can be `succeeded`, `not_needed`, or `failed`; compression in progress is not displayed during retry waiting. Summary errors do not replace the original context, following model retries, billing, and execution limits.

## Current Assistant Profile

`profile` Auto-source reads the current assistant's name, status, avatar summary, and profile `Version` at each model request boundary, updating with user manual modifications and `profile_update` success results. Fixed `Source=profile`, `Scope=assistant`; custom images include only type and summary, without injecting data URLs into the context. Provide this version when using tools; on conflict, first check the returned `current_profile` and do not blindly overwrite. Prompt projection configures whitelists separately for profile source, success receipts, and conflict details.

## Local Shared File Source

Runtime simultaneously discovers AGENTS.md from local `/global` and `/work` according to the aforementioned fixed entry points and access scopes, and shallowly discovers `.agents/skills/*/SKILL.md`. Paths and scopes retain their original prefixes, with shared sources combined before assistant sources. Skills load their body only if the corresponding local file_read succeeds; remote results cannot activate local skills. Memory serves independently as reference data, with only the root directory MEMORY.md summary automatically loaded; detailed files are actively retrieved via generic file_search/file_read. Recent file read/search references verify versions by path; old snippets become invalid after changes or deletions. Remote computers do not participate in auto-discovery. See [File Memory](dream-memory.md#files-and-context) for details.

## Built-in documentation Skill

`molr-docs` comes from the read-only `/molr/.agents/skills/molr-docs/SKILL.md` embedded in the binary. All accounts and assistants share this bundle without requiring a local workspace, sandbox or resource grant. Execution identity and file policy are still checked on reads. Initial context includes metadata only; successful local `file_read` activates the complete Skill. Metadata-only reads, failures, remote results and same-named workspace Skills do not activate it. Source paths distinguish built-in, account-shared and assistant Skills.

The bundle contains only Chinese documents explicitly registered in `docs-routes.json`; the website still publishes both languages. Content is generated from `docs/` and `docs/dev/`, with an index separating the Chinese content path from bilingual titles, topics and public links. Citations default to the answer language; an explicit documentation-link language takes precedence. Chinese links in the source text do not determine citation language. Run `npm run docs:generate` and commit the generated files. `npm run docs:check`, CI and release builds verify freshness. Direct Go and Docker builds use the generated files without runtime repository or network access.

File tools support reading, listing and searching built-in paths, and reject writes, edits, moves, deletions, remote and Full Access paths. These paths are not Shell mounts. Document text pages and search results are bounded to 12 KiB with continuation and truncation metadata, avoiding workspace archival. The bundle digest changes with any document, index or Skill change. Restored loaded Skills receive the current body and instruct the model to reread relevant references after revision changes.
