# Context Storage

`internal/contextstore` provides a shared, immutable message prefix tree and document storage for Agents and the development workbench. It uses existing SQLite transactions and does not expose interfaces for content-hash-based reads or arbitrary reference hooking to HTTP clients.

## Content Identity and Reuse

Each message node contains a complete message and its parent node identifier. The root uses a fixed all-zero identifier and does not occupy a database object. The node identifier is the full SHA-256:

```text
SHA256("molr.context-node:v1\0" + parent_id_bytes + canonical_message_json)
```

The parent node uses 32-byte binary, and the message is deterministically JSON-encoded: object keys are sorted, numbers do not undergo floating-point conversion, and distinctions are maintained between string content, field presence, empty lists, and null. Roles, tool calls and associations, attachment references, and vendor status all participate in identity calculation; body whitespace is not trimmed. Identical hashes are treated as identical content; old content is not read byte-by-byte for comparison, and truncated hashes or collision buckets are not used.

`Intern` calculates the candidate prefix identifier, first checking if the tail node exists; on a miss, it performs a binary search for the longest existing prefix and inserts only the remaining messages. The transaction invariant that parent and child nodes exist simultaneously guarantees monotonic existence. `Append` supports appending messages directly from a known parent node. Both must establish persistent references within the same write transaction; unreferenced new nodes cannot be used as return values for cross-transaction dependencies.

Messages can only be reused under the same parent node. Reuse of physically identical content is allowed across assistants and accounts, but business references are bound separately to `OwnerID`, `AssistantID`, purpose, and record ID. Public reads first verify the owner and permissions of the business record, then restore the context via the corresponding reference; holding a node identifier does not grant access permissions, nor does it expose deduplication hits from other accounts to clients.

## Documents and References

`context.objects` stores message nodes, shared content blocks, and content-addressed documents. Documents replace the complete message arrays in `Inputs`, vendor `messages` / `input` with path slots; slots reference the tail message node and message count; tool definitions and automatic context state are reused separately as content blocks, while other request parameters and general details are saved with the document. Documents are also content-addressed; identical documents are reused as a single instance. Actual vendor requests are stored independently and are not generated by guessing from logical context after the fact.

`context.references` stores external references with account/assistant boundaries, and `context.counts` separately stores the inbound reference count of objects to avoid rewriting message bodies when updating counts. Inbound references include documents referencing message tail nodes and shared content blocks, child nodes referencing parent nodes, and business records referencing documents. Reads check content hashes and path lengths, returning errors upon detecting corruption; this validation is used to detect storage corruption and does not guarantee detection of real hash collisions.

Message chains are read via `Ancestors` operations in the persistence layer. SQLite uses recursive CTEs with a depth limit, returning nodes from tail to root in a single SQL query, after which the application layer validates hashes, parent chains, and counts node-by-node and restores the order. Each message chain has a maximum of 1 million messages; writes and reads use the same limit; missing nodes or corrupted paths return errors and do not degrade to empty context. References, documents, and shared definitions are still read independently; there is no in-process read cache here.

Reference replacement and business metadata are committed in the same transaction; execution state becomes effective only after old reference release, new reference establishment, node insertion, and checkpoint version checks all succeed. Transaction failures must not leave visible half-contexts, nor prematurely delete old recovery states.

## Agent Recovery

The official runtime only reads the independent storage format and does not automatically migrate embedded old contexts. Old deployments must stop, back up, and complete a one-time offline conversion before starting this version; temporary tools and local upgrade records are not part of the Runtime release artifacts.

Current checkpoints, model call retry inputs, and dreaming execution progress use their respective persistent references. Disabling `debug.enabled` does not affect the saving of these core states. When core context cannot be written, the Agent must stop advancing; if external tool operations have been issued, continue using operation receipts and unknown result handling, and do not blindly resend due to save failures. Model outputs do not have a separate recovery cache; outputs not entered into checkpoints are allowed to be re-requested via new attempts, while the costs and unknown states of the original attempts are retained independently.

The first model call also loads inputs and tool definitions from persisted canonical encoding snapshots, ensuring that retries and restarts do not change request bytes or idempotency digests due to changes in JSON object key order. After the request completes, input references are retained until the completion/handover transaction for that event; completion, stop, and reset release retry references no longer used for recovery. Dreaming progress is released after batch commit or stop. The current checkpoint always retains an independent reference.

`agent.handled` only saves idempotency result metadata and no longer copies full historical checkpoints. Pre-compression inputs are retained separately by the current checkpoint, summary requests, and collected workbench records; no permanent full context archives are created; old branches can be reclaimed after all these references are released. Compression failure does not replace the current input.

In-memory execution progress carries pending tool evidence. Checkpoint saves read only the header to validate owner/assistant identity, the storage marker, and the expected sequence, then construct the new context from in-memory inputs, cursor, and evidence. Failed saves leave the caller’s progress unchanged. Preparing a new turn and recovering still load the full context and validate message chains; handoff refreshes pending evidence. Unchanged saves preserve the sequence, timestamp, and workbench revision. Encoding and content hashing of the new context remain part of the write path.

## Workbench and Reclamation

The workbench first desensitizes according to existing rules, then writes details to independent historical references; runtime original text is not modified by workbench desensitization. JSON strings without sensitive information retain original whitespace and key order to reuse the same message nodes; strings are re-encoded only when actual desensitization occurs. When reading the latest checkpoint, restore first, then desensitize the output. `debug.payloads` only saves collection status and storage markers; detail bodies are restored on demand in shared storage. Model completion events save context references containing output messages; when reading details, extract bodies, tool calls, and backend status; list summaries are still stored separately. Raw HTTP/SSE responses do not enter the database. Historical cleanup cannot delete messages still referenced by current checkpoints or pending recovery operations.

The workbench retention policy only includes account-level execution count `MaxRuns`, covering normal executions and dreaming trajectories. When the limit is exceeded, completed executions are deleted from oldest to newest by start time, first revision number, and ID; running executions are retained until completion; new details are not rejected based on days or total detail capacity. The collection size guard for single debug details is still controlled by `debug.max_payload_bytes`.

Deleting historical records only releases corresponding references. After Runtime startup and periodically in the background, orphan reclamation is executed: up to 200 objects per batch, with a 2-second limit per batch transaction; if a batch is full, continue after a 1-second interval, otherwise check every minute. Only objects with zero inbound references are deleted; after deletion, decrement the count of the parent node or message node it depends on. Reclamation and reference updates share write transaction boundaries; reclamation failures roll back and retry later, without affecting committed executions. This mechanism does not guarantee physical shrinking of the database file, nor does it provide hard disk capacity guarantees.

## Usage Statistics

The personal usage page displays the set of objects reachable by all business references of this account: traverse documents, message parent nodes, and shared content blocks, deduplicating by object ID within the account. The admin usage page displays global statistics for all stored objects; cross-account shared objects are counted only once, including objects waiting for background reclamation; it does not change with member filtering. Each statistics calculation uses the same read transaction. Personal statistics read document IDs from references, then traverse reachable objects in batches using only types, edges, and original byte sizes, served from covering metadata indexes without loading message bodies; global statistics aggregate raw JSON byte counts and message node counts within the database, without reading object bodies into the Runtime.

Both display the total JSON body bytes of objects and the number of unique message nodes; this does not include indexes, reference metadata, or SQLite free space, and is not equivalent to the database file disk size. The account scope only includes data still referenced, while the global scope includes data not yet reclaimed, and accounts can share data, so account usage cannot be summed to derive global usage.

## Validation

`internal/contextstore` tests cover deterministic encoding, cross-account physical reuse and reference isolation, branch reclamation, concurrent references and reclamation, transaction failures, append identity, longest prefix binary search, and storage growth of continuous snapshots. Agent and Runtime regressions cover checkpoint version conflicts, compression, reset, tool return recovery, model retries and restarts, persistence failures blocking model calls, and reading the latest context after workbench cleanup by count.

Read performance can be retested using `go test ./internal/contextstore -run '^$' -bench BenchmarkContextRead -benchtime=10x -count=3`. Benchmarks compare sequential reads with recursive reads, including message JSON decoding and content hash validation; measure repeated reads on the same connection and the first read after reopening the connection separately, excluding connection initialization time. The OS file cache is not actively cleared, so the latter does not represent cold disk performance, nor is it the duration of a full Agent turn or usage statistics interface.

Global usage aggregation can be retested using `go test ./internal/contextstore -run '^$' -bench BenchmarkGlobalContextUsage -benchtime=1x -count=3`. Benchmarks include 1000 objects each with a 16 KiB body, counting only the statistics read phase.

Account usage can be measured with `go test ./internal/contextstore -run '^$' -bench BenchmarkAccountContextUsage -benchtime=3x -count=3`. The benchmark contains 6000 document references and a shared message chain with 4 KiB message bodies, and verifies deduplicated byte and message counts.

Checkpoint save performance can be measured with `go test ./internal/agent -run '^$' -bench BenchmarkCheckpointProgress -benchtime=3x -count=3`. The SQLite benchmark covers different message counts and body sizes, unchanged saves, forced saves, and 16 consecutive tool steps (32 saves), including the full `saveProgress` reads, encoding, and transaction. Each tool-step iteration starts from the same history length; model and external tool calls are excluded, and debug collection is disabled.
