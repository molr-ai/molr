# Development Workbench

The workbench is located at `/#/workbench` in the existing WebUI, sharing login, Runtime connection, and component libraries. The main navigation allows viewing executions for all assistants. The "Debug this assistant" option in the chat's more menu opens `/#/workbench/<assistant_id>`. The current turn information popup in chat messages also provides an "View in Development Workbench" entry, which uses `/#/workbench/<assistant_id>?turn=<execution_id>` to locate the current execution, automatically loads the starting record of the target turn based on the cursor, pauses following, selects the turn, and opens the trigger snapshot. Refreshing retains the location target; multiple execution attempts for the same turn locate to the earliest retained attempt. A clear prompt is displayed if the target was not collected or has expired. This is displayed only when both the deployment capability and the personal toggle are enabled. Dream failure notices open the corresponding assistant’s info overview for duration settings. Background execution failure reminders use `/#/workbench/<assistant_id>?event=<event_id>` to locate the trigger event, selecting the earliest retained attempt for the corresponding turn based on the `EventID` of the retained Run, reusing historical pagination location and uncollected prompts. The `Source.ID` in notifications is the event ID and cannot be treated as `ExecutionID`. Chat banners, Toasts, and desktop notifications provide workbench jumps only when both the deployment capability and the personal toggle are enabled; when disabled, reminders and close actions are retained, and the Toast entry updates with the toggle. General settings provide a "Show Development Workbench" toggle; if the Runtime capability is not enabled, the toggle is disabled, and the server rejects forced enabling.

## Collection and Entry Display

The deployment configuration `debug.enabled` is the sole collection switch, disabled by default. When enabled, new executions are collected for all accounts, including those that have not opened the workbench or saved personal settings. The "Show Development Workbench" setting in General Settings (`Settings.WorkbenchVisible`) only controls the display of entries in navigation, chat menus, current turn information, and notifications; it does not affect collection, debug interface permissions, or real-time connections for already opened pages. When the entry is hidden, access is still possible via existing links. After enabling display, previously collected records within the retention scope can be viewed; uncollected or expired content will not be backfilled. Disabling the deployment switch stops collection and prohibits access to traces, details, checkpoints, and notification streams, but does not immediately delete existing records. The deployment switch cannot be modified via the WebUI.

```json
{
  "debug": {
    "enabled": true,
    "max_runs": 1000,
    "max_payload_bytes": 4194304
  }
}
```

By default, each account retains a maximum of 1000 executions, with the count shared across all assistants under the account, including dreaming executions. Administrators set the execution count limit (1–10000) in "Admin Settings → Development Workbench"; leaving it blank uses the deployment default. The policy is persisted, overriding the default values in the deployment file, without requiring a restart; saving uses version checks and idempotency keys, taking effect during subsequent collection writes and at the end of executions.

When the count limit is exceeded, completed executions are deleted entirely from oldest to newest based on start time, first revision number, and ID; running executions are retained until completion, potentially temporarily exceeding the limit. Retention days, total detail capacity, or minimum retention counts are no longer set, and new details are not skipped due to old detail occupancy. Deleting metadata simultaneously releases the detail references for that execution; shared contexts continue to be retained if still used by business checkpoints or other historical records, and are reclaimed by the background after the last reference is released. See [Context Storage](context-storage.md) for details.

The workbench does not persistently display the retention policy. When cleanup actually occurs for the current assistant, "Earlier events have been cleaned up" is displayed after loading to the start of the trace; hovering, focusing, or tapping on mobile displays the count policy at that time; if no cleanup has occurred, "No earlier events" is displayed. Subsequent setting changes do not rewrite existing cleanup events.

The limit for a single debug payload is still controlled by the deployment configuration, defaulting to 4 MiB. Over-limit payloads are marked `too_large`, and execution records are marked as incomplete; collection no longer stops at 1000 steps per execution. Failure to write core business context stops Agent progression; optional debug collection failures only mark the record as incomplete and do not retry business operations. Service startup marks running traces left by the previous process as interrupted.

Count checks and step records are in the same transaction, and execution counts are aggregated by account within SQLite. Historical bodies are not loaded when the limit is not exceeded; over-limit candidates are read in batches, with a maximum of 200 per batch. Detail references, summaries, run records, and cleanup policy snapshots are updated in the same transaction; rollbacks do not leave partial cleanup results.

## Pages and Records

The workbench defaults to displaying continuous traces across Runs per assistant. When entering from the main navigation, the first active assistant is selected (if no active assistants exist, the first assistant is selected); switching is also possible via the assistant selector, which lists only active assistants; opening a departed assistant via existing links and the behavior of already opened workbenches remain unchanged, and chat menus still directly locate the corresponding assistant. A Run represents an execution attempt for a single trigger event; retries with the same ExecutionID are merged into one turn in the interface, displaying only one trigger message and axis trigger marker, with the turn status taking the latest attempt. Each request still retains independent Run ID, duration, result, and details, and raw events are not merged. Collapsing a turn collapses all retries; selecting any call from the axis expands the belonging turn and locates that call.

The page uses a compact event table: the top merges assistant selection, connection status, and context entry; below the title and above the axis overview, a row of controls is arranged: on the left, "All / Model / Tool" reuses the minimalist underline style and height from the Resources and Plans pages; on the right, in order, are Raw Events, Follow Latest, and Search Box; the Raw Events and Follow buttons share size and spacing, with status emphasized by primary color text, font weight, and icon line width when selected, keeping the background transparent; on mobile, they are displayed as icons with accessibility names. The "Continuous Trace" title and execution/call statistics are removed; a single border is retained between the control row and the axis, and the axis no longer displays the "Time Overview" text. The list and detail areas follow the bottom separator line of the timeline or waiting execution area; event rows are separated only by the bottom of the row, with an additional separator line at the bottom of the start prompt to avoid missing lines for the first event or overlapping lines for adjacent events. The list removes the column header row; execution numbers are displayed directly as integers without leading zeros; records are still aligned by type, content, status, and duration. Normal requests do not display attempt counts or HTTP status; only retry requests are marked "Retry 1/3"; first requests are not marked; when a maximum of 4 attempts is made, subsequent ones display "Retry 1/3", "Retry 2/3", and "Retry 3/3" in order. Full request counts and HTTP status are retained in the details. Turn separators display execution numbers and trigger times, with retries marked separately; mobile uses two-line records and independent list scrolling. Tool summaries are displayed according to tool meaning: sending messages displays the body (if no body, displays the card title or attachment count), reading chat history displays the actual returned count, file operations display the path, command execution displays the command, memory search displays the query, and plan operations display the title or action. Read counts are calculated only from successful results; during execution, failure, or missing results, only the operation name is displayed, and the limit is not treated as the read count. The list and hover share the summary, and search includes these visible summaries; full parameters and results are still viewed in the side details.

Model calls between context compression start/end records are displayed as "Context Compression" in the trace list and timeline; the classification remains model call, with duration, status, details, and filters unchanged; identification is based on loaded compression boundary events.

The upper overview sequentially displays three tracks: Trigger, Model, and Tool. Trigger markers include user messages, plans, operation completions, and recovery requests, positioned using recorded execution start times; clicking locates the corresponding turn and opens the trigger snapshot. The duration axis displays duration and idle intervals based on actual start and end times; neither mode displays the bottom horizontal axis, and specific times can still be viewed in hover and range panels. The event axis assigns equal-width positions to each trigger/call based on collection order, not expressing duration. Both modes support click location, drag selection of intervals, and zooming. The range panel reuses the component library `RangeSlider`, dragging two handles on the same track; the duration axis displays the time range, and the event axis displays the event sequence range; Tab, arrow keys, and Home / End can also be used. Event ranges are saved by record identity; loading earlier history or appending new records does not automatically switch to other calls; switching coordinate modes clears the original range and zoom. The virtual list below continuously displays each execution, with model and tool calls aggregated by OperationID within the Run for start/request/response/completion steps, and tools can be collapsed with their belonging model calls. Records directly display tool names, parameter/result summaries, or model outputs; "Show All Events" switches to raw steps such as budget, permissions, and checkpoints. Search only matches loaded names, statuses, and summaries, not unread full payloads; time filters also only cover the loaded range.

Dreaming events reuse normal model call details; batch information and memory organization results are placed only in the "Overview" content area, scrolling with the content; other tabs do not attach the dreaming panel. The "Overview" distinguishes new memories, new memories pending confirmation, modification suggestions, and discarded items. Modification suggestions display the original text and suggested content saved at submission; before confirmation, this does not indicate that the original memory has been modified; subsequent memory edits do not rewrite this historical original text.

On desktop, selecting a record opens the right-side details; on narrow screens, details cover the trace area and can be closed. Details prioritize displaying input and output, collapsing event ID, connection, and operation status into "Call Information"; call context, diffs, provider requests, response content and metadata, costs, and raw data are still viewable. The independent "Latest Checkpoint" and historical call context are separated, retaining stop execution and reset context operations.

Initial loading fetches the latest 100 steps; clicking "Load Earlier Traces" paginates history, maintaining the current reading position. Following the bottom is enabled by default; scrolling up, selecting records, collapsing, or filtering pauses following; re-enabling following clears filters and returns to the tail. New records are supplemented via cursor, ensuring that even if more than one page is exceeded during disconnection, not just the latest page is retained. Each refresh synchronizes the retention scope, removing cleaned-up runs.

When a call lacks a start record, it is marked as not loaded; when a call lacks an end record, the estimated completion duration is not displayed; interval duration is calculated only when both start and end exist. The latest context reset uses the reset time saved by the Runtime to display the boundary, not inferring earlier resets from historical conversations. First token latency, generation throughput, token-by-token updates, and uncollected history are unavailable.

Records include trigger events and assistant configuration/permission snapshots, checkpoint loading, context construction, available tools, full logical context before model calls, budget validation snapshots, model permission checks, sanitized requests, HTTP response metadata, model output references and usage, tool parameters and results, final context, and checkpoint save results. For normal execution progress, if the full recovery status and execution/event identity have not changed, saving is skipped, no checkpoint event is generated, and version or save time is not advanced. Model call completion, turn end, user stop, and context reset retain forced save records. Each successful checkpoint save collects only the version number, previous version, save time, reason, context raw byte count, and `ContextOmitted=true`, no longer copying the full checkpoint to each debug event. Execution recovery still persistently saves the full latest checkpoint; historical model inputs, requests, and current turn start/final context snapshots continue to be collected. Intermediate save events do not provide the full context or diff at that moment; the UI explicitly points to the model call context and the latest checkpoint. Old records retain their original format and can still be read. Budget snapshots include limits, used and reserved occupancy, required amount, cycle, and conversion rules. Amounts retain the original currency, and display reuses the multi-currency component.

One event can have multiple execution attempts. Each attempt has an independent Run ID and is associated with the original EventID, logical ExecutionID, Attempt, OperationID, and Receipt, facilitating identification of each request and retry. Idempotent replays of processed events do not generate false new model calls.

The context panel displays character proportion progress bars for system / assistant / tool / user in historical calls and the latest checkpoint. Estimates are based on Unicode character counts of message bodies, tool names, and parameter values; message encapsulation, parameter field names, punctuation and escapes added by JSON serialization, attachments, tool definitions, or backend-specific status are not counted. Tool calls are categorized under assistant, and tool results under tool; roles follow the actual context; new trigger events and Runtime notifications use user, and base instructions use system. This ratio is not token usage. The chat interface no longer displays the context usage and compression count line.

The context view displays the actual `model.Input` roles, content, tool calls, and tool returns; the model request view displays the serialized provider request body and model configuration. Tools and session history only appear in the corresponding snapshots if they actually enter the request. Message diffs compare adjacent model calls; the first call is compared with the loaded checkpoint. Internal reasoning not returned by the model is not observable data, and uncollected historical requests are not reverse-generated.

Newly generated automatic context, control, recovery, verification, handover, and urgent notifications directly use user; identified Runtime notifications in old checkpoints are migrated during continued execution/request projection. Previously, the workbench "Call Context" recorded the internal role before adapter conversion, so there might be multiple system entries, while "Model Request" already has only one system entry at the beginning. Historical traces and checkpoint loading snapshots retain the raw data at the time of collection and are not rewritten after upgrades.

Backend-specific status returned by the model can be expanded and viewed in context messages, including raw payloads and their belonging protocol, Provider, model, and endpoint. Actual return rules are determined by the [Model Adapter](model-adapters.md); retaining status in checkpoints does not mean the current backend will accept that status.

## Runtime Implementation

Credential field identification reuses the read-only field name replacer, uniformly removing underscores and hyphens and converting to lowercase; the replacer can be used concurrently by multiple collection tasks. Each collection still independently parses and sanitizes payloads, not caching business content. Nested JSON objects and arrays in strings allow leading spaces, tabs, carriage returns, and newlines; internal sensitive fields are still recursively sanitized; JSON strings that do not require sanitization and have no extra trailing content are preserved verbatim. Text credential patterns, depth, and size limits continue to apply.

`internal/debugtrace` is a fixed module in the monolithic Runtime, using existing transactional storage: `debug.runs` saves run and step metadata, `debug.summaries` provides lightweight list and retention policy indexes, `debug.payloads` saves collection status and shared content reference markers, full details are restored on demand by `contextstore`, and `debug.revisions` provides real-time notification cursors. Summary writes persist `UpdatedRevision`, and `debug.summary_resets` stores the account revision of the last actual cleanup. These markers commit in the same transaction as the corresponding writes or deletions, without retaining a per-item deletion log. `debug.cleanup` saves the latest cleanup event by owner and cleaned assistant, in the same transaction as actual deletion, not saving deleted private content. Agent Loop, model adapters, and budget modules record data through optional observation entries. Debug read interfaces are separated from business execution interfaces; the workbench cannot forge run identities, tool calls, or settlement credentials.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/status` | `workbench_available` indicates deployment capability |
| GET | `/api/debug/retention` | Effective policy and current account usage, unaffected by personal display toggle |
| GET / POST | `/api/admin/debug/retention` | Admin reads/saves installation-level retention policy |
| GET | `/api/debug/trajectory?assistant_id=&limit=&cursor=&after=&runs_cursor=` | Lightweight trace pagination across Runs and incremental supplementation |
| GET | `/api/debug/runs?assistant_id=&limit=&cursor=` | Paginated execution list |
| GET | `/api/debug/runs/{id}` | Timeline metadata |
| GET | `/api/debug/runs/{id}/steps/{step}` | Selected step payload |
| GET | `/api/debug/assistants/{id}/checkpoint` | Latest checkpoint |
| POST | `/api/debug/assistants/{id}/context/reset` | Reset private run context for specified assistant |
| GET | `/api/debug/stream` | Independent real-time notification stream |

The trajectory interface returns `Items` (RunID and step metadata), `Runs` summaries with their synchronization state `RunsReset` and `RunsCursor`, `NextCursor`, `HeadCursor`, and `ContextResetAt`, `Cleanup` for the specified assistant (the time of the most recent actual cleanup `At` and the policy snapshot `Policy`, or `null` if it has not occurred). Full context and request bodies are still read on demand via the step details interface. `limit` defaults to 50, with a maximum of 200: reading the latest page without a cursor; `cursor` reads earlier pages forward; `after` appends updates in collection order. These two cannot be used simultaneously. Items on each page are arranged from oldest to newest; during real-time backfilling, continue using NextCursor until it is empty, then retain HeadCursor to wait for the next notification.

Summaries synchronize independently through `runs_cursor`. Omit it on the first request to receive the full retained list with `RunsReset=true`. Send the last `RunsCursor` on every subsequent request, including older pages and live backfill pages, and merge changed `Runs` by Run ID. Completion and restart recovery update summary revisions even without new steps. After actual cleanup, the server returns `RunsReset=true` with the full retained list; clients replace summaries and remove loaded steps belonging to expired Runs. Summary cursors are bound to the account and assistant, do not replace authorization, and are independent of the step `HeadCursor`/`NextCursor`. Summaries, steps, cleanup markers, and both cursors share one read transaction. Idle incremental responses neither read nor send unchanged summaries, and clients reuse their existing arrays to avoid recomputing the trajectory. Initial snapshots and post-cleanup reconciliation still read the full retained list; historical step pages retain their existing candidate scope.

Cursors are bound to the owner and assistant filters, allowing pagination to continue even after records are removed by the retention policy. Newly collected steps hold an incrementing revision number generated within the same transaction, avoiding missed reads due to identical timestamps or system clock rollbacks; old records are sorted by time, Run ID, and step sequence number. The tool semantic summary `Summary` is extracted from the saved fully sanitized payload before truncation, returning text or the actual number of result items, without loading extra details for the list. Step summaries are generated only from sanitized content; tool names are limited to 80 characters, and summaries to 240 characters (truncation appends an ellipsis). No summary is generated for payloads that exceed limits or are unavailable. For old records, summaries are extracted from saved payloads based on the current request page, without replaying external requests. Run summaries maintain the first and last revision numbers, allowing real-time reads to skip runs with no new steps.

The notification stream sends only record revision numbers, not context. Clients refresh lists, timelines, and selected payloads on demand, supporting `Last-Event-ID` for resuming after disconnection. It shares connection count limits and write timeouts with the standard event stream.

The workbench notification stream listens for committed version changes per owner; notifications are not sent for transaction rollbacks. Idle connections do not periodically query versions or identities, sending only keep-alive comments every 10 seconds. Account changes, session/token revocation, and credential expiration trigger identity checks; current identity and debug read permissions are still verified before sending a new version. Upon connection reconstruction, the current version is compared with the client cursor, and the client then reads the persisted trajectory.

Only the current owner's session or an owner token with the `debug.read` scope can read. Assistant identities cannot read; all data queries are bound to the owner. HTTP request credential headers are not logged; explicit credential fields, Bearer values, and identifiable keys are stripped before writing. The context itself contains user private data and cannot reuse standard chat SSE for external broadcasting. Currently, observation, historical positioning, execution stopping, and context resetting are provided; single-step debugging, arbitrary context editing, and re-execution are not yet provided.

## Reset Context

Select an assistant, open "Latest Checkpoint", click "Reset Context", and confirm. The confirmation window displays the assistant name and scope of impact; assistants without checkpoints can also be reset. Departed assistants cannot be reset.

The request includes `Mutation.IdempotencyKey` and the required `ExpectedSequence` (0 if there is no checkpoint). The server requires the workbench deployment switch to be enabled; personal display settings do not participate in authentication, and owner and assistant write permissions are verified; tokens also require `debug.write`. If the checkpoint changes during confirmation, a conflict is returned, requiring a refresh and re-confirmation.

Within the same transaction, current and queued old executions are canceled, an empty context is written, the checkpoint sequence number is incremented, the assistant's waiting reason is cleared, and reception of new events is resumed. The reset time also prevents late-arriving old events from executing again; active model requests are canceled, and old executions cannot overwrite the new checkpoint. Resubmitting the same idempotency key will not clear context generated later.

Chat history, long-term memory, assistant configuration, permissions, budgets, schedules, historical debug records, and cost evidence are all retained. Resetting does not mark business tasks as complete, nor does it release cost reservations for results that have not yet been verified; already issued external requests may still produce effects or costs. The reset itself does not call the model; new execution begins only after the user sends a new message or a subsequent schedule triggers it.

### Content Preview

The selected background and left-side marker for user message turns cover the entire row (including the collapse button and details entry), consistent with model and tool records. The left-side marker and timeline share type and status colors: trigger is neutral, model is model color, tool is tool color, and failure is error color.

The trajectory list is used for quick positioning: user messages and turn information are displayed on the same line, while model outputs and tool inputs use single-line truncated summaries, with tool results retained in the details. Time labels reuse formatters based on the current language and account timezone; scrolling and expanding records do not recreate them; time, retry time, and reset markers are updated when preferences change. Desktop record row height is 44px, and mobile call row height is 64px; clicking a user message or call record opens the details, while the left arrow separately controls collapsing. The rightmost arrow directly opens full details, reading collected payloads on demand; long content scrolls within the details. The details panel is located only in the record area below; when opening, switching, or closing, the width and position of the timeline above remain unchanged; on narrow screens, the details overlay the list below, but the timeline remains usable. The virtual list maintains the reading position when backfilling history.

New runs collect user input or the plan content of the corresponding version at the start, saving it independently from the actual model input, and adhering to credential sanitization and payload size limits. In run summaries, the body is limited to 1000 characters and the title to 128 characters; full content is saved in the starting step. For old records lacking snapshots, association is made only within the owner and assistant scope to the original message or plan of the same version, labeled "Associated with original content"; if the source is deleted, the plan version differs, or it was not collected, it is explicitly marked as unavailable, without using current plan content to impersonate historical snapshots.

Parameters, structured results, context, context diffs, model requests, response metadata, and raw data in full details uniformly use the shared `CodeBlock` to display JSON highlighting; regular body text retains text display. Code areas support line wrapping, scrolling uniformly through the Tab content area; oversized payloads fall back to full raw text, adhering to existing collection and sanitization rules.

Model responses use small-sized segmented Tabs to distinguish outer navigation, opening "Response Content" by default, sequentially displaying the actually returned thinking (if any), content, and tool calls; rejection explanations are also retained. Thinking and content can be collapsed separately, with thinking collapsed and content expanded by default. Completion events hold a context reference containing the output message; when reading details, the body, backend status, and tool calls are extracted from the last assistant message, without saving pre-computed results separately. Workbench summaries are still saved independently for lists and search. During workbench cleanup, detail references are released; messages still held by the current checkpoint are not reclaimed.

"Response Information" displays HTTP status, Content-Type, and completeness, but does not provide raw HTTP/SSE response bodies. Raw responses are written to rotating file logs only after the deployment configuration `diagnostics.model_responses=true` is enabled; this is disabled by default and is independent of the workbench collection switch. If the call is interrupted or the full output is not collected, it is explicitly marked as unavailable, without attempting to recover output from partial SSE.

The details panel no longer provides a "Raw Step" entry. "Raw Data" displays the data of the currently selected record in the trajectory; switching detail Tabs does not change the selected record, overview, or title. To inspect other steps, enable "Show All Events" in the trajectory and select the corresponding record.

Event details use a fixed title and Tab navigation, with an independently scrolling content area. The overview groups body, tool calls, usage, and call information, placing long IDs in call information; context is grouped by message sequence number, role, and source, with role proportions displayed in one segmented bar in the fixed order system, tool, assistant, user, with distinct colors and matching dots in the legend below showing each role’s percentage and character count (including zero usage), and the JSON and description of the Runtime context snapshot displayed separately. The diff page summarizes the counts of unchanged, removed, and added items; model requests separate configuration and request body, and response information displays HTTP status and completeness. Raw data retains full JSON, and all views share title, spacing, collapsible area, and empty state styles.

Body and code blocks in the details do not limit height and do not provide separate vertical scrolling, scrolling uniformly through the Tab content area. Request bodies, response bodies, raw data, inputs/outputs, tool calls, and non-empty diff blocks are all collapsible, expanded by default; thinking remains collapsed by default, and content is expanded by default. Context messages retain their respective collapse controls.
