# Frontend Interaction Conventions

Maintain shared navigation, form, notification, and feedback behaviors across themes. For component properties and examples, see [Component API](../../../../packages/ui/COMPONENTS.md).

## UI/UX Standards

- Keep page copy only when it helps users understand the current state, make a decision, or complete an action. Remove unhelpful copy and avoid excessive or lengthy descriptive text.
- Follow the [design system](design-system.md) and these interaction conventions. Prefer shared components and established page patterns, keeping action entries, interaction feedback, layout, spacing, and visual treatment consistent across similar pages.

## Overlays and Panels

Conditionally rendered dialogs and drawers use shared `ModalPresence` to remain mounted until exit finishes, including settings forms, confirmations, resource permissions, plans, memories, plugins, and identity verification. Closing must not clear the body early. Permanently mounted Dialog / Drawer components retain their title and contents during exit. Nested modals close independently; closing a parent waits for its children. Docked chat panels retain their width animation, while modal panels use the shared exit lifecycle. Forms, subscriptions, and modal restrictions are released and focus is restored after exit; reduced motion completes immediately. Page navigation cleans up directly.

The chat plan panel switches horizontally between its list and details within the same drawer, reusing the standalone plan page’s detail rendering and styles. The header back button restores the list and the original item’s focus while preserving list scroll position. The inactive view is inert and hidden from the accessibility tree. Details remain mounted during the return transition; system or account reduced-motion preferences switch views immediately.

In the default desktop assistant page, the shared `@molr/ui` `PaneSeparator` handles pointer capture and keyboard resizing within the existing 8px card gaps. `useAssistantPaneSizes` saves list and per-kind panel widths in localStorage scoped to the browser origin and account, on pointer release or keyboard adjustment. Minimum widths are 224px for the list, 360px for chat, 320px for tasks/running tasks, and 360px for other panels. ResizeObserver constrains the displayed layout without overwriting saved preferences when the window shrinks; docking continues to measure the stable outer workspace. Floating panels and mobile keep their respective layouts. `assistant-pane-resize.spec.ts` covers dragging, keyboard control, reload restoration, independent panel widths, and narrow viewport bounds. Switching docked panels animates from the previous panel’s actual width to the saved target width, with a content transition even for equal widths. Dragging and viewport constraints apply immediately, and reduced-motion settings disable transitions. Switching again during an animation continues from the current visual width.

Without active sessions, the terminal uses the same regular header spacing and button sizes as the files and browser panels. Only active sessions use the compact tab strip.

The mobile bottom navigation retains only business pages, using a floating rounded rectangle style with shadows. The selected item expands to show text, while others display only icons. Transition animations respect the "reduce motion" setting. The menu overlays content that fills the viewport. At the end of scrollable content on each page, space is reserved for the menu height, vertical spacing, and the device's bottom safe area, ensuring the last item is fully visible when scrolled to the bottom. On mobile, the status bar for Plans and Workbench scrolls with the content. The empty state of the plan list fills the available height, while the calendar maintains its full grid height. The status bar is positioned between the end of the content and the menu's reserved whitespace. Isolated plugin iframes shorten their own viewport to avoid content occlusion. When entering chat details, the menu fades out downwards; when returning to the assistant list, it fades in upwards. Interaction with the menu stops immediately upon exit initiation. Quick returns can reverse the transition from the current progress. If the system or account has "reduce motion" enabled, the switch is immediate. The default theme provides a chat back button. When opening the mobile chat panel and returning to the list, an in-place opacity transition is used, unmounting after the exit completes. Interaction is disabled during the exit. If "reduce motion" is enabled, the switch is immediate. Desktop chat does not use this animation. The entry for hiring a new assistant on mobile is located to the right of the search button, using an icon-only ghost button. The desktop version retains the entry at the bottom of the list.

The default theme displays the user avatar and username in the original Logo position. Clicking this entry opens User Settings. Admin Settings are accessed via a button in the top-right corner of the User Settings page header; this button is not shown to regular members. The Admin page header allows returning to User Settings. Each row’s Settings button opens a shared Dialog for proxy settings, loading the configuration on demand. Saving closes the dialog and shows feedback; cancellation or Escape discards the draft and restores trigger focus. On narrow screens, the form unmounts after the drawer exit animation; reduced motion closes it immediately. About always shows the service version in browsers and the desktop version in the desktop app. “Version mismatch” and “Update available” tags can appear together inside the same clickable version entry, sharing its hover state and keyboard focus. Clicking anywhere in the entry opens version details, presented as a bottom sheet on narrow screens. The dialog leads with update status and actions; available updates show the current and target versions. Admins see one upgrade action based on service capabilities: “Update and restart service” when online upgrades are supported, or “Manual upgrade instructions” otherwise. Both retain release notes. Installation details load only after opening manual instructions, which provide a terminal command or deployment guide. Failed reads can be retried; loading and errors are not treated as lack of online upgrade support. A compact list below contains desktop app (when present), Runtime, and WebUI versions and commits, followed by consistency icons. Recommended versions and check timestamps are not repeated; cooldown appears only in the footer check button. Browsers compare WebUI and Runtime; the desktop app also includes its own build. “All component versions match” appears only when every component has the same version and commit. Otherwise, only mismatched component pairs or incomplete metadata are listed; unreachable services never show a match. Opening the dialog refreshes component versions and consistency. Its only footer action is “Check for new versions now”; when disabled, it shows the reason or the remaining cooldown in seconds. WebUI says “Updated with the service” and has no separate upgrade action. The default page contains the Logo and version entry, service information, and GitHub entry, without separate build information or service update sections. Version details contains update checks, release notes, desktop downloads, service upgrade instructions, and upgrade progress. Desktop and service checks respect their own cooldowns; one source being unavailable does not block the other. Failed checks retain previous successful information and show an error. The desktop checks the stable catalog independently, including from connection management while disconnected; development builds are not automatically compared. Version or commit differences are informational and do not block usage. A page/service mismatch offers a refresh action after saving input. Avatar dots lead to About: desktop and pending local updates are shown to desktop users, while new standalone service releases retain administrator-only avatar reminders. When the bundled Runtime is newer than the installed local service, the top shows both tags. The local service entry in version details and the connection manager show “Local service update pending”, the current version, and the target version. “Update and restart local service” requires native confirmation of task interruption before upgrading from the bundled package. Success reconnects and refreshes component status; the top continues to show the desktop version. Users can close the dialog and keep using the old service. Quitting or restarting the desktop does not upgrade it. Cancellation leaves it unchanged, failure permits retry, and downgrade updates are not offered. The Runtime name and address are placed in a separate "Service Information" group on the About page, located below the version entry. Device and login times are viewed on the Security page. Logging out of the current device uniformly uses "Log Out," and no separate connection settings page is provided. The top of the About page displays the Logo and current version side by side, with update status shown as tags. The GitHub entry is placed at the bottom of the page. Mobile maintains the same information order, with upgrade guides expanding on demand. After login, the host layer shares the update status, reading it every five minutes and when visibility/connection is restored. When the About page is active, it checks the release source according to the server-side cooldown policy. Page/service build mismatches show an entry marker for all members. Admins can view fixed-version upgrade guides generated from installation records. Pages are not automatically refreshed, and updates are not automatically installed. The full Logo uses `animation="daily"` and interactive mode, switching day/night cycles based on device local time and respecting the "reduce motion" preference. Profile reuses existing avatar selectors and thumbnail processing. Avatars saved to the account are displayed in the desktop sidebar, mobile top bar, and admin user list.

## Shared Components and Profile Synchronization

WebUI main navigation and assistant list regions use `user-select: none` with the WebKit prefix, excluding navigation labels, assistant names, and message previews from page-wide and drag selections in desktop and mobile layouts. Inputs and editable content inside these regions explicitly restore `user-select: text`, preserving text selection and Ctrl/Cmd+A in search fields. Chat messages and detail content remain selectable.

Chat history loads earlier messages through centered text between light divider lines, using the same color as list separators. When the distance from the scroll bottom exceeds one message-area viewport height (at least 600px), a floating “Back to bottom” button appears at the bottom of the message area without taking composer space or changing scroll height. The label changes to “New messages” when the conversation has unread messages. Returning clears search-message navigation and any pending pagination scroll restoration, immediately scrolls to the bottom, and resumes following the latest messages. Scrolling, message updates, and message-area resizing refresh the button visibility.

Desktop main sidebar buttons are uniformly 44px. Menu buttons have a transparent background by default, showing a rounded rectangle background on hover and selection. Search buttons and account avatars remain circular, with avatars and buttons being the same size. The Logo remains unchanged, and mobile continues to use the bottom navigation layout.

In the desktop App's wide layout, empty areas of the main navigation sidebar are native window drag regions. Buttons explicitly use `no-drag` to retain clicks and tooltips. These styles apply only to the non-mobile layout inside `.app-frame`; browser and narrow bottom navigation interactions stay unchanged. A full-window `no-drag` layer handles modal interactions. Shared floating panels, including Tooltips, explicitly use `app-region: no-drag` inside the App, while their transparent `::backdrop` uses `app-region: initial`. This prevents inherited sidebar drag styles from turning the whole window into a drag region, while preserving titlebar and empty-sidebar dragging. `app-tooltip.spec.ts` checks panel and backdrop drag styles, navigation clicks with visible tooltips, and keyboard interactions; native macOS clicks and window dragging still require desktop acceptance.

After saving an avatar or display name, account profile information is synchronized in the background to the current page and same-origin tabs, preserving workspace and connection. Login, logout, and identity switching still reinitialize the session.

Shared Tooltips in locations such as the sidebar close and clear delay timers when the window loses focus or the page is hidden. Restoring focus by switching back to the page does not trigger the tooltip; subsequent keyboard navigation or mouse hover displays it normally. This behavior is handled by shared components, so the host does not need to clear button focus. Tooltips share a set of window activity listeners. Keyboard and pointer presses only advance the input version; instances in the process of closing do not execute input callbacks individually. Shared listeners are removed when the last instance unmounts.

## WeChat Connection and QR Code

The "… → Switch chat channel" in the top-right corner of the chat page opens a standalone connection management modal. After binding, the bottom uses shared `ChatComposer.lock` to retain the input box outline, displaying only instructions for WeChat sending and unbinding to restore input. "Manage WeChat Connection" opens the same modal. Connected states use success `Alert` (`tone="positive"`) within this modal, while abnormal connection states requiring re-scanning use warning `Alert`. Proactive reminders for re-scanning follow general server-side notifications, displayed in the chat top queue. The assistant information page no longer includes connection operations.

WeChat connection QR codes use shared `--color-qr-foreground` / `--color-qr-background` tokens. All color schemes and light/dark modes maintain dark modules and light backgrounds, preserving the quiet zone for the four modules. QR codes are encoded locally in the browser, and login content is not passed to third-party image services.

## System Reminders and Display Boundaries

The connection notice and Logo represent the live subscription. A terminal error or a handshake taking over 20 seconds displays “Live updates unavailable. Retrying automatically.” and continues with backoff. Offline pauses retries; online, visible-page, focus and successful non-auth API signals can wake recovery. Automatic wakeups are coalesced and throttled without replacing an active stream. Only SSE `ready` hides the notice, plays recovery feedback and refreshes queries. API success does not mark live updates as restored. Confirmed session expiry stops retries and follows the existing sign-in flow.

The current chat is marked as read when the page is visible, the window has focus, and the reader is at the bottom of the conversation. Docked side panels do not pause this behavior. Dialogs and drawers that cover the chat pause it; closing, removing, or docking them triggers another check. Background pages, scrolled history, and search locations do not automatically clear unread messages. New-message alerts use the same panel obstruction rule.

The host layer `notifications/AssistantNotifications.tsx` provides a shared chat reminder queue. Reminders for WeChat delivery and connection anomalies, persistent assistant blocking, authorization requests, pending plan handovers, and task/background execution failures are generated by Runtime. Chat banners and proactive reminders share notification IDs. The client does not provide a standalone notification page or notification history list; long-term information is managed by the original chat, approval, plan, and task pages.

Chat displays one reminder at a time, selecting the next one in order of occurrence. New reminders do not replace the current one. Closing only acknowledges the current ID, advancing upon server success. Failure retains the current item and error feedback. After closing, keyboard focus moves to the close button of the next item. The reminder area has no internal scrollbar, but visibility of input and channel operations on short screens must still be checked. Brief model retry prompts are displayed only when there are no server-side reminders. Read status does not hide pending banners. Reminders are resolved by the server once the source issue is recovered.

Toast auto-dismissal and desktop notifications collapsed by the system do not automatically mark as read or ignored. Chat banners and Toasts for background execution failures display "View in Dev Workbench" only when Runtime supports it and the user has enabled the Dev Workbench, locating the execution based on the notification source event. Desktop notifications use the same target; no jump occurs if not enabled. Uncollected or expired executions are clearly indicated in the workbench. Viewing other reminders goes directly to the corresponding business page. View actions in chat and Toasts mark as read. Desktop notifications, sounds, and current browser settings follow existing device policies. Even if proactive reminders are not enabled, pending reminders within chat can still be viewed. New assistant messages continue to use session sequence numbers and read status. Proactive reminders for authorization request cards are handled by notification records to avoid duplicate pop-ups.

Use shared Toasts for errors and informational feedback by default. Use `useErrorToast` for request and operation failures and `useToast` for ordinary results and brief information, without taking up page layout space. Exceptions may stay in context: form validation next to its field, persistent connection state or paused terminal input next to the affected control, and connection test results or dream conflicts that need to remain available for review. An exception must need context or persistent visibility; implementation convenience alone is not a reason to use an inline Alert.

Closing feedback does not clear connection test results. Brief model retry progress, local network disconnection, privacy notices, and form validation are not written as persistent notifications. Use `DismissibleAlert` only for the contextual exceptions above when the prompt may be dismissed. Ordinary errors are distinguished by call site; rate limiting and service unavailability are deduplicated within the current session. After closing or auto-dismissal, background polling does not repeatedly pop up. Proactive actions can re-prompt. Prompts are cleaned up upon error recovery, source unmounting, or session exit. Service unavailability Toasts are suppressed when connection banners appear. Errors with retries persist. Rate limit retries respect Retry-After. Timing stops when the countdown expires or the prompt is closed.

## Browser floating window

Browser and terminal panels share `SessionStart` when no session is active, with consistent icon, heading, description, execution options, and start-action spacing. The content area scrolls independently. The terminal header shows its new-session button only while sessions exist; the empty state keeps one primary action. Loading, unavailable capabilities, and startup progress stay in context; ordinary request failures continue to use Toasts. When Full Access is selected, a shared warning `Alert` below the execution options persistently explains the service-account permissions and isolation/quota boundaries. It disappears when switching back to sandbox mode and has no separate dismiss action.

When starting a browser or terminal, a single available compute resource is selected automatically and the resource selector is hidden. Multiple resources show a selector. An ordinary grant selects sandbox mode; a Full Access-only grant selects Full Access and displays a warning explaining its permissions. When both are available, sandbox mode is the default and a mode selector is shown. Full Access uses the service account permissions without Molr file/network isolation or resource quotas; Chromium retains its own sandbox. Selections apply to new sessions. Close the current browser before changing resource or mode; website login state is preserved. An invalidated selection must be selected again, and revoking a running task's authorization ends that task.

The desktop browser defaults to a nonmodal floating window. It uses the shared Drawer's nonmodal mode to preserve the DOM, stream connection and control ownership. ChatSidePanel reserves no sidebar space while floating, and chat remains interactive. Docking follows the available-space rules; phones use a bottom drawer. Position and size live in page memory and survive closing and reopening the panel.

`useBrowserView` handles dragging, proportional resizing, arrow-key adjustments and viewport bounds. The page maintains the remote 1280×800 aspect ratio while browser chrome stays at its normal size. Sizing subtracts the measured chrome height and rechecks bounds when auxiliary input expands or the viewport shrinks. Pointer input maps the displayed image back to remote coordinates. `browser-panel.spec.ts` covers floating/docked transitions, chat interaction, aspect ratio, coordinate mapping, bounds and the phone drawer.

The bottom bar contains only connection status followed by the keyboard and end-session buttons. The bottom-right resize area is transparent, with no icon or hover background; it uses a resize cursor and retains an outline for keyboard focus.

## Workspace file explorer

The chat file button shares the single-panel selection with the browser. `WorkspaceFiles` uses Drawer and ModalPresence: a nonmodal desktop window, reserved ChatSidePanel width when docked, and a bottom drawer on mobile. `useFloatingPanel` handles independent dimensions, dragging, keyboard adjustments and viewport constraints; browser geometry retains its separate aspect-ratio constraint. Switching floating/docked modes preserves the component and draft. Per-assistant page memory retains directory, selection, scroll, sorting and hidden-file preferences.

Above 640px panel width, the directory and preview appear side by side; narrower panels switch between list and detail. Creation, renaming, moving, deletion and upload conflicts use shared overlays. Edit conflicts preserve drafts and offer reload or save as; ordinary failures use error Toasts. Application navigation and panel switching use the cancelable `molr:before-navigation` event to protect unsaved edits. Browser closing uses beforeunload; page memory also retains drafts for native history navigation.

`workspace-explorer.spec.ts` uses a real Runtime to verify desktop/mobile file operations, upload and version conflicts, and window geometry. Palette checks and screenshots remain in local internal records.

## Chat commands

WebUI parses `/compress` (`/压缩`) and `/permission approve|reject` (`/权限审批 同意|拒绝`) before sending ordinary messages; recognized commands are not submitted to the model. Approval uses the current assistant’s pending requests: no argument selects the first request in the API’s newest-first order, a complete ID selects an exact match, and `all` / `全部` freezes the pending set at submission. WebUI reloads the list and checks the selected IDs and versions; no-argument commands also require the newest ID to remain unchanged. Batch processing checks all proposals before sequential submissions through the existing resolve API with expected versions. Failure stops processing and reports the completed count; successful decisions remain and new arrivals are excluded. Permission cards expose copyable request IDs. Approval preserves the proposed resource, actions, scope, quotas, temporary quotas, and expiry for every grouped item. Missing resources or compute/network quotas require the review form. The server continues to validate ownership, state, version, and grant scope.

The shared `ChatComposerCommand.aliases` field declares completable aliases. Chinese matches complete to Chinese text; multiword commands allow spaces in filtering. The menu only completes text; the application parses and executes it.

## Sandbox compute status

Overview, connection tests and Compute share the controlled-compute state decision, checking disconnected, disabled and offline states before disabled execution or available/unavailable controlled compute. Controlled compute uses `Capabilities.Shell`; Full Access independently uses `Capabilities.FullAccess` and must not make controlled compute appear available. Offline snapshots do not advertise current availability. Unavailable compute hides requestable capacity and shows its cause and recovery steps. Compute cards and new ordinary grants follow capability availability, while existing grants remain viewable and revocable. Empty states provide storage, network or compute-specific guidance. Full Access keeps its own section describing the full storage, compute and network scope.
