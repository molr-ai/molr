# Runtime Module Public Interfaces

Updated: 2026-10-03. Status: The monolithic Runtime is connected to real implementations; see [Runtime README](../../../../runtime/README.md) for verification scope and adapter limitations.

"Public" refers to the exported interfaces of Go packages within the monolith, not third-party SDKs, nor does it imply that all methods are open to clients. The current packages are grouped by IM, Agent, Business, and Common Support, using fixed in-process calls; Go dynamic business modules are not loaded; plugins provide pages, themes, and HTTP tools via [controlled extension points](../extensions/plugins.md).

## 1. Common Invocation Rules

- Methods involving I/O or business operations accept `context.Context`, propagating cancellation and deadlines.
- Identity is generated by `auth` or trusted scheduling as `core.Principal`; HTTP requests or model parameters must not be decoded into trusted identities.
- Standard business interfaces check object ownership, token scope, and current permissions; Agent execution additionally binds assistant, execution, and operation identifiers. Structural validation does not replace these checks.
- Creation and significant changes use `core.Mutation` idempotency keys; updating existing objects requires version matching. Same key with different parameters returns a conflict, preventing duplicate external side effects.
- Lists use bounded pagination and opaque cursors; amounts use integer micro-units with explicit currency, avoiding floating-point amounts and unbounded result sets.
- Errors use `core.Code`; API mapping fixes public messages, not exposing underlying errors, credentials, paths, or internal stacks.
- `core.Secret` defaults to masking in both printing and serialization; only trusted adapters explicitly read them. Secret values do not appear in the Agent's model/tool interfaces.

Authorization, atomicity, and recovery rules in interface comments are contracts that specific implementations must satisfy. Each module is connected to real implementations; the existence of interfaces or complete test mappings does not mean all execution branches have been verified; see module tests for verification scope.

## 2. IM

| Package | Exported Interfaces | Core Responsibilities |
| --- | --- | --- |
| `im/conversation` | `Client`, `Publisher`, `Service` | Query sessions/messages, user sending, assistant publishing, read status, and feedback |
| Same as above | `Repository`, `Outbox` | Transactional message persistence and reliable message creation events |
| `im/realtime` | `Feed`, `Subscription`, `Store` | Authorized real-time subscriptions, post-commit wake-ups, continuous authentication, persistent events, and batch replay |

User and assistant writes share `Message`, `Content`, and repositories. The difference between the two entry points is identity and business trigger semantics, not two separate IMs: senders cannot be specified by the request; user input can wake up Agents, while assistant publishing should not wake itself up again.

IM stores `MessageCreated` outbox, Agent scheduling consumes it and finds the assistant via business bindings. IM does not depend on Agent and business packages; business sources in messages are merely object references. Business status can also use visible event flows for client push, but internal reasoning and tool logs cannot directly enter this flow.

## 3. Agent

| Package | Exported Interfaces | Core Responsibilities |
| --- | --- | --- |
| `agent` | `Runtime`, `Observer`, `ContextBuilder`, `Checkpoints` | Independent Loop, visible state, limited context, and private checkpoints |
| `agent/scheduler` | `Service`, `Control`, `Queue`, `MessageConsumer` | Single-assistant serialization, multi-assistant bounded concurrency, IM handoff, recovery, and confirmation |
| `agent/model` | `Catalog`, `Client`, `Stream`, `Receipts` | Available models, authorized calls, streaming output, and persistent billing evidence |
| `agent/tools` | `Executor` | Query authorized built-in tools, execute, and cancel |
| `agent/operation` | `Recorder`, `Service`, `Repository` | Intent recording, results, cancellation, unknown result reconciliation, and deduplication |

`event.AssistantEvent` distinguishes user message references, scheduled occurrence points, operation results, and recovery requests. Validation prohibits mixing sources; scheduled tasks cannot carry forged user messages. Model input is constructed by the Loop and does not accept parameters for "automatically injecting the entire chat history."

Closing the model stream does not mean the provider has stopped or not billed; call receipts must be persisted independently. Tool results do not automatically become messages; publishing must go through IM's sending capability. Checkpoints are internal state and cannot be leaked via status queries or SSE.

Tool `permission_list` queries authorized tools and their current operation availability; `permission_request` creates authorization requests pending user approval, independent of Shell enablement status. The returned user authorization scope and the runtime's built-in workspace are identified separately; resource root paths do not represent the host root directory. File tools and Shell share storage permission checks; the latter only mounts explicitly selected scopes, using stable logical paths bound to resource identities. See [Command Execution Environment](../../admin/sandbox/linux.md) for detailed contracts.

File capabilities are `file_list`, `file_read`, `file_write`, `file_edit`, corresponding to independent parameter structures and tool definitions. Omitting `resource_id` defaults to reading/writing the current assistant workspace, requiring no storage/compute authorization, with paths being relative or `/work/...`; external storage is accessed only when `resource_id` is specified. Workspace identity is determined by the server and shared with Shell's `/work`. Directory listing and reading return pagination/ranges and versions; writing requires explicit overwrite selection, and partial editing requires version and exact matching. File modifications use temporary files and atomic replacement, re-checking permissions before commit; known pre-commit rejections are recorded as failures, and uncertain commit results remain pending reconciliation.

Model responses persist the complete status code and response body (up to 8 MiB) before adapter parsing, including error responses, not relying on the development workbench. The raw assistant message from successful responses is saved as `ProviderState` with context and call cache, preserving unknown extension fields; upon return, the corresponding protocol adapter selects fields and verifies Provider, model, and address identity. Saving fields does not mean automatic sending of fields. For DeepSeek requests with tools, if historical reasoning data is missing, `model_context_incompatible` is returned before sending, releasing the reserved budget for this call and prompting a context reset, without forging reasoning or silently deleting history. When no Provider preset is specified, only official DeepSeek HTTPS origins are automatically identified as DeepSeek; explicit presets always take precedence.

## 4. Business

| Package | Main Entry Points | Behavioral Boundaries |
| --- | --- | --- |
| `business/assistant` | Hire, query, modify, group pinning, fire, rehire, clone | Manage assistant identity and session bindings; cloning does not copy ongoing work |
| `business/task` | Create, revise, pause/resume/cancel, accept delivery | User control and execution reporting are separate interfaces; completion requires real acceptance evidence |
| `business/todo` | Add, query, modify, delete | Assigning assistants does not automatically start tasks |
| `business/plan` | Personal/assistant schedule aggregation, execution association, and handoff | Acyclic dependencies within the same account; idempotent execution; historical snapshots; explicit automatic handoff |
| `business/schedule` | Personal schedule/assistant plan maintenance | Timezone and missed plan handling are explicit, with bounded trigger counts |
| `business/resource` | Connect, describe, query, check, disconnect | Secure description and protected address/credential binding are separate |
| `business/memory` | Local Markdown shared/private memory maintenance | File content hash versioning, private scope bound to assistant; forgetting saves summary hash and source separately, not deleting original chats |
| `business/settings` | Preference update, export, cleanup | Sensitive operations require recent identity verification; new defaults do not reset existing budgets |

Each business package provides `Service` and required `Repository`; task additionally provides internal `Execution`. Repositories are trusted persistence ports, not interfaces for clients to bypass permissions; implementations are provided by the SQLite package, and business packages do not import specific storage or HTTP packages.

## 6. Atomicity and Recovery

`Transactions.Within` passes repositories within the same transaction to a callback. Callback failure, cancellation, or commit failure all return errors; repositories must not escape to asynchronous tasks, and cannot wait for models and external tools within the transaction.

Combinations that must be atomically committed include:

1. User message/assistant published message + IM outbox + visible event + idempotency receipt.
2. IM outbox confirmation + deduplicated Agent input; assistant messages are only confirmed, not creating new input.
3. Scheduled occurrence point registration + Agent input; personal schedules do not wake up assistants.
4. Assistant checkpoint + job processing confirmation; recovery first reconciles already issued external operations.
5. Concurrent budget reservation + operation identity; unknown costs continue to occupy the reservation and cannot be automatically released to zero.

Each visible event stream assigns cursors in commit order; each client reads independently, checking session and permissions during continuous push. File staging and SQL metadata are coordinated using a recovery protocol, not claiming cross-filesystem atomic commits.

## 7. Current Implementation and Verification

Public interfaces of each module are connected to real implementations, and independent storage-neutral `persistence` and underlying SQLite adapter packages have been added to avoid business dependencies on specific databases. SQLite transactions are reused across modules via context and bound Store; nested writes use savepoints; module JSON records are stored in a private keyspace.

Authentication, credential encryption, authorized budgets, IM, business, Agent, persistent queues, HTTP/SSE, files, and the main program are all implemented. The original TDD factories are all bound to real tested implementations, with additional cross-module business and complete message→Agent explicit tool read/publish→restart tests. `make -C runtime check` contains full behavioral tests; `check-contracts` only performs compilation, mapping, and static checks.

Contract corrections include: credential access supports real owner checks, without needing to forge Agent execution; model reconciliation parameters are fixed to local receipt ID; HTTP only holds budget query and operation control capabilities; task wake-up events carry TaskID, schedule events carry version; sessions retain monotonically increasing message high-water marks; historical cost settlement is separated from new side-effect authorization.

The model adapter has read the vendor SSE and collected generation timing; chat still only displays explicitly published messages and does not directly forward the vendor token stream. Currently, there is no vector search or general task acceptor; automatic context compression is implemented, triggered by the model token window and preserving the original history, see [Context Updates](../runtime/agent-context.md#token-capacity-and-automatic-compression). When external results are unknown, they remain pending verification, without assuming zero cost or safe retries. For complete boundaries and startup methods, see [Runtime README](../../../../runtime/README.md); for test records, see [Test Notes](../../../../runtime/tests/README.md).

### Plan and Execution Association

`GET /api/plans` aggregates existing todo/schedule identities, handover settings, and execution history by current owner, supporting occurrence point projections for up to 125 days. `POST /api/plans/configure` updates versioned dependencies and pause settings; `POST /api/plans/execute` starts assistant execution or records personal start/completion, validating owner, prerequisites, and idempotency keys in both cases. Completion of assistant execution still requires the original execution evidence chain.

`Task.Plan`, `PlanTitle`, `PlanInstructions`, `PlanVersion`, and `OccurrenceAt` retain source snapshots. Runtime startup creates one-time schedules for old standalone tasks without changing old task IDs. Plan metadata is stored in `business.plan-links` and included in owner data exports; automatic handover, occurrence point registration, and task and event writes are within the same storage transaction.

## General Timed Triggers

`internal/trigger` provides `Rule.Validate`, `First`, `Due`, `Between`, and `RecordOccurrence`. The calculation result consists of the selected occurrence points and the next cursor; business adapters are responsible for persisting cursors and effects. Occurrence point identifiers include owner, kind, ID, revision, and UTC time; retries within the same transaction must not duplicate business events. The common layer does not depend on Schedule, Plan, Task, or Agent; permissions, lifecycles, and delivery logic for plans and dreaming are kept separate.

## Installation and component maintenance

`internal/installation`, executed by `molr-setup`, owns application and component maintenance. `Maintenance` exposes read-only status and launch methods to Runtime. It invokes the installed setup binary through an independent systemd user service, never installing in the Runtime process. The installer holds the instance lock throughout work; a verified newer installer inherits that same lock through a controlled file descriptor. Ordinary child processes do not inherit it.

The component catalog pins versions, sources, digests and size limits. Verified staging directories become immutable installations, with a component receipt separate from the application receipt. Filesystem operations reject links and path escapes. Component and maintenance directories cannot become ordinary assistant storage resources. Only trusted browser plans can mount program assets read-only; browser startup still uses the existing compute, network and sandbox authorization.
