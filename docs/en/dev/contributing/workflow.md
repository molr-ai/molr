# Development Collaboration Workflow

This document covers task isolation, branches, validation, commits, merging, and cleanup. See [environment conventions](environment.md) for development setup and [acceptance standards](acceptance.md) for acceptance entry points and service activation.

## Scope

- Decide whether a worktree is required based on the files being changed. Tracked code, tests, configuration, and documentation, as well as new files intended for version control, must follow this independent branch and worktree workflow.
- When maintaining only ignored internal materials such as `internal-docs/` that will not be committed, edit them in place. Do not create a branch or worktree, commit, merge, start acceptance services, or run project build tests for that work alone. Deliver file links and verify content and referenced resources. If the same task includes version-controlled changes, create a worktree for them. Store newly produced internal records in that worktree, keep existing internal materials in their original location, and preserve them during cleanup according to [public content and internal materials](../releasing/public-content.md#public-content-and-internal-materials).
- Keep the main working directory, identifiable through `git worktree list`, on `main` for inspection, synchronization with the merged GitHub mainline, and main branch services. **Do not edit code directly in the main working directory or switch it to a feature branch.** Develop version-controlled features, fixes, refactors, tests, configuration, and documentation in independent worktrees.

## Mainline and PR Gates

- The GitHub repository's `main` is the authoritative mainline. Merge version-controlled changes through GitHub PRs. Local worktrees handle development and independent acceptance; the main workspace only fast-forwards to the remote mainline, without locally merging task branches or pushing directly to `main`.
- Commands here use `github` for the remote pointing to the upstream GitHub repository. Check its address with `git remote -v`; substitute the actual remote name where different, rather than assuming `origin` is upstream. Fork contributors create branches from upstream main, push to their own fork, and open PRs against upstream.
- If Gitea is retained, synchronize its `main` one way from GitHub; it must not accept independent mainline merges. Gitea CI can provide additional validation. Compare both histories before switching workflows. Integrate commits missing from GitHub through task branches and PRs instead of overwriting differences with a force push.
- Maintainers should configure GitHub's `main` to require PRs, linear history, the required check `PR checks passed`, and branches up to date with the target mainline before merging. Disable force pushes and deletion of the main branch; routine development must not bypass protection. Allow Squash merge and Rebase merge, without merge commits. Verify the actual workflow check name and successful runs before enabling the gate; this documentation does not establish that remote settings are active. Update branch rules when check names change.
- `PR checks passed` aggregates the PR source, build, Runtime, desktop, and browser checks; the separate installer group is skipped as planned. Failed, cancelled, or unexpectedly skipped required jobs block merging. Manual and pre-release complete CI use `CI passed v3`; see [CI and build reuse](../releasing/releases.md#ci-and-build-reuse) for coverage. Passing PR CI still requires user acceptance and explicit merge authorization. The current workflow does not additionally require multiple approval layers or a merge queue.

## Starting and Developing a Task

- Before starting, inspect `git status --short --branch` and `git worktree list` to confirm the directory, branch, and existing tasks. Never overwrite, reset, or clean up another person's uncommitted changes.
- Use one branch and one worktree per independent task. Run `git fetch github` first and create the task from the latest `github/main`; continue an existing worktree for the same task. Use descriptive branch names such as `feat/<task>`, `fix/<task>`, or `chore/<task>`. If fetching fails, report that the latest mainline could not be verified; do not treat cached references as current.
- Place worktrees under `.cache/worktrees/<task>` in the main working directory, covered by the existing `.cache/` ignore rule. For example, run `git worktree add --no-track -b feat/<task> .cache/worktrees/<task> github/main` from the main directory. Resolve paths relative to the main directory; do not nest worktrees inside task worktrees. Resolve path or permission problems if creation fails instead of developing directly in the main directory.
- Perform all version-controlled edits, dependency installation, code generation, builds, tests, and commits in the corresponding task worktree. Parallel tasks must not share a worktree or modify another task's worktree.
- When adding, removing, or renaming public Runtime functions, concrete methods, or interface methods, update behavior test mappings in `runtime/tests/coverage-*.md`, including methods expanded from embedded interfaces. Run `npm run check:contracts` after local package tests, and `npm run check` before committing and after rebasing. Each mapping must reference a test that actually verifies the entry point's behavior. Add assertions where missing; never fill gaps with unrelated tests or skip manifest checks. Runtime test entry points such as `make -C runtime test` run repository-wide contract checks regardless of `PACKAGES` or `RUN` filters.
- Keep dependencies, build artifacts, compilation caches, and Runtime test data independent for each worktree. Persistent acceptance instances and their private records live outside source trees under the [instance directory convention](environment.md#private-instance-directories-and-source-isolation), associated with and cleaned up by their task. Reusable downloads follow the [shared cache conventions](environment.md#machine-directories-and-shared-download-caches). Never reuse or change the main workspace's running databases, credentials, or private data directories. Do not stop or replace main branch or other tasks' services during development and acceptance. After merging, update main services according to [post-merge activation](acceptance.md#post-merge-service-activation).

## Background Waiting and Polling Gate

Changes to internal authorization, plans, tasks, messages, and persisted state wake consumers through committed notifications. Known expiry times use the nearest deadline timer. Subscribe before reading, never notify on rollback, and release subscriptions/timers on cancellation or closure. Without a new event, due deadline, or pending failed operation, do not periodically query the database or reread state. Indexing queries or increasing the polling interval does not replace this rule.

Timed work is appropriate when an external system cannot notify, a protocol requires heartbeats, a measurement requires separated samples, or a visible interface needs animation/time display. Each site must document:

- Why notifications or a known deadline cannot serve the purpose; distinguish one-shot timeouts, retry backoff, protocol heartbeats, and continuous polling.
- Per-instance minimum interval/maximum rate, activation conditions, idle call budget, retry backoff, and termination conditions. Requests must not overlap. Background work ends with its context; frontend work follows visibility and subscription lifetime.
- Executable behavior evidence: advancing time after initialization makes no extra storage/HTTP calls, changes wake promptly, expiry takes effect, and cancellation leaves no work behind. Prefer virtual clocks and actual call counts; asserting only that a configured interval exceeds a threshold does not prove idle behavior.

`npm run check:polling` parses Runtime Go sources for all platforms, TypeScript sources in applications/packages, and the release observer `scripts/watch-release.mjs`. It checks timers, waits, Reset calls, frontend polling coordinators, and explicit query intervals. Production `realtime.NewFeed` construction must explicitly supply `WatchAuthorization`; `scheduler.NewService` must supply `TickSignals` and `NextTick`. An inventory entry cannot waive missing capabilities. New sites, changed site counts, delay/local cadence expressions, and stale entries fail the check. New untracked source files are included. `scripts/polling-policy.json` records existing sites, their purpose, operating budgets, and related tests. `--list` only reports discovered sites; there is no automatic update/accept command. First consider an event-driven implementation. When timed work is necessary, review entries individually and update the budget and tests in the same change; do not regenerate the whole inventory to silence failures. Existing exceptions are not a precedent for copying polling into new business logic.

`npm run test:polling` runs adversarial scanner fixtures, frontend virtual-clock request budgets, and idle/change/expiry contracts for authorization observers, scheduling, event streams, and channel delivery. A required contract that is removed, skipped, or never executed fails the suite. The static gate is part of `npm run check`; GitHub and Gitea run the behavior contracts in their source CI job. New background services must add idle behavior contracts as well as timer entries.

The static gate is a local syntactic check. It cannot prove that arbitrary wrappers, cross-file configuration, or third-party libraries never poll, and it does not equate every timer with an SQL query. Changes to shared cadence settings or wait wrappers require reviewing callers and adding call-budget tests. Review actual calls on the business path; a passing inventory alone does not establish a sound design.

## Acceptance, Merging, and Cleanup

- Commit, push, open PRs, and merge within the user's authorized scope. Do not ask again for existing authorization; completing development alone does not authorize pushing or merging. Before pushing, review actual content and the staging area under the public-content rules. When authorized, push the task branch and open a PR against upstream `main`; a Draft PR is appropriate while acceptance is pending.
- Each PR should represent one clearly scoped logical change and explain the problem, final behavior, validation results, and unfinished work. Keep its title and description aligned with the final implementation. Use **Squash merge** by default to combine development and review fixups into one mainline commit; the final message explains the change and its reason and links to the PR. Prefer separate PRs for independently acceptable changes. When a meaningful commit sequence needs to be preserved, explain why in the PR, organize and validate each commit, and use **Rebase merge**.
- **Deliver an acceptance entry point and wait for user acceptance before merging.** Merge on GitHub only after the user accepts and explicitly authorizes merging and the current PR passes required checks. Development completion, passing tests, creating a PR, or providing a link do not authorize merging. Preserve the worktree and acceptance services while waiting. Deliver one-time login links, private deployment addresses, and detailed acceptance materials through private channels, not public PRs.
- Before merging, run `git fetch github` and `git rebase github/main` in the task worktree. Do not synchronize the task branch with `git merge main` or `git merge github/main`. Resolve conflicts there, run `npm run check` and relevant validation, update the PR, and wait for CI on the current version. Integrate PRs sequentially; synchronize and validate subsequent tasks again after each merge. Coordinate with users before rebasing shared branches. Rewriting a remote task branch requires explicit authorization and `--force-with-lease`, without overwriting others' new commits. Changes affecting an acceptance conclusion require renewed acceptance rather than reusing earlier results.
- When merging on GitHub, verify that the PR target branch, final head SHA, merge method, checks, and authorization refer to the same version. Recheck if the head changes; do not enable unauthorized auto-merge. Record the resulting mainline commit and run `git fetch github`. Once the main workspace is clean and local `main` is an ancestor of `github/main`, synchronize with `git merge --ff-only github/main`. Preserve and investigate local-only commits or divergence rather than overwriting them with reset or force push. Confirm that synchronized `main` contains the PR's resulting mainline commit, then complete [main service activation](acceptance.md#post-merge-service-activation).
- Delivery must state the task branch, worktree path, PR link (or that none has been created), validation results, and merge status. After merging, also report the resulting mainline commit and main service activation. Provide an entry point according to [delivery standards](acceptance.md#acceptance-delivery-standards). One-time direct login links are required only for authenticated worktree acceptance pages. Ordinary URLs suffice for main workspace services.
- **After a successful merge and verified main service activation, clean up the task worktree without waiting for another request.** Squash/Rebase merge creates new SHAs, so neither `git branch --merged` nor task branch ancestry alone establishes completion. Confirm that the PR is merged, its final head matches the local task HEAD, local `main` contains the resulting mainline commit, and there are no uncommitted changes or new commits after merging. Preserve and investigate the worktree if these checks disagree. Stop only that worktree's acceptance services and delete historical acceptance materials under the [retention limits](environment.md#acceptance-data-and-backup-retention-limits), retaining only one development environment backup. Preserve product requirements, research, and promotional work under the public-content rules, then remove the directory with `git worktree remove`. Do not bulk force-delete branches or worktrees merely because they appear unmerged, or affect other tasks' worktrees or services. Report cleanup in the merge delivery.
