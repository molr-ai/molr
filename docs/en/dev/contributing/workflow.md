# Development Collaboration Workflow

This document covers task isolation, branches, validation, commits, merging, and cleanup. See [environment conventions](environment.md) for development setup and [acceptance standards](acceptance.md) for acceptance entry points and service activation.

## Scope

- Decide whether a worktree is required based on the files being changed. Tracked code, tests, configuration, and documentation, as well as new files intended for version control, must follow this independent branch and worktree workflow.
- When maintaining only ignored internal materials such as `internal-docs/` that will not be committed, edit them in place. Do not create a branch or worktree, commit, merge, start acceptance services, or run project build tests for that work alone. Deliver file links and verify content and referenced resources. If the same task includes version-controlled changes, create a worktree for them. Store newly produced internal records in that worktree, keep existing internal materials in their original location, and preserve them during cleanup according to [public content and internal materials](../releasing/public-content.md#public-content-and-internal-materials).
- Keep the main working directory, identifiable through `git worktree list`, on `main` for inspection, integration, and main branch services. **Do not edit code directly in the main working directory or switch it to a feature branch.** Develop version-controlled features, fixes, refactors, tests, configuration, and documentation in independent worktrees.

## Starting and Developing a Task

- Before starting, inspect `git status --short --branch` and `git worktree list` to confirm the directory, branch, and existing tasks. Never overwrite, reset, or clean up another person's uncommitted changes.
- Use one branch and one worktree per independent task, created from the latest local `main`. Continue an existing worktree for the same task. Use descriptive branch names such as `feat/<task>`, `fix/<task>`, or `chore/<task>`.
- Place worktrees under `.cache/worktrees/<task>` in the main working directory, covered by the existing `.cache/` ignore rule. For example, run `git worktree add -b feat/<task> .cache/worktrees/<task> main` from the main directory. Resolve paths relative to the main directory; do not nest worktrees inside task worktrees. Resolve path or permission problems if creation fails instead of developing directly in the main directory.
- Perform all version-controlled edits, dependency installation, code generation, builds, tests, and commits in the corresponding task worktree. Parallel tasks must not share a worktree or modify another task's worktree.
- When adding, removing, or renaming public Runtime functions, concrete methods, or interface methods, update behavior test mappings in `runtime/tests/coverage-*.md`, including methods expanded from embedded interfaces. Run `npm run check:contracts` after local package tests, and `npm run check` before committing and after rebasing. Each mapping must reference a test that actually verifies the entry point's behavior. Add assertions where missing; never fill gaps with unrelated tests or skip manifest checks. Runtime test entry points such as `make -C runtime test` run repository-wide contract checks regardless of `PACKAGES` or `RUN` filters.
- Keep dependencies, build artifacts, compilation caches, and Runtime test data independent for each worktree. Reusable downloads follow the [shared cache conventions](environment.md#machine-directories-and-shared-download-caches). Never reuse or change the main workspace's running databases, credentials, or private data directories. Do not stop or replace main branch or other tasks' services during development and acceptance. After merging, update main services according to [post-merge activation](acceptance.md#post-merge-service-activation).

## Acceptance, Merging, and Cleanup

- **Deliver an acceptance entry point and wait for user acceptance before merging.** Merge into `main` only after the user accepts and explicitly authorizes merging. Development completion, passing tests, or providing a link do not authorize a merge. Preserve the worktree and acceptance services while waiting.
- Before merging, run `git rebase main` inside the task worktree to replay task commits on the latest local `main` and keep new history linear. Do not use `git merge main` to synchronize the task branch. Resolve rebase conflicts and rerun relevant validation in the task worktree, never by editing the main directory. Integrate branches sequentially; after each merge, rebase and validate the next branch against the updated `main`. Coordinate with users of shared task branches before rebasing; rewriting a remote branch requires separate explicit authorization.
- Commit, merge, and push only within the user's authorized scope. Completing development does not authorize a push. Ensure the main working directory is clean, then fast-forward the verified branch with `git merge --ff-only <branch>`. If a fast-forward is impossible, rebase and validate again in the task worktree rather than creating a merge commit. Check the resulting state and required integration validation.
- Delivery must state the task branch, worktree path, validation results, and merge status, and provide an entry point according to [delivery standards](acceptance.md#acceptance-delivery-standards). One-time direct login links are required only for authenticated worktree acceptance pages. Ordinary URLs suffice for main workspace services.
- **After a successful merge and verified main service activation, clean up the task worktree without waiting for another request.** First confirm all changes are committed and merged, stop only that worktree's acceptance services, and preserve valuable acceptance data. Then remove the directory with `git worktree remove`. Never force-remove a directory containing uncommitted changes or affect other worktrees or services. Report cleanup in the merge delivery.
