# Acceptance and Service Activation

This document covers feature delivery, independent acceptance, real-model tests, Runtime verification, and post-merge service activation. See [environment conventions](environment.md) for service ports and caches and the [collaboration workflow](workflow.md) for tasks and merging. Production deployment belongs to the [administrator guide](../../admin/README.md).

## Acceptance Delivery Standards

- Deliver a directly accessible WebUI acceptance link for features that do not involve the desktop app, following the service isolation and login requirements below. Changes to the website or UI Design itself use an acceptance link for that application.
- For features involving the desktop app, deliver a `local` development package that the user can install on their machine. State the supported OS, architecture, and installation method, and verify the feature through the installed app. See [desktop development](../../../../apps/desktop/README.md#packaging-and-release) for packaging commands.
- Development and production packages must use separate installation directories and isolate configuration, databases, login sessions, and other user data. Development packages use a consistent installation identity and directory so that they can replace one another. Verify installation isolation, data isolation, and replacement installation before delivery.
- For documentation-only changes, deliver file links and validation results; no acceptance service or desktop package is required.
- State the task branch, worktree path, validation results, and merge status. Acceptance and merge authorization follow the [collaboration workflow](workflow.md#acceptance-merging-and-cleanup).

## Independent Worktree Acceptance Services

- For changes to runtime behavior or interfaces, start isolated acceptance services without waiting for another request. Start only the involved applications, with one development service per frontend. Documentation-only changes do not require additional services. When connecting WebUI to a real backend, use that worktree's own Runtime, never the main branch or another task's Runtime.
- Inspect existing processes and listening ports before starting, and allocate unused ports to each instance. WebUI, the website, and UI Design use the `0.0.0.0` LAN listening convention in [development services](environment.md#development-and-preview-services). Keep the agreed Runtime listening and TLS security configuration; do not weaken it to bypass startup restrictions.
- Give each acceptance instance independent configuration, databases, keys, login accounts, assistant workspaces, caches, and logs. Local runtime files may live under `.cache/acceptance/` in that worktree. Never copy real credentials from the main environment or reuse its data directories. Keep credentials and acceptance data out of Git commits.
- Record the instance's startup method, ports, and data directories for continued acceptance and restarts. After changes, check that the service loaded the current code. Rebuild or restart only the relevant service in that worktree when needed, preserving existing acceptance data.
- Before delivery, verify page access, the frontend proxy's connection to the correct independent Runtime, and relevant features or capabilities. Provide the LAN URL and validation results. **Authenticated worktree acceptance pages must include a one-time link that logs the user in directly; an ordinary login page or instructions to enter a username and password are insufficient.** Provide direct links for pages without login. Temporary test services do not replace the acceptance service available to the user.
- Generate one-time links with an account belonging to the acceptance instance and target that worktree's WebUI and independent Runtime. Explicitly set the default validity to **3 hours** (`expires_in: 10800`), unless the user requests otherwise; do not rely on a shorter tool default. Use a separate test link to validate login, then generate a fresh, unused delivery link and state its exact expiration time and timezone. Never consume the delivery link in advance. Regenerate expired or used links without requiring manual login. Do not commit links or tokens.
- Preserve acceptance services with the worktree while awaiting acceptance and merging. Clean them up after merging and verifying main branch service activation. Stop only that worktree's processes and preserve valuable data; do not use broad termination commands that affect other instances.

## Real-Model Tests

- **When tests or acceptance require a real model, prefer the local model already configured in the main environment.** First inspect the existing connection, model name, and capabilities read-only, verifying availability and the tool calling, multimodal, context capacity, or other features required by the task. Do not default to starting another inference service or using a cloud model.
- Configure the same local inference endpoint and model in the task worktree's independent Runtime, using its own test accounts, assistants, and synthetic materials. Only the inference service is shared; Runtime configuration, databases, login sessions, and workspaces remain isolated. Follow the credential rules above, and do not modify the main model configuration or stop or replace its service.
- If the configured local model is unavailable or lacks required capabilities, choose another suitable model and record the reason. Record the test date, actual model, configuration, and results. Keep deployment addresses, credentials, and complete requests and responses in local ignored directories, not public documentation or test fixtures.
- Deterministic protocol and regression tests may still use mock model services. Tests of real model behavior or summarization quality must call the preferred real model and clearly distinguish their results from mock tests.

## Runtime Builds and Sandbox Acceptance

- **Explicitly set `CGO_ENABLED=0` for main services and all worktree acceptance instances. Linux Runtime must be a static ELF; native macOS Runtime must be Mach-O.** Use the Go version in `runtime/.go-version` and build in the task worktree. Main service updates must use a clean build worktree matching the target `main` commit. For example, from its `runtime/` directory, run `CGO_ENABLED=0 go build -o ../.cache/acceptance/molr ./cmd/molr` after creating the output directory. Runtime normally reuses its own binary as the sandbox helper. Dynamically linked artifacts cannot run in the minimal sandbox even if their HTTP service starts.
- Inspect the final artifact before deployment rather than relying on build flags. Use `file <binary>` to confirm a static Linux binary or macOS Mach-O and `go version -m <binary>` to confirm `CGO_ENABLED=0` and the build commit. Main service artifacts must also have `vcs.modified=false`. Record the task's modification state for acceptance builds; never deploy acceptance artifacts with uncommitted changes to the main service. When needed, use `readelf -h -l <binary>` to check architecture, ELF type `EXEC`, and absence of an `INTERP` segment. Do not replace a running service when checks fail.
- **Check binary permissions after building and deployment. Runtime and helpers must use `0755`, never group-writable or other-writable modes such as `0775` or `0777`.** Bubblewrap (normally `/usr/bin/bwrap`) and the helper must be executable regular files, with no symlinks in their paths or parent directories. Do not weaken permissions to bypass checks. Confirm a static BusyBox is available with a source and resolved file permissions that satisfy Runtime checks.
- Linux instances with sandboxing enabled require valid cgroup v2 delegation. Use the verified systemd user service method with `Type=exec`, `Delegate=yes`, `DelegateSubgroup=supervisor`, and `KillMode=control-group`. Service names start with `molr`, with a separate unit per worktree. Do not casually switch to background startup from an ordinary login session or treat successful unit startup as proof of sandbox readiness.
- Before updating the main Runtime, recheck the build commit against current `main` and preserve the old binary and configuration. Validate a temporary file and replace the binary by atomic rename; do not overwrite an executing binary. Preserve the database, keys, and accounts. If data directories must be copied, stop that instance normally first and restart with the original security configuration. Record the actual PID, build commit, binary digest, startup method, and rollback location.
- **After every start, rebuild, or restart, check `GET /api/sandbox` using an authenticated request in addition to page and HTTP connectivity checks. Instances with WebUI must also be verified through its proxy.** Unless the user explicitly disabled sandboxing, require `Enabled=true`, `Capabilities.Reason=available`, and `Shell`, `ProcessIsolation`, `FileIsolation`, `NetworkIsolation`, and `ResourceLimits` all `true`, confirming Runtime's real isolation startup probe passed. This applies to independent acceptance and post-merge main services. Logs, listening ports, or a working `/api/status` alone do not establish success.
- macOS acceptance uses independent data directories and services. Controlled execution requires `Enabled=true`, `Reason=available`, `Shell`, `FileIsolation`, and `NetworkIsolation` true, with `NetworkBackend=seatbelt-toggle`; `ProcessIsolation` and `ResourceLimits` are false. With commands disabled, check `Enabled=false` and `Storage=true`; when Full Access is independently enabled, check its capability is true. Verify file and network toggles, terminals, and revocation natively. Remote nodes follow their execution platform's requirements: Linux rules on Linux and Seatbelt rules on macOS. Disabled standalone nodes require Enabled=false and Storage=false.
- Diagnose sandbox problems using the actual reason code. For `sandbox_package_incomplete`, first check static helper linkage and static BusyBox. For `sandbox_helper_unavailable`, check Bubblewrap/helper existence, executable permissions, group or other write permissions, and symlinks. For cgroup or other startup failures, inspect the unit, delegation, and logs. Never hide problems by disabling sandboxing, weakening isolation, or falling back to host execution. Recheck capabilities after fixing the issue and explicitly report unavailable capabilities if recovery fails.

### Startup Readiness and Authentication Verification Order

These rules apply to independent acceptance and post-merge main service updates. Verification scripts must separate startup waits, session recovery, capability checks, and rollback decisions so that verification itself does not trigger repeated restarts or login throttling.

- **Wait for HTTP readiness before authentication checks.** A returned `systemctl restart` or an `active` unit only means the process started. Use a read-only request that needs no login, such as `GET /`, with an explicit overall deadline and polling interval. Treat short connection refusals before the deadline as startup in progress, without immediate rollback. Readiness probes must not call login or one-time link preview/redemption endpoints. After HTTP is ready, still complete the authenticated sandbox capability checks above.
- **Reuse verification sessions instead of logging in before every check.** Reuse the Cookie jar or browser context and its CSRF proof for the pre-update baseline, post-update checks, and necessary rechecks at the same entry point. After a restart, confirm validity with `GET /api/auth/me` before reauthenticating. Maintain separate sessions for direct and WebUI proxy access according to their cookie names and origins; do not count them as one login or mix other instances' credentials. Log out script-created sessions after the full verification run. If sessions must persist across scripts, store them only in the task's private ignored directory with `0600` permissions, without printing or committing credentials.
- Before verification, inspect the actual rate-limit implementation and deployment configuration and reserve enough login attempts for testing, including delivery link validation for worktree acceptance. The current [authentication implementation](../../../../runtime/internal/auth/service.go) uses a 1-minute account window and a 10-minute source-address window with the same configured threshold, defaulting to 5 attempts each. **Successful logins also count; the name `login_attempts_per_minute` does not mean every window lasts one minute.** Records persist across restarts, and Runtime may identify direct and proxy traffic as the same source address.
- **HTTP 429 means verification was throttled; it is not sufficient evidence of a new-version failure or reason to roll back.** Stop repeated authentication, respect `Retry-After` when present, and check for additional authentication windows. Without that header, use the actual active limits and windows to determine recovery time instead of guessing one minute. Existing valid sessions can continue checks within their permissions. Do not bypass throttling by clearing counters, raising thresholds, switching source addresses, or repeatedly restarting.
- Before rollback, inspect process state, startup logs, readiness deadline, and the exact failing stage. An unfinished startup, expired verification credentials, or throttled verification requests do not by themselves prove an artifact fault. Decide on a fix or rollback only after confirming startup failure, an exceeded reasonable readiness deadline, or failed capability checks. If authentication checks cannot finish, report “verification incomplete”; accessible pages alone do not prove deployment success.
- Issue worktree delivery links through the already authenticated verification session. Use the established flow for required sensitive-operation checks and retain the three-hour validity and separate test/delivery link requirements. Do not repeatedly log in to issue, preview, or verify links.

## Post-Merge Service Activation

- **After merging into the main workspace, verify that running main branch services loaded the merged version. Necessary rebuilds, restarts, and verification are part of merging and do not require another reminder.**
- When a compiled service such as Go Runtime changes, build from a clean worktree matching current `main`, then update its binary and restart normally. Follow the static build, permission, startup, and capability checks above. Recheck the `main` commit before updating to avoid overwriting a newer concurrent merge with an older build. Preserve configuration, databases, credentials, and a rollback binary.
- Main workspace frontends use the three development services defined in [environment conventions](environment.md#development-and-preview-services). Keep services running when hot reload has loaded the new code. Restart affected services when dependencies or startup configuration change, or hot reload fails. Do not start additional build previews, documentation servers, or duplicate frontend instances for merging.
- Operate only on processes confirmed to belong to the main workspace, preserving other worktrees' acceptance services. After restarting, check listening addresses, ports, frontend/backend connections, and affected functionality. Startup logs alone do not establish success.
- In merge delivery, report whether the changes are active, which services were restarted, and ordinary main environment URLs. Login links are not required. If startup or verification fails, identify the part that is not active.
