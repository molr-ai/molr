# Quick Start

From installing Molr to completing your first delegation. If you already have an accessible service, start directly with [Login](#login); for public-facing or long-running production deployments, see [Deployment and Maintenance](deployment/README.md).

## Install Molr

Select a channel with an available version from the installation section on the official website, then select the target platform. Available versions are subject to the official website's release list; channels without available versions do not provide download links. Current platforms are defined as Linux amd64/arm64. The installation package includes Runtime and WebUI; static dependencies such as BusyBox for the sandbox are provided by the target machine's system package manager.

After preparing Python 3.11+, download the official installation script and select a channel:

```bash
curl -fL https://molr.ai/install.sh -o install.sh
bash install.sh --channel stable
```

The example uses `stable`; if this channel has no available version, select `preview` or `nightly` with an available version on the official website, and use the fixed-version command generated by the official website. Users do not need to install Go, Node.js, or deploy the web interface separately.

The first installation defaults to using the current regular user, selecting an available port starting from 8787, installing a systemd user service, and generating independent configuration. When executed as root, a non-root runtime account must be specified via `--user molr`. If dependencies are missing, apt-based systems will ask whether to install them; other systems require installing dependencies as indicated by the output. The systemd user manager must be available; if you need the service to continue running after logout, configure linger as prompted during installation.

Upon completion, the installation outputs a LAN access address and a one-time login link valid for 15 minutes. Click the link and confirm login to enter the initial setup:

1. Select an auto-discovered local model service, or configure a cloud/custom Provider.
2. After connecting, confirm the selected model and the default daily budget of USD 1, which can be modified. Unknown prices must be supplemented; entering 0 explicitly confirms that it is free.
3. Click "Get Started" to automatically create the **Molr** assistant and enter the chat. The initial greeting calls the selected model and counts towards the budget.

Language and timezone are determined by browser settings. During installation, the `owner` account is automatically created, and the random initial password is saved in the `initial-password` file (0600) in the data directory; the specific path is displayed in the terminal. You can change the password later and delete the initial password file yourself. To regenerate the login link, use the program in the installation directory:

```bash
/path/molr-server access -config /path/server.json
```

If the initial password was not retained or has been changed, enter the current password via `-password-stdin`; if MFA is enabled, `-mfa-code` is also required. Re-running the installation preserves the original configuration, accounts, and data, without resetting passwords or recreating the assistant.

LAN can use HTTP without certificates. HTTP does not encrypt passwords, sessions, or messages, and is suitable for trusted networks; public networks must continue to use HTTPS. Browser capabilities such as system notifications may require HTTPS, but in-page reminders remain usable.

### Auto-Discovery of Local Models

Both the initial setup and "Resources → Models → Connect Provider" automatically detect common ports on **the device where Molr is located**: Ollama 11434, llama.cpp 8080, vLLM 8000, SGLang 30000. Detection only reads interfaces and model lists; it does not start services, download models, or send inference requests. If the implementation type cannot be confirmed, it is displayed as an OpenAI-compatible service.

Custom ports or other devices can be manually entered. Clear prompts are provided if the service requires authentication, has no models, or is already connected. The local address inside a container refers to the container network; discovery results do not indicate that model tool calling has been verified, nor do they imply that the service is free.

For source code deployment and offline installation, see [Source Code Build](deployment/source-build.md) and [Installation Guide](deployment/installation.md) respectively.

## Login

The first administrator logs in using the account created during initialization; regular members use accounts created by the administrator. There are no default username/password combinations or public registration entry points. If two-factor authentication is enabled, enter the verification code or recovery code as prompted on the page.

Existing logged-in devices can generate a one-time link via "User Settings → Security → Login Links" for logging in on another device. The link has an expiration time and can only be used once; if MFA is enabled, two-factor authentication is still required. Links should only be given to the individual or explicitly authorized users, and should not be placed in public documents.

## Connect Models

Administrators go to "Resources", select a model category, and connect a provider. Regular members do not need to configure connections; administrators assign available models and tools via [User Groups](administration/users-and-groups.md). If available models already exist, you can directly hire an assistant. Fill in the service address and required API Key; for local services without authentication, select no authentication as required.

You can test the connection first, then save and retrieve the model list. A successful test only indicates that the model list interface is accessible; actual inference and tool calling still depend on the capabilities of the selected model. If the model list is empty or lacks capabilities/prices, supplement them in the model configuration.

Do not enter zero if the price is unknown; explicitly setting it to zero confirms that the item is free. When connecting to local models, the address refers to the device where the Runtime is located, not the computer where the browser is running. Deployment network policies may require administrator adjustments; see [Deployment Instructions](deployment/configuration.md#model-network-and-pricing-configuration).

## Hire an Assistant

Set a name for the assistant, a model that supports tool calling, consumption limits, and a daily or weekly reset cycle. Hiring authorizes the selected model; it does not simultaneously authorize all models under that provider or your file directory.

The budget belongs to the assistant. The assistant's chats and all planned executions share the quota; there is no separate task budget. For detailed rules, see [Resources, Permissions, and Budgets](guides/permissions-and-budget.md).

## Assign the First Task

Start with a small task whose results you can verify, such as uploading a document, asking the assistant to list key points and questions to confirm, and pointing out the basis. Specifying inputs, expected results, and originals that should not be changed helps determine whether the task is completed.

Attachment sending, model replies, or tool operations may fail; pay attention to the status and reasons on the page. Normal conversations do not force plan generation; when the model explicitly creates a task, execution is associated with a plan. The actual file types and content sizes that can be processed are limited by model and deployment capabilities.

## View Results and Continue

View related executions and artifacts in the chat and "Plans"; existing deliverables can be downloaded, and task revisions retain historical versions. Receiving a reply does not mean that materials have been modified or tasks have been accepted; verify the actual results and explicit completion status.

If the assistant needs to read external directories, connect to that directory and grant scope; if command execution is needed, additionally grant execution permissions for the ready compute environment. For operation paths, see [Assistants, Chats, and Plans](guides/assistants-and-chat.md) and [Linux Command Environment](deployment/sandbox.md).
