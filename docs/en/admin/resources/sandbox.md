# Manage Sandbox Resources

Controlled macOS commands use Seatbelt, duration-only compute grants, and a network permission toggle. Linux hard resource quotas are unavailable. See [native macOS command permissions](../sandbox/macos.md) for paths, revocation, and forwarding boundaries.

This page is for administrators. In "Resources → Sandbox", connect execution machines and add storage, compute, and network resources allowed for deployment. Assistant workspaces always reside locally in the Runtime.

## Local Resources and Member Scope

Local sandboxes are built into the Runtime and do not require starting a separate service. Default compute and network resources are registered only during initial instance setup, according to deployment policy. Subsequent starts never recreate them. Connect directories and additional network resources in their respective sections. Unrestricted directory configuration accepts absolute paths or `~/` on that machine. Restricted configuration offers exposed roots and optional relative subdirectories. Connecting and adding resources does not automatically grant assistant permissions. Trailing directory separators are removed automatically. Saving reports a specific reason below the path field when the directory is missing, inaccessible, contains symbolic links, or is outside the allowed scope. Editing the path or directory source clears the message.

Assign sandboxes and tools via [User Groups](../administration/users-and-groups.md); members then approve directory read/write, compute, and network permissions for their own assistants. GPU devices must first be opened by the deployer, then selected in the user group's compute configuration; an empty selection means GPUs are not allowed. Full Access also requires deployment enablement and explicit administrator permission to grant it to the corresponding user groups.

For deployment dependencies, GPU, and network candidate scopes, see [Linux Sandbox Deployment](../sandbox/linux.md). For user authorization and usage, see [Permissions and Budgets](../../user/guides/permissions-and-budget.md).

The Compute section describes controlled command execution. It distinguishes disabled execution, unavailable controlled compute, offline nodes and disconnected nodes, showing capacity only when available. Failures show their cause and recovery steps, without asking users to expose directories or networks. Compute cards and new grants follow current controlled execution capability; existing grants remain viewable and revocable. Full Access has its own section and covers storage, compute and networks accessible to the service account. It may remain available when controlled compute is unavailable, requires its own grant and explicit invocation, and never becomes an automatic fallback for ordinary calls.

## Disconnect, reconnect and delete

The default list shows resources that have not been disconnected, including unavailable entries and their reasons. The Disconnected resources entry in each storage, compute and network section lists disconnected records. Opening it loads current status. Active grants disable deletion; hover, focus or tap the disabled menu item to see why, without probing disconnected resources.

Disconnect resource suspends access while retaining settings, grants and quota usage. Reconnect validates the original resource and restores access through existing active grants without changing the resource ID, grant expiry or quota usage. Failed validation leaves it disconnected. Disconnected compute entries show both ordinary compute and full-access grants for inspection and revocation.

Deletion requires a disconnected resource with no active grants. Unrevoked, unexpired grants across all accounts block deletion, including grants held by unavailable assistants. Their account owners must revoke them first; deletion never revokes grants implicitly. Revoked or expired grants and historical use do not block deletion. Only the resource connection is removed; files, deployment network rules and history remain. Adding the resource again creates a new ID and requires new grants. The built-in assistant workspace cannot be disconnected or deleted.

First-time initialization creates the account and policy defaults atomically, rolling back together on failure. Subsequent startup and Check again only check existing resources that are not disconnected. They never reconnect disconnected entries or create resources because the catalog is empty or deployment rules have changed. Multiple independent resources may refer to the same network rule; disconnecting or deleting one does not affect the others.

## Connect in the WebUI

Use each remote sandbox instance with only one Runtime. Do not share an instance or its connection credentials across multiple Runtimes. The service currently does not prevent multiple Runtimes from connecting and does not isolate permissions or operation state by Runtime. Deploy a separate [sandbox instance](../sandbox/remote.md) for each Runtime.

1. Go to "Resources → Sandbox → Connect Sandbox", enter a name, the HTTPS service address and the connection code exported on the sandbox, then test the connection and save. The code does not contain the address; users enter it separately. Code format and node protocol compatibility are checked automatically. Test again after changing the address or code.
2. Go to the "Storage / Compute / Network" partitions of that sandbox and add resources that have been opened on the server side. Compute limits are displayed as read-only; directory and network scopes are managed by deployment configuration and cannot be expanded on the page.
3. Use the "Authorize to Assistant" option on resource cards to grant external storage read/write, compute execution, or network usage permissions. You can also view, modify, and revoke existing authorizations; management can also continue on the assistant permissions page. Connecting to a remote computer does not automatically grant any resource permissions, nor does it create an assistant workspace.
4. Assistants work locally by default. Remote file and Shell calls must explicitly pass `sandbox_id` and use the resources of that node; omitting the node but referencing remote resources will be rejected. There is no assistant `/work` on the remote side, and remote AGENTS.md, skills, or memory are not discovered.

The page displays connection, storage, and compute status separately; a successful connection does not imply that compute isolation is ready. "Re-check" refreshes actual capabilities, and when offline, the configuration snapshot from connection time is retained. "Rename" in the sandbox menu only changes the display name and does not require re-entering the token; "Update Connection Credentials" and "Disconnect Sandbox" are handled independently. Desktop shows the sandbox list and connection button on the left, with details on the right. Phones open with the list; selecting a sandbox opens details, and the back button or browser Back returns to the list. The selected sandbox is included in the URL so details survive reloads. The current sandbox and section are remembered within the same browser tab.

Sandbox status, capabilities, and resource details are cached for five minutes by default, with the check time shown on the page. Check again fetches and replaces status and details immediately; editing a connection or resource also rechecks the active page. Assistant, grant, and resource lists remain live, and execution-time authorization and isolation checks do not use page caches.

Administrator-configured remote Sandbox services allow private and loopback IPs without setting `network.allowed_private_ips` or restarting Runtime. Connections still verify the TLS public-key fingerprint and connection credential and stay bound to the configured scheme, host, and port. Automatic redirects are disabled, every DNS answer is checked at dial time, and cloud metadata, link-local, and other prohibited destinations remain blocked. The network resources of the Sandbox describe the network where the execution machine resides, where loopback addresses refer to that execution machine.
