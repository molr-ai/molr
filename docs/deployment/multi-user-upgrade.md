# 从单账号升级到多用户（一次性）

正常运行的 Runtime 不包含旧账号转换逻辑，也不会回退读取旧单例格式。升级只需由部署者显式运行一次独立 Python 工具；转换后和全新安装都不依赖此工具。

## 升级步骤

1. 准备通过验证的新版程序和 WebUI，保留旧二进制。不要先用新版启动或执行 `init`。
2. 正常停止当前 Runtime，保持停服直至转换和程序替换完成。
3. 使用 Python 3.9+ 在 Linux 上检查并转换。命令中的配置须指向该实例原来的配置，备份目录须是尚不存在、且位于数据目录之外的私有目录。

```bash
python3 runtime/scripts/migrate-multi-user.py \
  --config /absolute/path/server.json --check

python3 runtime/scripts/migrate-multi-user.py \
  --config /absolute/path/server.json \
  --backup-dir /absolute/path/backups/before-multi-user
```

4. 工具返回 `converted` 后，按通常静态构建、0755 权限及 systemd 委派要求替换程序，使用原配置启动新版并更新 WebUI。
5. 检查原账号登录、助理和历史数据、模型与凭证，以及认证后的直接和代理 `/api/sandbox` 能力状态。再通过管理员设置创建用户组和成员。

工具持有与 Runtime 相同的 `server.lock`，服务仍在运行时拒绝执行；SQLite 事务也会排除其他写入者。`--check` 只检查停服实例，不改写数据库记录。转换前复制完整数据目录及配置；若配置了数据目录之外的 `sandbox.work_root`，同时复制该工作区。符号链接按链接本身保存，不跟随它们读取外部文件。备份不包含挂载目录指向的其他外部存储；本次转换也不修改那些目录。

备份完成后才在单个事务内调整账号索引、写入原账号的管理员组和必要元信息。原 ID、密码哈希、二次验证、个人资料、会话／令牌、资源凭证、聊天和文件保持原身份及数据；并不把其他私人数据变成共享数据。用户名本来就是 `owner` 或账号 ID 本来就是 `owner` 均可转换。

已经转换的实例再次执行会返回 `already_converted`，不重复改写或重建账号，不覆盖已有备份。未知／混合格式、备份失败或转换失败会终止；事务失败保留旧数据库。失败留下的备份目录保留供检查，修正问题后请使用新的备份路径。

## 回退

新版不保证旧程序能读取转换后的账号布局。需要回退时，先停止新版，另行保留升级后产生的数据，再恢复迁移前的完整 `data/` 副本、原配置及旧二进制。外置工作区如需回退，用对应的 `workspace/` 副本；备份的 `manifest.json` 记录原路径。备份内容包含私密数据和主密钥，应按生产数据保护。

不要将备份数据库文件直接覆盖到仍在运行的服务，不要只回退二进制。恢复旧快照会丢弃升级后的新记录，恢复前需要保留它们。
