# 开发协作流程

本文维护任务隔离、分支、验证、提交、合并与清理流程。开发环境见[环境约定](environment.md)，验收入口和服务生效见[验收规范](acceptance.md)。

## 适用范围

- 先按修改对象判断是否需要 worktree：已由 Git 跟踪或计划纳入版本管理的代码、测试、配置和文档，适用本节的独立分支与 worktree 流程。尚未跟踪但准备提交的新文件也属于此范围。
- 仅维护 `internal-docs/` 等已被 Git 忽略、且不准备提交的内部资料（如推广文案、研究笔记、内部规划）时，直接在资料原位置修改；不为此创建分支或 worktree，也不走提交、合并、服务验收或项目构建测试流程。交付时提供文件链接并核对内容及引用资源即可。若同一任务还涉及版本管理范围内的修改，则按本节创建 worktree；随开发产生的内部记录保存在该任务 worktree，已有内部资料仍在原位置维护，清理时按[公开内容与内部资料](../releasing/public-content.md#公开内容与内部资料)要求保留资料。
- 主工作目录（仓库的主 worktree，可通过 `git worktree list` 确认）固定保留 `main`，用于查看代码、集成已完成的分支和运行主分支服务。**禁止直接在主工作目录修改代码，也禁止在该目录切换到功能分支进行开发。** 上述版本管理范围内的功能开发、修复、重构及其测试、配置和文档修改均在独立 worktree 中完成。

## 开始任务与开发

- 开始任务前先检查 `git status --short --branch` 和 `git worktree list`，确认当前目录、分支与已有任务。不得覆盖、重置或清理他人的未提交变更。
- 每个独立任务使用一个分支和一个 worktree，从最新的本地 `main` 创建；如已有该任务的 worktree，则继续使用。分支名使用 `feat/<task>`、`fix/<task>` 或 `chore/<task>` 等有明确含义的名称。
- worktree 推荐放在主工作目录下的 `.cache/worktrees/<task>`，该目录由现有 `.cache/` 忽略规则排除，不纳入 Git 提交。例如，在主工作目录执行 `git worktree add -b feat/<task> .cache/worktrees/<task> main`。路径统一以主工作目录为基准，不在任务 worktree 内嵌套创建。不能创建 worktree 时先解决路径或权限问题，不得退回主工作目录直接开发。
- 创建后，版本管理范围内的编辑、依赖安装、代码生成、构建、测试及提交都以对应 worktree 为工作目录。并行任务不得共用同一个 worktree，也不得修改其他任务的 worktree。
- Runtime 新增、删除或改名公开函数、具体方法或接口方法时，同步维护 `runtime/tests/coverage-*.md` 中的行为测试映射；嵌入接口展开的方法也需要登记。局部包测试通过后仍须运行 `npm run check:contracts`，提交前和 rebase 后运行 `npm run check`。映射必须引用实际验证该入口行为的测试，缺少断言时补测试，不得自动填入无关用例或跳过清单检查。`make -C runtime test` 等测试入口会先执行全仓库契约清单检查，不受 `PACKAGES`、`RUN` 筛选影响。
- 各 worktree 的依赖安装目录、构建产物、编译缓存和 Runtime 测试数据独立管理；可复用下载遵守[共享下载缓存约定](environment.md#开发机器目录与共享下载缓存)。不得复用或修改主工作目录的运行数据库、凭证及私有数据目录。开发和验收期间不得停止或替换其他任务或主分支的服务；合并完成后按[合并后的服务生效](acceptance.md#合并后的服务生效)要求更新主分支服务。

## 验收、合并与清理

- **任务完成后必须先提供验收入口并等待用户验收，不得直接合并。** 只有用户验收后明确授权合并，才能将任务分支合并回 `main`；开发完成、测试通过或提供验收链接均不代表获得合并授权。等待验收期间保留任务 worktree 和验收服务。
- 合并前必须在任务 worktree 内执行 `git rebase main`，将任务提交重放到最新本地 `main` 上，保持新增历史线性；不得使用 `git merge main` 同步任务分支。Rebase 冲突在任务 worktree 内解决，完成后重新执行相关验证，不得在主工作目录手工修改代码。多个分支按顺序集成；前一个分支合并后，后续分支必须基于更新后的 `main` 重新 rebase 并验证。已共享的任务分支在 rebase 前需协调使用者，重写远端任务分支须另有明确授权。
- 提交、合并和推送按用户已授权的范围执行；完成开发不代表自动获得推送授权。合并回 `main` 时确保主工作目录干净，必须使用已验证分支的快进合并（`git merge --ff-only <branch>`）；若无法快进，回到任务 worktree 重新 rebase 并验证，不得改用生成合并提交的方式集成。合并后确认状态与必要的集成检查。
- 交付时说明任务分支、worktree 路径、验证结果及是否已合并，并按[验收交付标准](acceptance.md#验收交付标准)提供验收入口；仅 worktree 验收服务中需要登录的页面要求提供可直接登录的一次性链接。主工作区服务提供普通访问地址即可，无需生成或提供登录链接。
- **合并成功且主分支服务生效验证通过后，必须清理本任务的 worktree，无需等待用户再次要求。** 清理前确认变更已提交并合并，精确停止该 worktree 的验收服务，妥善保留需要留存的验收数据，再使用 `git worktree remove` 移除目录；不得强制删除含未提交变更的目录，也不得影响其他任务的 worktree 或服务。合并交付时说明清理结果。
